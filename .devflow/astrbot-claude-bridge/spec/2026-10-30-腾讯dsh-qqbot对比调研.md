## 一、结论摘要

1. **两者解决的问题不同**。dsh-qqbot 是"把 DSH 自家 agent 接到 QQ"的**渠道插件（channel plugin）**，代理能力由 DSH 宿主提供；本 mission 是"把外部 CLI（Claude Code / Codex）接到 QQ"的**代理桥（agent bridge）**，隔离边界须由插件自身在 CLI 层建立。
2. **dsh-qqbot 没有解决 T02 的"工作目录外拒读"，而是绕开了它**：官方实现中不存在"非白名单只读"档位，不存在工具级允许/拒绝列表，也不存在进程级读取边界；它用「白名单准入 + 独立 workspace + 敏感操作审批」兜底。
3. **它在消息工程上强于 `cc-qq`**（流式双轨、被动回复三级兜底、审批 nonce、交付物投递）；**在权限与隔离上弱于 `cc-qq`**（无档位、无群间隔离、无审计、无审批超时）。
4. **附带查实 `cc-qq` 的三条现存缺口**（见第六节 6.2），其中"群级与用户级没有取交集"与 `spec/design.md` 的原始要求不一致，属安全语义偏差。

## 三、各维度对比

### 3.1 权限模型

| 维度 | dsh-qqbot | cc-qq |
| --- | --- | --- |
| 准入 | `c2cMode`/`groupMode`：open / allowlist / disabled；白名单为空即拒绝所有人（0.5.4 收紧） | 群须在 `enabled_group_ids`；群内非白名单降为 `guest` 只读放行 |
| 分级 | 无只读档，放行即全权 | 四角色 × 三档位 |
| 工具粒度 | 无 allow/deny 列表，工具面由宿主 preset 决定 | readonly 档给 `Read,Grep,Glob,TodoWrite`；workspace 档 hook 分类审批；full 档守护 hook |
| 群间隔离 | 无，所有群共用同一 workspace 与 media 根 | 每群独立 `work_dir` |
| 管理命令 | 仅 `/model`、`/preset` 要白名单；`/new`、`/compact`、`/stop` 任何人可发 | 全部命令有最低角色门槛 |
| 审计 | 无持久化审计，成功批准/拒绝不落日志 | `permission_audit` 表全量落库 |

源码定位（相对 `tmp/refs/dsh-qqbot/`）：

- 访问控制默认值与判定：`src/config.ts:104-107`、`src/config.ts:127-132`、`src/gateway/middleware-setup.ts:43-57`
- 工作目录：`src/config.ts:66-67`、`src/shared/dirs.ts:19-20`、`src/session/session-manager.ts:544-545`
- 管理命令鉴权：`src/commands/auth.ts:21-33`、`src/commands/model.ts:8-16`、`src/commands/preset.ts:10-17`

判断：这是两条不同的安全哲学。dsh-qqbot 是「信任名单，名单内不做细粒度约束」；本 mission 是「所有人都可进入，但用档位与边界收敛能力」。

### 3.2 工作目录与目录外拒读（T02 直接相关）

dsh-qqbot 在该维度的**全部**实现：

1. 全局 `cwd`，缺省 `~/.dsh-qqbot/workspace`，与宿主进程目录解耦；
2. `qqbot_send_file` 与交付物投递的**发送路径白名单**（`realpath` 判定，阻断符号链接逃逸）；
3. 群聊默认开放但要求 `@bot`（`requireMention` 默认 `true`）。

它**没有**每群 cwd、每会话 cwd、只读挂载或任何进程级读取边界。

源码定位：`src/media/send-media.ts:39-80`、`src/media/send-file-tool.ts:123-129`、`src/transport/deliverables.ts:43-55`、`src/config.ts:117`。

结论：**官方参考实现不能为 T02 提供技术方案**，只能为需求取舍提供先例。

其自身暴露的两处边界（不应照搬）：

- `qqbot_describe_image` 读本地路径**不过路径白名单**，URL 分支无私有 IP 阻断（`src/media/vision-tool.ts:80-105`、`:277-290`），仅在 `vision.enabled`（默认关闭）时暴露；
- `qqbot_send_file` 的 `target` 只校验 `c2c:`/`group:` 格式，**不校验目标归属**，可显式发往任意 openid（`src/media/send-file-tool.ts:41-49`、`:109-127`）。

### 3.3 审批

| | dsh-qqbot | cc-qq |
| --- | --- | --- |
| 接入点 | 宿主 `approval/request` waterfall（`global+prepend`），非 QQ 会话 `next()` 让给 Web/TUI | Claude `PreToolUse` hook → 本机 Broker |
| 授权 | 按钮 + nonce；白名单模式下只认 `c2cAllow` 内点击者，身份缺失亦拒绝 | `/approve` `/deny`，admin 门槛 |
| 粒度 | 仅"允许一次 / 拒绝"，无 always | 同左 |
| 超时 | **无审批超时**，仅靠 abort / 会话回收 | 默认 300s，超时即拒 |
| 审计 | **无** | 全量落库，含 `approver_id` |
| 防死锁 | 命令与问答答案插在并发守卫之前 | `/approve` `/deny` 插在会话串行队列之前 |

源码定位：`src/features/approval-channel.ts:152-241`、`src/features/approval-renderer.ts:11-59`、`src/features/button-utils.ts:25-43`。

结论：两者对"审批不能排队"的处理一致，可互相印证设计成立；cc-qq 在审计、超时、fail-closed 上更完整，该维度无需借鉴。

### 3.4 会话模型

| | dsh-qqbot | cc-qq |
| --- | --- | --- |
| 会话键 | `qqbot:${appId}:${scope}:${peerId}` | `(platform_id, kind, conversation_id)` |
| 重启恢复 | `model-prefs.json` 三张表，`get→resume→create` 三段式 | SQLite `sessions` 表 |
| 空闲回收 | 有：30 分钟，回收时 cancel + dispose + 清 pending | **无**（会话常驻） |

源码定位：`src/session/session-manager.ts:451-572`、`src/session/idle-evictor.ts:22-35`、`src/model/prefs-store.ts:16-141`。

### 3.5 消息链路与流式

dsh-qqbot 的出站是一条完整流水线：

1. **静态/流式双轨**（`outbound-buffer`）：同时累积全量文本与流式会话，只有本次从未成功流式过才降级整段发送，不会出现"半截流式 + 整段重发"；
2. **节流而非防抖**（200ms）：chunk 持续到达时防抖会永久等待；
3. **分块感知 Markdown**：代码块不断、GFM 表格不拆、优先空行切；
4. **被动回复三级兜底**：显式 msgId → 缓存候选（群 5 分钟 / 私聊 30 分钟 TTL）→ 主动推送；每条消息最多 4 次被动回复；
5. **交付物投递**（`deliverables/present`）：模型声明产出文件，轮末自动发送，文本先于文件；
6. **工具结果结构化展示**：优先 `presentResult` 的 terminal/diff/read 卡片，fallback 原文。

源码定位：`src/transport/outbound-buffer.ts:48-99`、`src/transport/streaming-writer.ts:56-158`、`src/transport/chunker.ts:17-85`、`src/transport/reply-target.ts:23-69`、`src/transport/reply-limiter.ts:8-77`、`src/transport/deliverables.ts:41-87`、`src/transport/tool-presenter.ts:39-154`。

对照 `.devflow/cc-qq-full-migration/state.md` 中的流式延期项：cc-qq 当前是"攒齐 TEXT 一次返回"，改造需动 `main.py` 回复链路与 `send_text` 分段。dsh-qqbot 的**双轨结构**是该问题的标准解——增加一层 buffer，静态路径保持不变，流式路径失败自动回退，不必重写回复链路。

### 3.6 配置与管理面

dsh-qqbot 把配置做进 DSH 桌面版/Web 设置页（`dsh.client` + `settings.section` + 侧栏席位），扫码绑定、白名单编辑、模型覆盖均在端内完成；CLI 模式退化为终端二维码。源码定位：`src/client/`（1,199 行）、`src/setup/`（1,290 行）、`src/setup/persist.ts:204-262`。

这为本 mission 的 Web Console 目标提供了一个"官方形态"参考，但其权限模型较本 mission 简单，不能直接复用。

## 四、可借鉴设计（候选项，未批准）

按对本仓库的价值排序：

1. **流式双轨 + 只降级不重复**——对应 cc-qq 的流式延期项，属低风险增量改造。
2. **节流而非防抖**（200ms）与 `sentChunkCount===0` 才允许降级的判据。
3. **审批按钮 nonce + 点击者白名单 + 身份缺失 fail-closed**——cc-qq 已有 admin 门槛，可补"旧卡片防误点"这一层。
4. **被动回复三级兜底 + 每消息限额 + msgId/eventId 分开缓存带 TTL**——NapCat 侧主动消息配额问题同样存在。
5. **交付物投递（present）**：把"模型产出的文件"与"聊天回复"解耦，轮末统一投递。
6. **扫码绑定即授权**：绑定者 openid 直接写入私聊白名单并切 `allowlist`，重绑即换人，是干净的 owner 初始化模型。
7. **空闲会话回收 + 回收时清 pending 审批/提问**——cc-qq 会话常驻，长跑会积压僵尸会话。
8. **命令的 per-scope 可见性**（`scope: 'c2c'|'group'|'all'`，帮助按场景标注）。

## 五、明确不应照搬（候选项判断）

1. **单 workspace 全局共享**：所有群共用一个目录与一个 media 根，存在跨群文件触达风险。
2. **没有只读档**：与本 mission 的"非白名单只读"需求正交。
3. **无工具级白/黑名单**：工具面完全交给宿主 preset。
4. **无审计、无审批超时**：cc-qq 在该两项上更强。
5. **管理命令只看 `c2cAllow`，且 `c2cMode=disabled/open` 时直接放行**：群聊中切模型/预设可能不受控。
6. **视觉工具绕过路径白名单**：图片理解能力建设时不可复制该分支。

## 六、对本仓库 mission 的启示

### 6.1 对 `astrbot-claude-bridge` T02 卡点

事实：连腾讯官方参考实现都没有实现进程级"目录外拒读"，而是把需求降为"名单内全权 + 敏感操作审批"。

| 候选项 | 做法 | 代价 |
| --- | --- | --- |
| A. 需求降级（参照官方） | 非白名单用户**不服务**（而非只读），"只读"降为可选体验档 | 改变已对齐的需求边界，但可立即解开 T02 |
| B. 维持需求，缩小可开放面 | Windows 不开放 Codex；Claude Code 只开已实测的基础文件工具；macOS 用 Seatbelt 单独实测 | 与"本轮支持 Codex"冲突，需重新谈范围 |
| C. 引入外部隔离 | 容器 / 沙箱进程 / WSL | 与"Windows/macOS 原生运行"冲突（WSL 已被用户否决） |

观察：A 与 B 是同一事实的两面——T02 根因不是"配置没调对"，而是"Codex 在原生 Windows 上不提供该边界"。官方插件以 A 绕开，本 mission 以 B 硬顶。

### 6.2 对 `cc-qq-full-migration` 的现存缺口（跨 mission 观察）

1. **群级与用户级没有取交集**：`resolve_permission_profile` 是"群规则覆盖角色默认档"，群规则可把 `guest` 提升为 `workspace`/`full`；群白名单与全局白名单为**并集**。与 `spec/design.md:44` 的原始要求不一致，属安全语义偏差。
2. **`allowed_work_dirs` 不约束群规则的初始 `work_dir`**：只有 `/cd` 与 override 受约束。
3. **Codex 无逐次审批**：dsh-qqbot 同样没有，可作为"业界暂无成熟解"的旁证，宜写成"不可行/待上游"而非"待做"。

源码定位（相对 `integrations/astrbot/astrbot_plugin_cc_qq/`）：`permissions.py:193-206`、`policy.py:128-130`、`permissions.py:209-249`、`agents/profiles.py:215-262`。
