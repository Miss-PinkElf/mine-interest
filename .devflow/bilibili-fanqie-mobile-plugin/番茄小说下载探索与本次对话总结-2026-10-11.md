## 2. 结论与此前说法的修正

**公开下载思路确实存在，而且两个最初指定项目都值得研究。** 缺少当前版本的某个正文底层依赖，并不等于整个下载流程没有公开。

1. POf-L **当前**公开分支主要提供文档、构建和发行入口；README 和工作流明确当前 Rust/Tauri 核心来自私有仓库。
2. POf-L **公开历史**保留了 Python 下载器及单本 / 批量 CLI。最初只检查当前浅克隆（Shallow Clone），遗漏历史，这个调查范围不足已纠正。
3. Tomato **当前**公开了目录、任务规划、章节分组、第三方请求、重试、缓存、恢复和导出。缺口在官方模式所调用的外部依赖，以及第三方模式实际可用的正文服务。
4. yinian / Gavin 下载源码也公开，但它们取得正文的主要方式是请求第三方服务；有下载代码不等于自己实现了平台正文获取内核。
5. 网页还原路线有公开实现，可以研究直接从官网阅读页得到文本；当前网页返回正常不等于所有章节、所有书都可完整下载。

“当前核心为什么改成私有”的作者动机，本轮没有可靠证据，不能猜测。公开源码也不自动等于有复制和分发许可；没有发现许可文件的项目，先参考思路，正式复制前另行核查。

## 3. 下载到底是怎样完成的

### 3.1 整条链路

```text
小说分享文本 / 链接 / 编号
  → 解析并得到书籍编号（book_id）
  → 获取书籍信息及有序目录
  → 得到每章编号（item_id / chapter_id）
  → 逐章或分组请求正文
  → 必要时还原字体字符 / 解码协议内容
  → 清理段落、校验结果、保存章节及状态
  → 按目录顺序合并
  → 输出 TXT / EPUB 和缺失章节报告
```

“批量下载多本书”是在外层增加书籍队列（Book Queue）。单本下载内部仍要完成这条链路。正文来源只是其中一个环节；调用接口之后，章节对应、重试、恢复、排序和导出仍需要客户端实现。

### 3.2 第一步：确定书籍编号

输入可能是官网书页、阅读页、短链或一段分享文案。链接解析器（Link Parser）应提取链接并处理重定向，再识别书籍编号。阅读页中的编号有时是章节编号，需要查所属书籍；不要把所有数字串都认定为书籍编号。

得到 `book_id` 后，后续下载核心不必关心用户最初是粘贴链接、搜索选书，还是从书架选择。这三种方式都可以转成同一种书籍任务。

### 3.3 第二步：获取有序目录

项目通常从 `fanqienovel.com/page/{book_id}`、页面初始状态（Initial State）或目录接口读取书名、作者和章节列表。每一章至少需要编号、标题和目录序号。

目录序号是合并依据。网络请求完成顺序可能是第 5、1、3、2、4 章，最终文件仍必须写成第 1、2、3、4、5 章。只把“哪一章先完成就先追加到 TXT”用于并发任务，会导致错序。

### 3.4 第三步：请求正文，识别来源

主要有三种方式：

| 方式 | 客户端如何请求 | 得到什么 | 尚需承担的工作 |
| --- | --- | --- | --- |
| 官网阅读页 | HTTP GET `/reader/{item_id}`，解析 HTML 内初始数据 | 带 HTML 的正文，可能有字体混淆字符 | 字符还原、清理、校验及下载管理 |
| 第三方正文服务 | 向别人提供的 HTTP 地址提交章节编号 | 通常为已处理好的明文 JSON 或文本 | 检查契约、处理失败、保存及导出；其内部取文方法可能不公开 |
| 平台内部协议 | 直接请求平台服务，带所需设备信息、会话或签名 | JSON；部分路线为加密或压缩内容 | 按实际协议实现鉴权、密钥、解码 / 解密和版本维护 |

HTTP 客户端（HTTP Client）直接请求即可完成很多网页任务，不一定需要自动化浏览器（Browser Automation）。如果必须执行脚本、交互登录或分析动态请求，浏览器才成为相应环节的工具。

自动请求网页、提取数据通常叫爬虫（Crawler）；请求 JSON 接口也属于自动获取网络数据的做法。实现难点在获取正确数据和完整处理，而不在是否给它起名“爬虫”。

### 3.5 第四步：网页字符还原与协议解密不同

网页可能把正文中的汉字替换成私用区（Private Use Area，PUA）字符，再用特殊网页字体显示正常字形。浏览器看起来是汉字，直接复制初始数据却可能是乱码。

已观察到的两种公开方法：

- 静态字符映射（Static Character Mapping）：根据码点和预置字符表，把 PUA 字符替换回汉字。`fanqie-downloader` 使用这条思路。
- 字体映射（Font Mapping）：下载网页使用的 WOFF2 字体，读取字符映射表（cmap），再通过预置字形编号与汉字表还原。`fanqiexiaoshuo-Download` 属于此类。它会读取当前字体，但字形对应汉字的表仍是预置数据，不能说可以无条件识别任何新字体。

这两种方法通常是替换和映射，**不是密码学解密**。平台内部协议中的 AES、Base64、Gzip 是另一条链路，不能把网页映射表拿去当 AES 密钥。

### 3.6 第五步：清理与验证

从正文 HTML 中保留段落和必要换行，去除标签；同时检查空内容、错误 JSON、登录页、验证码页、试读提示、锁定章节和仍未还原的 PUA 字符。

不能只按 HTTP 200 宣布成功，也不能把第三方返回的错误说明写成小说正文。章节编号与返回内容应对应，缺失章节需要单独记录。网页只开放部分内容时，应明确导出范围，不能推测或补写原文。

### 3.7 第六步：章节缓存与断点恢复

每章独立保存结果；状态记录章节编号、成功 / 失败、重试次数和错误原因。重启时对照目录，验证已保存章节，跳过确实完整的部分。

只在内存中保存下载索引不等于持久断点恢复（Persistent Resume）。重试应有上限；超时、限流及业务响应失败都要进入明确状态，不能在返回错误 JSON 时无限循环。

### 3.8 第七步：按序导出与批量调度

按目录读取缓存并合并，最后比对预期章节数、成功章节数及缺失清单。TXT 输出以稳定顺序为核心；EPUB 另需章节结构、封面和元数据。

多本书可以由外层队列依次或有限并发执行。每本书独立记录结果，一本失败不阻断其余书。书籍并发与章节并发要共同限制，不能简单把两者相乘扩大请求量。

### 4.2 zhongbai2333/Tomato-Novel-Downloader

当前调查提交：`e2197970c366180bb566b8acfbda67cc1331a1ef`，有 MIT 许可文件。

源码链路是：`download/plan.rs` 准备书和目录 → `download/downloader.rs` 分派章节组 → 官方依赖或第三方请求 → `book_parser/parser.rs` 取正文与清理 → `book_manager.rs` 保存章节 / 日志 / 状态 → 按目录导出。

第三方客户端公开请求 `/reading/reader/batch_full/v`，将 `item_ids` 以逗号连接。它期待服务返回按章节编号组织的 `content/title` JSON；相同路径名称并不证明请求一定直接发给番茄官方。

官方模式调用 `tomato_novel_official_api::FanqieClient` 等外部实现，`Cargo.toml` 指向相邻目录 `../Tomato-Novel-Official-API`，本轮克隆没有该依赖源码。默认第三方 `api_endpoints` 为空，不能凭空下载正文。

入口限制也需注意：该版本命令行首次 `--download` 被禁用，`--update` 面向已有本地记录；网页任务接口仅允许一个活跃任务，返回 429 不代表自动排队。因此不能把循环调用首次下载参数当成已可用的批量办法。不过下载核心公开，可以研究新入口如何接入，实施仍需另行对齐和计划。

## 7. 官方接口、第三方接口与登录书架

### 7.1 官方到底有没有接口

官网和官方 App 为目录、阅读、账号及书架提供内部网络接口。**本轮没有找到面向普通开发者、提供小说全文下载的公开开放接口（Open API）文档。** 没找到不能证明绝对不存在，也不应把内部请求路径宣传成稳定开放 SDK。

第三方项目将某个模块命名为 `Official-API`，只能说明它试图访问官方来源，不能证明该模块由番茄官方提供或维护。知道 `/reading/reader/batch_full/v`、`/reading/crypt/registerkey` 等路径，也不等于掌握实际可用的鉴权和正文解码流程。

### 7.2 “第三方接口”意味着什么

用户的客户端把章节编号发送给另一个人提供的服务，由那个服务返回正文。服务背后可能读取官网、调用内部协议、使用缓存或应用内能力；若其服务端源码不公开，本轮无法确定实际做法。

因此，第三方调用的完整客户端流程仍可复用，但它不能单独回答“怎样不依赖别人服务取得正文”。要满足后者，必须选定并验证官网取文、直接协议或其他明确来源。

### 7.3 POf-L 如何登录、如何取书架：已知与未知

当前 README 描述登录后获取官方书架、同步阅读进度及退出时清理本机凭据 / 官方书架缓存。这是功能声明，未在本轮用用户账号验证。

作者在 [问题记录 337](https://github.com/POf-L/Fanqie-novel-Downloader/issues/337) 中说明：官方书架请求 `/reading/bookapi/bookshelf/info/v/`，再通过 `/api/bookshelf/multidetail` 和 `/api/book/simple/info` 补充书籍信息；缺失字段从目录来源回填。该回复是作者说明，涉及的当前实现属于私有核心，未进行源码核验。

[问题记录 339](https://github.com/POf-L/Fanqie-novel-Downloader/issues/339) 的登录白屏及 WebKit 进程崩溃说明登录流程会使用网页视图（WebView）相关组件。具体登录 URL、会话 Cookie / 令牌（Token）提取方法、凭据保存及请求头组合，本轮尚未确认。不能将通用推测写成已读源码的事实。

可以复用的通用结构是：

```text
用户完成登录 → 获得有效会话（Session）
  → 带会话请求账号书架 → 提取书籍编号
  → 转成普通下载任务 → 接正文来源 → 缓存 / 导出
```

书架负责选书，正文来源负责取文；取到书架不证明全文可得。旧项目里的网页随机标识 / `get_cookie` 也不能直接认定为账号登录。

## 9. 调查中的问题：现象、原因、处理方向

| 问题现象 | 原因 / 证据边界 | 解决方案或后续方向 |
