## 修正结论

两个项目都能提供下载思路。POf-L 当前公开分支没有下载核心，但公开 Git 历史保留旧版 Python 下载器和命令行工具（CLI）。Tomato 当前版本公开了目录解析、任务编排、章节分组、第三方正文请求、重试、恢复与导出，缺口在部分底层正文获取依赖。

此前只检查 POf-L 当前分支，未检查完整历史；也没有充分解释 Tomato 已公开的下载链路。这不足以回答用户希望复用思路的目标。

历史代码流程：输入书籍编号 → 查详情及目录 → 尝试整本正文响应或逐章请求 → 对齐章节顺序 → 保存状态及正文 → 完整性检查 → TXT/EPUB 导出。多本书由 `run_batch` 编排。

旧 CLI 已定义 `download` 与 `batch-download`，后者支持 `-i/--file`、`-p/--path`、`-f/--format` 和并发选项。因此可以直接研究其参数与任务组织方式，无需从零猜测 CLI 设计。上游还包含可选自动提交参数，本轮没有执行程序或任何提交。

关键依赖：`APIManager` 虽在代码中被称为“官方 API 管理器”，实际主机来自可配置节点池，包括第三方域名与 IP；仅凭类名不能认定直接调用平台官方服务。客户端主要取得已经可用的正文或整本响应，未在此调用链中找到独立平台鉴权和正文密码解密的完整实现。

历史 README 声称 MIT，但该历史树没有独立 LICENSE 文件；正式复制前需进一步核查许可。旧服务节点是否还可用没有实测。

正文请求公开契约：配置服务端点 → 拼接 `/reading/reader/batch_full/v` → 将章节编号用逗号拼接为 `item_ids` → HTTP GET → 解析 JSON。正文客户端注释明确期待服务返回可直接解析的内容：顶层或 `data` 对象以章节编号为键，值包含 `content/title`。

这已经足够研究如何将自己的正文服务接入下载流程，以及如何实现分组、恢复与导出。

两条正文分支的缺口不同：

- 官方路线调用外部 `tomato_novel_official_api::FanqieClient`，`get_contents_best_effort` 等关键操作位于该依赖中。本次克隆没有其源码；`Cargo.toml:79` 是相邻目录路径依赖。
- 第三方路线的请求客户端公开，但配置默认 `api_endpoints` 为空，需要实际可用的明文正文服务。客户端不会自动生成不存在的服务，也不实现底层加密正文解密。

`resolve_api_urls` 还暴露 `registerkey` 与 `batch_full` 的路径约定，但知道路径不等于拥有完整鉴权和解密实现。

命令行首次下载禁用只是现有入口限制，不代表下载核心缺失；网页界面与终端界面仍调用公开下载流程。正式改造成新 CLI，应按本仓库对齐（Align）和计划（Plan）后实施。

## 对本软件 / CLI 的候选价值

- Python CLI：POf-L 历史版提供现成的单本、批量、文件书单、保存与恢复思路，是直接相关的参考。
- Rust 下载核心：Tomato 当前版提供模块化目录、分组下载、端点轮换、恢复和导出，可参考或按许可复用。
- 独立正文来源：两者都不能据此直接认定已经提供当下可运行的完整平台协议内核。优先核验服务依赖，或单独实现已确认的正文适配器（Content Provider）。

## 本轮不做 / 后续阶段

旧版程序运行、旧节点可用性验证、新 CLI 与软件集成本轮未实施；本轮只核验源码与历史。后续确认“接受自配正文服务，还是要求独立正文获取”后，进入对齐和计划，再分别验证正文、单本与小批次。原有延期项继续保留，正文来源核验通过时恢复评审，不是永久放弃。
