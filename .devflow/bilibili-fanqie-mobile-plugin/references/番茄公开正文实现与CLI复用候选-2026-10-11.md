## 路线一：网页正文 + 字符还原

关键流程：书籍链接或编号 → 官网目录 → 按目录顺序读取章节页 → 提取正文 → 字符还原 → 保存章节 → 导出 TXT。

`fanqie-downloader/skill/fanqie_txt.py` 的 `down_zj`、`down_text`、`down_book` 实现了这条路线，正文不是转发到私人 API。它也具备命令行参数、缓存和下载流程，因此适合作为 CLI 的优先参考。

两个字符还原实现有实际差别：

- `fanqie-downloader` 使用按码点范围索引的静态字符表，未根据当前字体建立动态映射。字体改变可能产生乱码或错误字符，不能把请求成功视作正文正确。
- `fanqiexiaoshuo-Download/download.py` 的 `build_font_mapping` 下载当前字体，用 cmap 对接内置字形表。该方法仍依赖字形表有效；部分正文在 `download_chapter` 中直接复用前面取得的映射，没有逐章核验字体变化。

网页范围受实际访问权限约束。`fanqienovel-decryptor` 的 README 明确说明无法保证下载全部章节；字体还原解决已返回文字的显示编码，不能创造网页没有返回的全文。

本次少量联网核验：通过本机代理读取候选 README 的示例书页 `https://fanqienovel.com/page/7362803513664998424` 与章节页 `https://fanqienovel.com/reader/7362805062902481432`，均返回 HTTP 200。章节页包含初始状态、章节数据、WOFF2 引用与 3,056 个私用区（PUA）字符。仅检查页面结构和数量，没有输出正文，没有验证字体还原、全文或整本下载。

因此，这条路线已经有公开代码及当前页面结构证据，下一步应验证少量章节的真实输出质量，而不是直接宣称全本能力成立。

## 路线二：直接正文协议

`fqnovel-api/src/fq_api.rs` 公开 `batch_full` 与 `register_key`；`src/fq_struct.rs` 公开解密和 Gzip 解压流程，README 说明需要用户自己的设备标识。

可研究的结构是：设备与版本配置 → 正文请求 → 获取相应正文密钥 → 解码解密 → 解压文本。将网络调用、配置、正文处理分开，便于适配接口变化。

缺口：仓库最后提交在 2024 年，没有本轮可用性验证；设备标识获取需要特定环境；不应假设旧请求参数能够满足当前鉴权。它是 Cloudflare Worker 项目，尚无完整书籍目录、批量任务和 CLI 入口，需要自行实现这些部分。未发现 LICENSE，直接复制代码前须确认授权。

## 路线三：应用内调用并暴露本地服务

FQWeb 的 `MainHook.kt` 实现 Xposed 加载入口，`DragonService.kt` 调用番茄应用内部类，`HttpServer.kt` 提供目录、搜索和正文接口。

这说明“让原应用处理请求，再通过本地服务给其他软件调用”确实有公开实现。代价是依赖注入框架和特定番茄版本，当前说明只列出旧版本。它不符合现有独立 Kotlin 应用的默认形态，暂列研究备用路线。

## 推荐的候选方向

先验证网页路线，以 MIT 的 `fanqie-downloader` 为 CLI 行为参考，对照字体解析项目核查字符还原。先做到一本书的目录和少量可访问章节正确，再决定是否扩展到完整书单。

如果网页无法覆盖目标正文，则把原因明确区分为登录/权限、正文缺失、验证码、映射失败或接口变动，再评估直接协议路线。不要把网页只有部分正文包装成成功导出全本。

候选软件结构：正文适配器（Content Provider）负责目录和章节获取；下载核心（Download Core）负责顺序、重试、恢复与导出；CLI 负责参数和结果输出。软件调用同一下载核心，或调用 CLI 并读取结构化结果（JSON）。这是讨论方向，尚未批准实现或选定语言。

大语言模型（LLM）可辅助解析杂乱分享文案和确认候选书籍。字符还原与正文完整性必须依赖确定性转换和真实数据，不使用模型猜写缺失正文。
