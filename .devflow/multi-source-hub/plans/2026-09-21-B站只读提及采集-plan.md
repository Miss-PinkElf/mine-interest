# B 站只读提及采集实施计划（Implementation Plan）

目标：AstrBot 内运行独立采集插件，以账号 @ 通知为入口，保存来源、评论关系、视频简介或图文正文和附件。插件不注册发送评论、私信、点赞等接口。

架构：复用 AstrBot 插件生命周期和配置，不依赖完整 BiliBot 的内部方法或自动互动循环。小型只读客户端（Read-only Client）负责网络，采集器（Collector）负责补全，存储（Store）负责去重及原子落盘。原始数据和可读 Markdown 同时保留，失败状态可重试。

技术栈：Python、AstrBot、aiohttp、BeautifulSoup/markdownify；验证使用 `backend/.venv` 和标准库 unittest。顺序执行，代码仅用补丁修改；不自动提交。

## 审查修复：部分归档字段合并（Field Merge）

用户已确认采用字段合并，不采用每次尝试单独快照。

- 完整状态（Complete）仍不覆盖。
- 部分状态（Partial）重试时：新一轮成功的对象、评论、来源链接、已下载图片覆盖对应字段；新一轮失败或空结果保留上一轮已保存的原文、`raw.objects` 和本地图片。
- 缺失原因（gaps）按合并后的结果重算，不能因为本轮接口失败就把已有正文打成空。
- 合并后若仍有缺口，保持 Partial，不能把 Partial 直接视为 Complete。
- 队列：`process()` 隔离单条普通异常并写入 `attempted_at`；`CancelledError` 必须传播。修正 `desc is None` 等链式空值访问。
- 正文：渲染后既无文本也无图片才记空正文；纯图片正文在下载成功后可以 Complete。
- 评论关系：字段缺失或 null 记缺失并标 Partial；明确 `0` / `"0"` 表示没有父评论或根评论。

## 数据与验证契约

```text
notifications/<通知编号>.json：原始通知，先写入
items/<通知编号>/record.json：原始详情、父/根评论、状态、缺失原因
items/<通知编号>/content.md：可读正文和本地图片引用
items/<通知编号>/media/：内容校验后的图片
cursor.json：通知扫描进度，不代表内容采集成功
```

每个账号一个数据子目录；临时文件写完再替换。登录失效暂停本轮拉取并输出不含凭证的错误。重试不得覆盖用户修改的完整归档，重复通知直接跳过完整条目。身份由账号登录校验结果确定，不从通知发送者推断。

验收：普通视频顶层 @、根评论下 @、子评论下 @、动态 @、专栏 @ 五类真实样本；比较页面原文、图片和父评论。离线模拟通过仅证明内部逻辑，不能替代平台连通与完整性实测。
