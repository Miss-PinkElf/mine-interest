# 需求 7：登录告警与 B 站文档排版对齐

## 目标与范围

本轮分为两个可独立验收的子变更：

1. B 站采集插件独立检查和刷新自身登录凭据；QQ 登录失效或持续连接中断时产生告警。两者通过专用私有 GitHub 告警仓库的推送邮件提醒用户。
2. 调整 B 站视频、专栏和动态条目 `content.md` 的可读排版、评论图片归属和媒体去重，并保存视频封面；三类已有 B 站条目也按新格式重新生成。

需求 4 的真实运行验收（Verify）继续保留，不能用需求 7 的设计替代其未完成的网络诊断、历史 QQ 链接修复和新样本验收。原先在 `backlog.md` 中记录的“需求 5：B 站 Cookie 检查/刷新”由本轮需求 7 吸收；此对齐节点尚未实施，后续实现状态以需求 7 的 `tasks.md` 为准。

## 登录检查与告警

- B 站采集插件使用独立扫码登录与自动刷新；参考 `astrbot_plugin_bilibili_ai_bot` 的现有流程，但不直接读取它的配置文件，也不依赖它持续运行。两个插件当前使用同一 B 站账号。
- 先区分已确认的凭据失效、网络错误和其他接口错误。凭据失效时尝试刷新；刷新失败或确需重新扫码时告警。DNS 等采集网络错误只记录日志，不报成“登录失效”。
- QQ 确认需要重新登录时告警；连接持续中断超过可配置等待时间时，单独以“连接中断”告警。不能用“暂时没有收到消息”推断登录失效。计划阶段须核实 AstrBot 与 NapCat 当前可用的状态接口和重连事件，再定具体判定方式。
- 专用私有 GitHub 仓库是主告警渠道。采集端只把故障类型、脱敏账号标识、时间等最小信息写入告警记录并推送；仓库设置推送邮件接收地址。Cookie、刷新令牌、私人正文和媒体不得进入告警仓库或日志。
- 按故障状态变化发送：首次确认故障时推送一条，持续故障不重复推送，恢复正常时再推送一条。推送失败需保留待送状态并可重试，避免一次网络波动丢掉告警或产生邮件风暴。
- 告警检查与发送频率、QQ 断线等待时间采用具名配置和常量；计划阶段依据现有轮询节奏与误报风险确定默认值，不在函数体写魔法数字。

## `content.md` 的目标结构

视频采用已获用户认可的样本结构：

```text
# 视频标题
原视频链接、首次采集时间
视频封面（本地图片）

## 简介
视频简介正文

## 附件
本地视频链接，只显示一次

## 相关评论
按评论关系组织评论串；评论图片紧随其所属评论
```

专栏与动态沿用“标题、原文链接、首次采集时间、正文、相关评论”的阅读顺序。专栏和动态使用 `## 正文` 承载完整原文，正文图片保留在原文对应位置；有非正文附件时才显示 `## 附件`。纯图动态仍显示正文图片，空文字不生成空章节。视频独有的封面、简介和本地视频附件不能套用到没有这些对象的条目。

专栏原始 JSON 中有段落、图片和部分显式格式标记，例如 `content.ops[].attributes.header` 及 `opus.content.paragraphs[].text.nodes[].word.font_level`。转换器应优先使用这些结构化标记恢复有证据的标题层级；没有标记的普通文字不能仅凭“像标题”就自动升为 Markdown 标题。先前专栏预览中的“【这个网站能做什么】”“历史项目”“网站截图”曾被人工升为三级标题，核查 JSON 后已撤回。原始 JSON 两次出现同一张图片时，媒体文件只存一份，但原文中两个位置是否都显示应按原始结构保留；不得仅凭相同哈希删除原文中的一次引用。

用户明确要求原始文档生成不使用大语言模型（LLM）辅助判断排版。没有结构化格式证据时保留原样；若源数据的显式标题标记本身不符合阅读直觉，也先按原始标记忠实转换，并在预演中呈现，不由模型改写原始层级。

- 三类真实排版预览位于本机 Vault 相应条目同级的 `content-new`：视频 `items/bilibili/2026-09-28/video/...-BV1cueG6sE85/content-new`、专栏 `items/bilibili/2026-09-22/article/崩坏3剧情助手正式上线-40034538/content-new`、动态 `items/bilibili/2026-09-21/opus/记录一下-1230082413158203411/content-new`。这些路径相对于本机 Vault 根目录，不属于代码仓库。
- 不重复输出作品标题、作品链接、原始归档正文中的技术性 `trigger/parent/root` 标题，亦不在评论区重复输出视频附件。
- 同一作品的多次 `@` 继续合并。评论按平台评论 ID 去重；同一父评论兼任根评论时只展示一次。不同评论 ID 即使文本相同，也要保留并标出 ID，避免误删真实互动。
- 评论图片下载到本地媒体目录，正文链接放在所属评论下；相同文件按内容哈希（Content Hash）只存一份。视频封面从作品信息取得并下载到本地，正文放在标题信息下方；视频文件仍只在“附件”一处引用。
- 技术字段继续保留于 `envelope.json` 等结构化原始记录。`content.md` 是可再生成的人类可读投影；用户已明确本轮无需保留对它的手工编辑。
- 已有 B 站条目先预演重渲染、备份并核查评论 ID 与全部本地媒体链接，再实际更新。不得从当前重复的 `content.md` 反向解析出新的真相源；优先从已有结构化采集记录生成。

## 验收标准

1. B 站登录有效、刷新成功、确实失效且刷新失败，以及 DNS 错误分别得到正确状态；只有确认登录失效需要用户操作时触发对应告警。
2. QQ 重新登录要求和持续连接中断分别能产生不同告警；短暂重连不误报。
3. 专用私有仓库的故障与恢复各只收到一次推送，邮件端到端实测可达，敏感凭据不进入仓库。
4. 视频排版样本中的三次 `@` 全部保留，同一上级评论只展示一次；评论图片处于对应评论下，封面和视频均为可解析的本地链接，视频只出现一次。
5. 专栏和动态的标题、链接、正文与图片只按所属内容展示；多个不同评论 ID 仍保留，正文图片不误归为评论附件。
6. 三类存量 B 站条目迁移预演与实际结果可核对，原始结构化记录和无关条目不被修改。

## 本轮不做 / 后续阶段

- B 站 DNS、发布器私有性校验及旧 QQ 媒体链接缺陷继续由需求 4 的运行验收和问题日志处理；原因是它们不是登录失效。触发条件：恢复需求 4 的 Verify 路径时按 `bug-log.md` 排查。
- 整台电脑或 AstrBot 进程完全停止后的外部心跳监控本轮不做；本机停止后无法主动推送告警。原因是本轮聚焦账号登录与持续连接状态；用户以后要求监控主机/进程可用性时，独立对齐外部监控方案。
- 手工编辑 `content.md` 的保留与冲突合并本轮不做；用户已明确只询问覆盖风险，不要求此能力。若以后要把该文件当作人工编辑真相源，再独立设计双向编辑与冲突策略。
- 远端媒体上传、百度网盘及语雀同步继续按已有候选方案和延期记录单独对齐；本轮只在本地保存视频封面和评论图片。

## 进入计划前的技术核查

- 核实当前 B 站采集插件的扫码、刷新所需凭据与参考插件的可复用边界，确保两个同账号插件不会互相覆盖各自的登录状态。
- 核实 QQ 适配器（Adapter）可提供的账号在线、重连和需重新扫码的明确信号；若接口不能可靠区分，计划不得以消息静默时间替代。
- 核实专用 GitHub 仓库的推送邮件配置及实际投递；选择最小权限凭据和最小记录格式。
- 核实存量 B 站采集记录中视频封面、评论 ID、评论图片归属的数据完整性；不足的历史条目应记录缺口（Gap），不能猜造内容。
- 核实专栏和动态各种原文格式标记的含义与覆盖率，再制定到 Markdown 标题、粗体、列表及图片的确定性映射；没有标记时保留原样，不用大语言模型（LLM）推断。
