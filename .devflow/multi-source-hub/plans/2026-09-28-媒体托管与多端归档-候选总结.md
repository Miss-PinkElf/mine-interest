## 1. 问题的起源

多源信息中心（source hub）从 QQ 群转发、B 站采集到的媒体素材，目前以「采集时的原始 URL」形式落盘，例如：

```
https://multimedia.nt.qq.com.cn/download?appid=1407&fileid=...&rkey=CAMSMCeo...
```

这类 URL 内嵌**鉴权参数（rkey）**，**会过期**。文件自身也已注明：

> url 含 rkey 鉴权参数，会过期；属于私人数据，禁止提交到 git、禁止外传。

因此最初的诉求是：**找一个能长期托管这些文件、并提供稳定 URL 的图床（Image Hosting）**。

在选型过程中，依次评估了手上已有的三个会员服务：百度网盘、夸克网盘、语雀。结论是**三者都不能作为图床**，但各自有明确的、可以互补的定位。

## 2. 核心结论：三个会员都不能做图床

### 2.1 根本原因（共性）

三家都是**消费级产品（Consumer Product）**，都用 **Referer 防盗链（Hotlink Protection）** 保护自身带宽。这是**产品设计决策**，不是技术缺陷，也**与会员等级无关** —— 买什么档位的会员都不会解锁「对外稳定直链」。

**关键认知：会员买的是「容量 + 速度」，不是「直链权限」。**

### 2.2 平台能力对照（据公开资料查证，待实测）

| 维度 | 百度网盘 | 夸克网盘 | 语雀 |
| --- | --- | --- | --- |
| 官方开放 API（Open API） | ✅ 有，个人开发者受限 | ❌ 无 | ✅ 有（`/api/v2`） |
| 官方 MCP（Model Context Protocol） | ✅ 18 tools，**仅限企业开发者** | ❌ 无 | ✅ **19 tools，个人可用** |
| 官方 CLI（Command Line Interface） | ❌ 仅第三方 | ❌ 无 | ✅ **有官方 CLI** |
| 官方 Skills 生态 | ❌ | ❌ | ✅ 8 个 |
| API 限流（Rate Limit） | ❌ 上传 100 次/天 | — | ✅ 5000 次/小时 |
| **图片上传能力** | ⚠️ 有，但分享需企业认证付费 | ❌ | ❌ **官方明确「不支持附件上传」** |
| **外链可用性** | ❌ 临时链接 5~30 分钟过期 | ❌ 临时链接数分钟过期 | ❌ Referer 白名单，外部站点 403 |
| 合规风险 | 高（协议禁止自动化访问） | 高（Cookie 挂载） | 中（偏离文档产品定位） |

### 2.3 各平台的硬伤明细

**百度网盘**

- 直链内含 HMAC 签名的**临时令牌（Temporary Token）**，5~30 分钟过期，且绑定 `session_id` / `device_id` / `client_ip_hash`。
- 2024-07 起启用 **Referer 白名单**，仅放行 `pan.baidu.com` 一级域，外部引用一律 403。
- 开放平台个人开发者受**目录沙箱（Sandbox Directory）**限制，只能操作 `/apps/{应用名}/`；**分享功能需企业认证 + 付费**。
- **上传配额 100 次/天**，量级上无法支撑图床场景。
- 单账号 10 分钟内超 50 次直链请求触发滑块验证或限流（429）。

**夸克网盘**

- **无官方开放 API、无官方 MCP**。社区方案清一色为 Cookie 挂载（Alist / OpenList）+ 油猴脚本。
- Cookie 方案意味着**账号 Cookie 泄露 = 网盘被完全操控**，且随官方改协议随时失效，不适合服务端常驻。

**语雀**

- 图片存于 `cdn.nlark.com`，**Referer 防盗链只放行 `*.yuque.com` / `nlark.com`**，外部来源 403。`no-referrer` 绕过方案**仅对自有 HTML 页面有效**，URL 一旦离开可控页面即失效（Markdown / 聊天软件 / 第三方站点 / CSS 背景图均无法绕过）。
- **官方 MCP README 明确写明**：「当前不支持：评论读写、**附件上传与文件管理**、权限与成员管理……」。
- **官方 OpenAPI 没有附件导出接口**，图片不作为一等资源，只是文档正文的内嵌内容。
- 优点：URL 稳定（不像网盘几分钟过期）、限流宽松、AI 生态（MCP / CLI / Skills）最完整且个人可用。

### 2.4 一个被否掉的思路

**「自己的后端做代理，实时换直链」**（调用百度开放平台 API 取临时链接后 302 转发）技术上可行，但代价是：

- 需常驻服务器；
- 承受风控封号风险；
- 违反平台用户协议；
- 流量成本最终仍由自己承担。

**结论：收益不抵成本，不采纳。**

## 3. 目标架构（候选）

放弃「找一个图床」的思路，改为**分层（Layered）架构**，让每个会员承担它擅长的角色。

```
① 采集层（Collection）
   QQ 群转发 / B 站采集
        │  AstrBot 插件（已有）
        ▼
② 本地存档层（Local Archive）  ← ★ 真相源，必须有一份
   按天归档目录 + 索引文件
        │
        ├──▶ ③ 冷备份层（Cold Backup）
        │      百度网盘
        │      目的：异地容灾、大容量、不对外暴露
        │
        └──▶ ④ 展示层（Presentation）
               语雀文档
               目的：随时可查、可读、可检索
```

### 3.1 各层职责边界

| 层 | 承载 | 不承载 |
| --- | --- | --- |
| ② 本地存档 | **真相源**、原图、索引 | 对外分发 |
| ③ 百度网盘 | 冷备份、容灾 | 对外分发、实时读取 |
| ④ 语雀 | 人类可读的索引与展示 | 图片本体存储、机器调用的图片分发 |

**核心原则：图片本体（②③）与图片分发（④）必须解耦。** 不要让任何一层兼任另一层的职责。

### 3.2 接入方式：统一走 MCP / CLI

所有跨端操作**不写死接口**，统一通过 MCP 或 CLI 暴露为工具，由 agent 自行选择调用。

**百度网盘（③ 冷备份层）**

```bash
# 方式 A：官方 MCP（注意：官方文档称"仅限企业开发者注册调用"，个人仅"限时体验"）
claude mcp add --transport sse baidu-pan https://mcp-pan.baidu.com/sse

# 方式 B：CLI — bypy（Python，走官方 API 授权，合规性较好）
pip install bypy
bypy info          # 浏览器授权一次

# 方式 C：CLI — BaiduPCS-Go（第三方，功能最全，但封号风险高）
BaiduPCS-Go sync /本地目录 /云端目录
```

> 选型倾向：**冷备份场景「写入为主、读取极少」，bypy 的合规性优势更重要**；BaiduPCS-Go 作为速度兜底备选。此倾向**待验证**（见第 5 节）。

**语雀（④ 展示层）**

```bash
# 官方 MCP（19 tools，个人可用）
claude mcp add yuque -- npx -y yuque-mcp --token=YOUR_TOKEN

# 或一键安装到指定客户端
npx yuque-mcp install --token=YOUR_TOKEN --client=cursor

# 官方 CLI
npm install -g yuque-cli
yuque whoami
```

**跨端同步的编排**：由 agent 读取本地索引，按需调用上述工具完成「上传 / 生成文档」，**不新增硬编码的同步脚本**。

## 4. 索引与目录设计（本方案的核心）

> 用户明确要求：**上传时需要自动维护一个索引或目录，方便下载和寻找。**

索引是这套架构的**枢纽**：它同时服务于「本地查找」「网盘恢复」「语雀展示」三个场景。因此**索引格式必须先定，再谈上传**。

### 4.1 目录结构（建议）

```
图库/
├── 2026-09-28/
│   ├── index.md            # 人类可读索引（真相源）
│   ├── index.json          # 程序可读索引（由 index.md 派生或同源生成）
│   └── media/
│       ├── a1b2c3d4.gif
│       └── e5f6a7b8.jpg
└── 2026-09-29/
    └── ...
```

**命名约束**：媒体文件名使用**内容哈希（Content Hash）+ 扩展名**，**不保留原始文件名**。

- 理由：原始文件名（如 `C7DC02D6C3B23FDCA8ADAC057F77D873.gif`）无语义、易重复、不利于去重；
- 哈希天然支持**去重（Deduplication）**——同一张图重复采集只存一份。

### 4.2 索引条目字段（草案）

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| `hash` | 内容哈希，兼作文件名 | `a1b2c3d4` |
| `ext` | 扩展名 | `gif` |
| `size` | 字节数 | `8851998` |
| `captured_at` | 采集时间（UTC） | `20260928T105053Z` |
| `source_type` | 来源类型 | `qq_forward` / `bilibili` |
| `source_id` | 来源标识 | 群号 / 转发 ID / 稿件 ID |
| `origin_url` | 原始 URL（**仅留档，不作引用**） | `https://multimedia.nt.qq.com.cn/...` |
| `description` | 内容描述 | 由 LLM 生成（见 4.3） |
| `tags` | 标签 | `["表情包", "动漫"]` |

> **关键约束**：`origin_url` 字段**只作历史留档**。任何下游引用一律指向 `hash` 派生的路径，**不得引用 `origin_url`**（因为它会过期）。
>
> **延伸建议（待决策）**：架构上应「存对象 key，不存完整 URL」—— 由 `存储域名 + key` 在运行时拼出 URL。这样未来更换存储或域名时，数据无需迁移。

### 4.3 LLM 辅助索引（暂定，待讨论）

> **状态：暂定（Tentative），待讨论** —— 本节仅为方向性建议，**需与作者专门讨论后才能确认**。当前**不作为既定设计**，**不进入实现**。相关待办见第 5 节 **Q4**。

`description` / `tags` 字段**不硬编码规则**，交由 LLM 生成：

- 图片内容描述、自动打标、按主题归类；
- 判断是否与已有素材重复（近似去重）；
- 为语雀文档生成可读的分组标题与摘要。

这与项目既有约定一致：**能由 LLM 介入判断的，就不写死规则。**

**以下为方向性描述，具体方案未定，需讨论：**

- 打标的粒度与受控词表（Controlled Vocabulary）是否需预先定义，还是完全自由生成；
- 近似去重是否需要，以及判定阈值如何设定；
- 模型选型（成本与效果如何权衡）、是否需要人工复核环节；
- 存量素材是否回溯处理，还是仅对新采集生效。

### 4.4 索引的三端映射

| 端 | 索引形态 | 说明 |
| --- | --- | --- |
| ② 本地 | `index.md` + `index.json` + 目录树 | 真相源 |
| ③ 百度网盘 | 镜像同样的目录结构 | 用 `sync` 增量同步，索引文件随之备份 |
| ④ 语雀 | 每篇文档对应一天 / 一个主题 | 正文列出条目；图片是否内嵌见第 5 节 |

## 5. 待决策项（Open Questions）

> 以下问题**尚未定论**，是推进本方案的前置条件。在解决前**不进入实现**。

### Q1（阻塞项）：语雀里的图片从哪里来？

语雀**官方 API 不支持图片上传**，图片进不了 `cdn.nlark.com`。因此语雀文档若要显示图片，只有两条路：

- **选项 A**：文档内嵌**外部图片 URL**。前提是图片存在一个**无防盗链的对象存储（Object Storage）**上（如 Cloudflare R2 / 阿里云 OSS）。语雀文档本身不受 `cdn.nlark.com` 防盗链影响（防盗链针对的是语雀自己的 CDN）。
- **选项 B**：语雀文档**只放文字索引**（标题、来源、描述、标签），不放图片本体；图片查看走本地或百度网盘。

**这是个真正的分叉点，取决于「展示」到底要展示到什么程度：**

- 若只需「随时翻阅收集了什么」→ **选项 B 足够**，架构里不需要引入对象存储，成本最低。
- 若需「在语雀里直接看到图片」→ **必须引入选项 A 的对象存储**，这是唯一能提供稳定无防盗链 URL 的层。

> **注**：对象存储（Cloudflare R2 等）在本次讨论中**未被用户确认采纳**，此处仅作为选项 A 的技术前提列出，**不构成已批准方案**。

### Q2：百度网盘的写入路径选哪个？

- 官方 MCP：官方文档称「仅限企业开发者注册调用」，个人仅能「限时体验」，**密钥会不定期变更，不能用于正式环境**。
- `bypy`：走官方 API，合规性好，但受**上传 100 次/天**配额限制，需评估日均采集量是否够用。
- `BaiduPCS-Go`：走非官方接口，无该配额限制，但**存在封号风险**，且可能被限制上传。

**需先确认日均媒体增量**，才能判断配额是否够用。

### Q3：语雀 Token 权限是否可用？

语雀个人 Token 在 `https://www.yuque.com/settings/tokens` 创建。公开资料对「Token 是否需要超级会员」说法**不一致**，需**实测确认**用户当前的「专业会员」能否创建。

**这是 30 秒就能验证的事，应最先做。**

### Q4：LLM 辅助索引的具体方案（暂定，待讨论）

**问题**：第 4.3 节的「`description` / `tags` 交由 LLM 生成」这一方向，**需与作者专门讨论后才能定稿**，当前**暂定**。

**性质**：**不阻塞**架构决策。它只影响索引的「充实程度」，不影响本地存档 / 冷备份 / 展示三层架构的搭建 —— 可以在索引跑通之后再补。

**待讨论的子问题**：

- 打标粒度：是否预先定义受控词表（Controlled Vocabulary），还是完全自由生成；
- 近似去重：是否需要，判定阈值如何设定；
- 模型选型：成本与效果如何权衡，是否需要人工复核；
- 存量处理：是否回溯处理已有素材，还是仅对新采集生效。

**触发条件**：索引 schema（第 7 节第 4 步）落地后，再专门讨论本节。

> **注**：本项属于**暂定项**，**不是「不做」**，也不得理解为永久放弃。按项目约定，延期项需写清「暂不做的原因 + 后续触发条件」，故在此登记。

## 6. 风险登记

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 百度网盘第三方 CLI 封号 | 冷备份中断 | 优先 bypy；降低并发；保留本地真相源 |
| 百度开放平台配额不足 | 备份不完整 | 实测日均增量；必要时分片调度 |
| 百度 MCP 密钥变更 | 不可用于正式环境 | 不将 MCP 作为正式写入路径 |
| 语雀 API 无图片上传 | 展示层受限 | 见 Q1，需先定选项 A / B |
| 语雀 Token 不可用 | 展示层不可用 | 见 Q3，最先验证 |
| 索引格式定得太晚 | 后期迁移成本高 | **索引先定，再谈上传** |
| 原始 URL 过期 | 素材永久丢失 | ② 本地存档层为真相源；及时转存 |
| 第三方免费图床关停 | 链接大面积失效 | **不用第三方图床**；重要素材多端留存 |

## 7. 下一步（建议顺序）

按「先验证、后设计、再实现」排列，**每步都有明确的验证标准**：

1. **验证语雀 Token（约 30 秒）** → 验证标准：能成功创建 Token 并 `yuque whoami` 通过。
   - 打不开 → 第 ④ 层改用本地 Markdown 索引，语雀路线放弃。
2. **统计日均媒体增量（约 5 分钟）** → 验证标准：得出日均图片张数与总体积。
   - 用于判断 Q2 的配额是否够用。
3. **确认 Q1 选 A 还是 B** → 验证标准：明确「语雀里要不要直接看到图片」。
   - 选 A → 需要评估对象存储选型（另开文档）。
   - 选 B → 无需对象存储，可直接进入第 4 步。
4. **落索引 schema 与目录结构** → 验证标准：产出 `index.md` / `index.json` 样例各一份。
5. **改造 `sourcehub-image-urls.json` 的存储结构** → 验证标准：不再存完整 URL，改存 hash + key。
6. **接入 MCP / CLI** → 验证标准：agent 能通过工具完成一次「归档 + 生成语雀文档」的闭环。

> 第 5 步与本方案的其他决策**解耦** —— 无论最终选哪条路线，「不存完整 URL、改存 key」都是正确的，可以最先动手。
