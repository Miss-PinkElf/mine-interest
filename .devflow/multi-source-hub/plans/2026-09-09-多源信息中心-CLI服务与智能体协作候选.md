# 面向智能体的命令行与服务形态

## 用户已明确的方向

1. 原始数据（Raw Data）保留，只有用户可以编辑；二次处理内容（Derived Content）由用户与人工智能（AI）共同编辑。
2. 自动整理默认开启，必须有开关，同时支持手动整理。

## 候选形态比较

| 候选 | 能力与使用方式 | 取舍 |
| --- | --- | --- |
| 纯命令行工具（CLI） | 外部智能体按需执行收集、检索、更新等命令 | 简单；命令退出后不会自行继续同步和整理，需外部调度器或运行中的执行者 |
| 仅后台服务（Service） | 长期接收资料、安排任务，通过应用程序接口（API）调用 | 自动化方便；日常终端调用还需适配入口，并依赖服务运行 |
| 共用知识核心，提供命令行入口和可运行的后台服务（推荐） | 人与外部智能体调用命令；后台负责持续接入和任务安排；双方共用数据与规则 | 同时覆盖手动与自动场景，但要明确写入协调及实际智能体执行者 |

“服务”不必等于云端部署。可以先讨论本机进程；是否必须常驻、是否开放网络、首期提供哪些入口，都尚未确认。

## 推荐分工

| 部分 | 职责 |
| --- | --- |
| 知识核心（Knowledge Core） | 原始资料保存、条目与页面访问、结构校验、引用、修改记录及受控写入 |
| 命令行接口（CLI） | 对人及能调用命令的智能体提供可发现命令、参数说明、结构化输出和错误信息 |
| 后台服务（Service） | 接收更新、安排任务、执行自动整理开关、提供运行状态 |
| 智能体执行器（Agent Runner） | 接收整理目标、结构约定与工具说明，由智能体判断读哪些资料、更新哪些主题、调用什么工具 |

自动模式与手动模式改变的是任务触发方式，应该复用同一套整理能力。来源含义、主题关联、何时新建页面由模型辅助判断；权限、开关、格式校验和写入完整性由程序明确执行。

工具可暴露读原文、查目录、检索、读页面、提交页面修改、查看历史等基础能力。外部智能体已有推理能力时，可直接用这些工具完成整理；提交整项后台整理任务则是另一种入口，不能强迫所有请求都再嵌套调用一次模型。

若目标客户端需要模型上下文协议（MCP），可讨论薄适配层；它只负责暴露同一组能力，不另外复制知识库逻辑。此处未决定是否首期提供 MCP 或网络 API。

## 两种日常使用场景

- 用户对外部智能体说“把这些收藏整理到某个主题”：智能体读取工具说明与结构约定，调用知识核心提供的能力，读取原始数据和已有页面，更新二次内容并记录修改历史。
- 来源有新数据且自动整理开启：运行中的后台安排任务，调用已配置的智能体执行器完成整理。没有可用执行器时只能保存资料并记录待处理状态，不能声称仅凭工具接口就实现自动整理。

关闭自动整理开关，推荐含义是停止自动触发新的整理任务，手动整理与原始数据接收仍可使用。开关对已运行任务和重新开启后的积压任务如何生效，留待后续具体设计；这不是已批准的细节。

## Git 管理历史的边界

- 推荐用独立的知识数据仓库管理原始文本的用户修订、二次页面、结构化元数据；与产品代码仓库分开。
- 完成一次整理后形成可回看的修改记录，标明执行者和关联来源；具体记录粒度未确认。
- Git 能提供差异、历史与恢复，但不负责判定语义冲突，也不自动阻止模型改原文。原始数据权限仍需工具及执行环境落实，不能只靠提示词或版本历史。
- 对二次内容共同编辑，建议写入前检查所依据的版本；版本已变化时重新读取或报告冲突，不直接覆盖。这是候选策略，不是已批准实现。
- 图片和视频保留本地副本及来源引用；大媒体是否进入普通 Git、采用大文件存储（Git LFS）或独立媒体目录，需结合规模决定，不预设所有二进制都入普通 Git。
- 产品对知识数据的版本记录，与本次开发中的代码提交（Commit）授权无关；本轮未执行任何提交。

## 指定信息源收集与增量去重候选

以下能力目标已获确认，具体机制为候选（Candidate）。

- 开关建议：后台运行开关控制持续同步与任务执行；自动整理开关只控制自动触发知识整理。关闭后台不应丢失资料或进度；手动命令按需运行的能力建议保留。首期是否增加每源自动收集开关尚未决定。
- 工具建议：智能体可查看已配置信息源并调用指定来源的收集动作，默认从已保存进度继续，也可指定历史范围；返回新增、跳过重复、源版本变化、失败及进度。此处不是最终工具命名或参数规格。
- 判断分工：智能体决定收集哪个源、什么范围以及如何整理；程序负责身份判重、进度、重试及写入一致性。不能把可靠性判断只交给模型。
- 增量收集（Incremental Collection）：优先使用平台游标（Cursor）或变更版本，时间范围作为按源可用的补充。时间边界可重叠回看再去重，避免同一时间多条消息或延迟到达漏采；无法穷尽的平台历史修改需通过按需复查或范围回采发现，不承诺仅靠时间绝不漏采。
- 去重（Deduplication）：优先使用来源实例、来源条目标识（Source Item ID）和版本确定是否已保存。聊天可用平台及会话内消息 ID；仓库文档按来源仓库、路径与文件版本区分，不因仓库其他文件提交就重复创建未变化的文档。
- 缺少稳定 ID 的来源，由适配器（Adapter）结合来源定位、时间与内容指纹（Fingerprint）确定识别策略。不能全局仅以正文哈希（Content Hash）合并不同来源的相同内容，避免丢失出处；无法区分的条目应保留不确定性，不能用模型猜测后静默丢弃。
- 源内容变更建议追加版本，原文保留；用户编辑过的本地原文不被再次收集覆盖。判重比对平台取得的源版本或快照，而非用户修改后的正文。
- 手动和后台共用增量进度与判重入口；并发写入需防止“双方都检查不存在后重复创建”。保存成功后再推进进度，部分失败可重试，不能提前越过失败条目。
- 手动限定时间回采不应错误推进常规同步进度；进度必须与来源及收集范围对应。
- 关闭或开启自动整理后如何处理积压、已运行任务如何停止，仍需具体设计。

候选验收场景：同批资料连续收集两次，第二次无重复条目；手动与后台同时收集仍不重复；同时间不同消息均保留；来源新版本可追踪；失败重试不丢数据；用户编辑原文后重采不覆盖；跨平台同内容保留各自出处。

## QQ Bot 调研状态

用户希望优先考虑 QQ，并让信息源通过 Bot 接入。当前环境未能完成在线核验，以下只作候选方向：

- 官方 QQ Bot / OpenAPI：合规和长期稳定性优先，需核验私聊、群聊、媒体、事件推送、主动发送、历史消息读取及权限限制。
- NoneBot2、Koishi：可作为统一 Bot 编排和适配层候选，需核验当前 QQ 适配器、插件生态、版本及许可证。
- Lagrange.Core、NapCat、go-cqhttp：通常属于非官方协议或客户端接入方向，可能更接近个人 QQ 场景，但稳定性、账号风险与合规边界较高，不推荐作为默认首选。

QQ Bot 更适合“用户主动把一条消息或图片投递给 Bot”，未必能合法稳定地读取完整历史聊天。因此首期需求应区分“Bot 收到的事件”与“主动历史同步”，不能假设有了 Bot 就能收集全部历史消息。
