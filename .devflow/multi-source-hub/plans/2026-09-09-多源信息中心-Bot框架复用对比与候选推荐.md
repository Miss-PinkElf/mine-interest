# 框架复用与独立知识核心

## 2026-09-09 14:32:30：用户确认

用户确认借用 AstrBot，承接本报告建议的独立信息中心分工。以下比较保留为决策依据，末尾原有待确认问题已由本次回复解决；验证清单及集成细节尚未批准，不代表可直接实施。下一步对齐 QQ 场景及首期验收。

## 本轮结论

推荐优先验证“AstrBot 负责多平台机器人接入与可替换的智能体执行，信息中心保留独立数据、命令行及工具接口”。理由是用户既要后台自动整理，又希望复用现成能力；AstrBot 已提供模型接入、工具循环、MCP 客户端、定时任务和管理界面。不是把整个信息中心做成 AstrBot 内部知识库，也不是已经证明它能满足所有需求。

若 AstrBot 的聊天流程、后台接口或运行体量不适合收集，退回 NoneBot2 或 Koishi 作为薄接入层，整理执行器另接。没有依据一开始就限定 NoneBot2，也无需同时维护三个机器人框架。

## 已确认需求

- 原始数据（Raw Data）保留且只有用户可编辑；二次内容（Derived Content）用户与 AI 均可编辑。
- 后台可独立运行且有开关；自动整理默认开启且有独立开关；可手动收集与整理。
- 外部智能体（Agent）可以指定信息源；重复调用、重试与后台并发不能重复入库。
- Git 是修改历史方向；最终知识中心以命令行接口（CLI）或服务形式供外部智能体使用。
- Bot 是统一交互入口，Github 等来源的实际内容仍由对应源适配器获取。

### NoneBot2

- [README](https://github.com/nonebot/nonebot2)：明确是事件处理框架，平台能力由适配器决定；列出 QQ 官方、OneBot、GitHub、Milky 等适配器。
- [QQ 事件源码](https://github.com/nonebot/adapter-qq/blob/master/nonebot/adapters/qq/event.py)：已找到 `GroupMessageCreateEvent`、`GroupAtMessageCreateEvent` 和 `C2CMessageCreateEvent`。官方全量消息不是仅凭 README 推测。
- 优势是接入层清楚、扩展直接。若后台整理仍需自己整合模型、工具执行与管理，则对当前需求未必最省工作。
- 未逐一审核社区 Agent / MCP 插件；不能写成 NoneBot 不支持这些能力。

### Koishi

- [README](https://github.com/koishijs/koishi)：控制台、插件市场、多账户与 TypeScript 是明确能力。
- [QQ 官方适配器文档](https://github.com/koishijs/docs/blob/master/zh-CN/plugins/adapter/qq.md)：区分 `qq` 和 `qqguild`；群与频道接口不可混用。文档部分配置体现较早接口形态，当前全量消息与认证兼容需要核验版本，不能据此宣称不支持。
- [中间件文档](https://github.com/koishijs/docs/blob/master/zh-CN/guide/basic/middleware.md)：明确指出中间件可能被更早过滤，捕获全部消息建议使用事件监听器或前置中间件。
- [生命周期文档](https://github.com/koishijs/docs/blob/master/zh-CN/guide/plugin/lifecycle.md)：插件可停用，事件和副作用可回收；但这不等于信息中心所需的可靠收集任务已实现。
- 若核心诉求是可视化管理大量 Bot，Koishi 很有竞争力；本轮没有证明其 AI 插件组合比 AstrBot 内置能力更省集成。

### AstrBot

- [README](https://github.com/AstrBotDevs/AstrBot)：集成平台、模型、插件、WebUI 和 Agent。
- [MCP 文档](https://github.com/AstrBotDevs/AstrBot/blob/master/docs/zh/use/mcp.md)：它作为客户端使用外部 MCP 服务的工具。不能将“支持 MCP”误写为“自动向其他智能体暴露了信息中心工具”；工具服务仍需我们提供。
- [内置执行器文档](https://github.com/AstrBotDevs/AstrBot/blob/master/docs/zh/providers/agent-runners/astrbot-agent-runner.md)及[上下文接口](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/star/context.py)：`tool_loop_agent` 接收工具集合并迭代执行；`llm_generate` 明确不会自动执行工具。前者仍要求消息事件上下文，不能当作现成通用后台 RPC 接口。
- [定时任务管理器](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/cron/manager.py)：存在持久任务装载、启用状态、基础任务与 Agent 任务方向。证明可复用调度设施，不证明与本项目数据版本和失败重试自动一致。
- [事件监听文档](https://github.com/AstrBotDevs/AstrBot/blob/master/docs/zh/dev/star/guides/listen-message-event.md)：消息对象提供消息 ID、会话、消息链、原始对象。
- [QQ 适配器](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/platform/sources/qqofficial/qqofficial_platform_adapter.py)及[Webhook 适配器](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/platform/sources/qqofficial_webhook/qo_webhook_adapter.py)：有全量群消息处理和引用字段保留逻辑。源中 `abm.timestamp = int(time.time())` 是处理时间，桥接必须从原始对象另取来源发送时间，不能直接拿它做源时间游标。
- [唤醒检查](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/pipeline/waking_check/stage.py)：插件匹配能激活处理，不只依赖 @ 或命令；过滤配置仍影响可见消息。
- [处理阶段](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/pipeline/process_stage/stage.py)：先执行激活插件，再检查通用模型启用开关。
- [会话状态检查](https://github.com/AstrBotDevs/AstrBot/blob/master/astrbot/core/pipeline/session_status_check/stage.py)：会话整体停用会阻断事件。因此“关自动聊天”“关会话”“关自动整理”“停后台”不能混成一个开关。

## 推荐架构及具体分工

- AstrBot 以可替换外部运行组件存在，负责 QQ/其他聊天平台接入与模型工具调用；先不建议修改其核心或直接复制大段源码。
- 小型桥接插件（Bridge Plugin）把已授权来源的事件与附件信息发送给独立信息中心。收集不依赖模型决定“是否调用保存”，否则模型不回复或失败可能造成漏收。
- 信息中心负责原始资料及权限、来源定位、时间、幂等性（Idempotency）、任务状态、Git 历史、页面及引用、自动整理开关。
- 信息中心提供应用程序接口（API）及薄命令行（CLI）；模型上下文协议（MCP）可以作为工具协议适配。同一组业务能力供外部智能体和 AstrBot 使用。
- 模型决定如何关联主题、修改哪些二次页面、调用哪些工具；格式校验、原文禁写及去重由程序执行。
- 自动模式由独立运行的服务安排任务，复用 AstrBot 执行器或另一个执行器。任务状态由信息中心统一记账；不能同时开两套调度独立扫描同一批待整理内容。
- 后台调用 AstrBot 的具体方式尚未选定，需要验证其任务上下文、完成回报、失败重试与无聊天回复运行方式。当前没有承诺无需桥接代码即可实现。
- 信息中心工具避免强制再嵌套调用一个模型；外部智能体可以直接读取和修改二次内容，也可以提交整项后台任务。
- AstrBot 的内置检索增强生成知识库（RAG Knowledge Base）不自动等同于本需求的持续维护维基（LLM Wiki）；本轮不迁入其私有知识库存储。

独立进程与 API 有助于降低耦合，但不自动消除许可义务；AstrBot AGPL 与插件/分发方式的具体关系在决定复用形式时核查，不凭架构图给出法律结论。
