## 最新澄清：多平台接入复用 AstrBot

用户指出多平台接入应由 AstrBot 承接。按此收敛：AstrBot 已支持的聊天平台直接复用其适配器，信息中心不另建重复的平台接入框架。本文的“通用接入协议”仅指一个桥接插件向独立信息中心提交统一数据封套；来源注册用于来源标识、范围和能力记录，不是重新实现聊天平台登录、连接或协议。

先以 QQ 收藏群验证同一桥接插件，再按实际需求配置其他 AstrBot 平台。只有 AstrBot 现有消息/插件能力不能满足的来源动作，例如拉取 GitHub 仓库文档版本，才评估补充工具，仍优先查找现成插件。GitHub 作为知识数据远端备份是另一项需求，不能与聊天平台接入混在一起决定首期顺序。此前将“多平台”理解为另建适配框架、据此要求二选一调整阶段顺序的提问撤回；GitHub 同步范围仍可单独对齐。

> 执行者要求：后续在开发流程（devflow）内先调用规格提案（openspec-propose），生成 proposal/design/tasks；实施使用计划执行（executing-plans）与实施子技能（openspec-apply-change）。本计划采用逐任务执行，不默认启动并行代理。代码提交（Commit）须用户单独明确允许，提交信息使用中文。

**目标（Goal）**：以通用接入协议接住 QQ 收藏群主动投递，独立保存可追溯资料，提供可靠去重和外部工具，再复用 AstrBot 进行可开关的自动整理。

**架构（Architecture）**：AstrBot 桥接只负责接入和可替换执行，独立服务负责结构化资料、任务、权限及版本。命令行和工具协议共用服务能力，平台字段通过适配器转换，不复制平台解析到核心。

**技术栈建议（Proposed Tech Stack）**：Python 3.12、FastAPI、Pydantic、SQLite、HTTPX、Typer、Git；工具适配使用官方 Python MCP SDK。使用 `backend/.venv`，不使用全局 Python。以上为计划工程建议，版本经任务 01 兼容验证后锁定；不据此推断用户已提供模型或远端授权。

## 0. 范围与阶段顺序

### 已批准需求

- AstrBot 作为接入/执行组件，信息中心独立。
- 用户把内容转发到现有专用收藏群；群内两三个号和群主均属于用户。
- 转发即收藏，不需要额外 @ 或命令。
- 原文仅用户可编辑；模型只读。二次内容人和模型共同编辑。
- 后台独立运行且有开关，自动整理默认开且可关、支持手动。
- 收集工具支持指定信息源，重复事件/重试不得重复入库。
- 修改历史使用 Git。
- 日常群规则/正则/模型筛选明确延期。

### 本轮新增输入及门禁

读取原始笔记时发现新增：先接多平台、允许其他开发者按协议扩展、统一结构化数据、本地与 GitHub 配合浏览。新增段落还明确要求讨论数据结构。

- 本计划先把平台无关数据与适配器契约落成任务，符合原始“插件化接入”愿景。
- **顺序澄清**：多平台由 AstrBot 承接，不因此新增一套平台框架或要求重排已确认的 QQ 闭环。先跑通单一桥接插件与 QQ 收藏群；GitHub 远端同步的范围和位置单独对齐，此前二选一问题撤回。
- **GitHub 不是 Git 的同义词**：Git 本地历史属于已定方向；远端上传需确认私有目标仓库、上传原文还是二次内容、媒体与自动推送策略。
- 不因多平台已由 AstrBot 承接而阻断共同基础计划；GitHub 远端同步未确认部分不写成已批准规格，不执行上传。
- “GitHub 作为资料来源”与“GitHub 存放个人知识”是两条不同能力，不能用实现后者冒充完成前者。

### 依赖顺序

`01 兼容与接入证据 → 02 契约 → 05a 最小服务与测试夹具 → 03 保存去重 → 06 AstrBot 桥接 → 07 收集恢复 → 最小真实 QQ 接入检查 → 04 原文权限/Git/基础二次写入 → 05b 完整 CLI/API → 08 工具 → 10 二次变更集 → 09 整理执行 → 11 集成验证 → 12 文档收口`

编号用于稳定追溯，实际执行遵循上述依赖顺序和 `../spec/tasks.md`。任务 05 分拆为 05a、05b，先建立夹具，避免前序验收依赖尚不存在的后序模块。任务 10 的确定性变更集先于任务 09 真实模型接入，合成资料不等于真实模型已通过。GitHub 同步 G 作为独立范围对齐记录，不在本次实施关键路径；用户确认目标与内容范围后再形成同步计划，不默认上传。

## 1. 数据和运行边界

### 数据建议

- SQLite 保存来源、事件索引、版本映射、任务和运行状态；唯一约束保证并发幂等。
- 原始正文/源事件和二次页面采用文件保存；写入暂存文件后原子替换，持久操作日志追踪跨文件、数据库、Git 的恢复。
- 原始来源快照与用户修订分开保存。重新接入按来源身份判重，不比较用户编辑后的正文。
- 文本与元数据进入独立知识数据 Git 仓库；媒体保存在内容寻址目录，清单引用内容哈希。普通 Git 不自动装入大媒体。GitHub 媒体方案由 G 任务确认，不能静默只上传失效引用。
- 二次页面提案携带基准版本，服务统一验证、写入、记录 Git 历史；整个变更集成功才标记整理完成。
- 产品日志、数据库、凭证、临时媒体下载 URL 不进入代码或知识远端仓库。源事件若含短期鉴权信息，保存于受保护本地捕获档案，对外提供移除凭证后的保真内容表示。

### 权限建议

核心服务是数据目录唯一系统写入者；AstrBot 和其他模型执行环境不挂载可写原始目录，不持有用户编辑凭证。用户通过单独的本机编辑入口修改原文。收集凭证仅能创建所配置来源的条目，不能修改已存在的原文；整理凭证仅可读资料和写二次内容。

这是一项部署约束：若用户给外部智能体与本人相同的完整磁盘和凭证权限，本应用接口不能承诺阻止绕过。验收必须包含受隔离的真实执行环境，而不是只测提示词。用户编辑入口建议使用不暴露给执行器的本机管理通道；具体系统用户/容器与管理通道在设计中固定。

### 开关建议

- 后台暂停：停止领取新任务与新的收藏桥接，安全完成已进入提交阶段的操作；管理 API 仍可用。程序进程退出另由服务管理器控制。
- 自动整理关闭：继续收集，条目标记待手动处理；不启动新的自动整理任务。
- 自动整理重新开启：默认仅处理此后新收藏；积压由用户或智能体显式选择“处理积压”。
- 手动整理不受自动开关影响；后台暂停时普通手动提交仅入队，明确 manual_run_once 才允许一次按需运行，不偷偷恢复持续调度。
- 完全离线时保存已经到达桥接的事件缓存；未被平台送达的时间窗口标记缺口，不声称完整补齐。
- 开关、状态键、提示词、超时、重试次数与上传限制均集中配置，不散落实现。

## 4. 已批准延期项与未定范围

### 已批准：日常 QQ 群规则筛选

对象为从普通信息源群持续读取消息，按规则、正则表达式及 LLM 辅助判断是否收藏。本轮先做用户主动转发的专用收藏群，减少两种入口同时实施的复杂度。推荐主动收藏闭环验收后，由用户开启新一轮对齐、计划和规格。详细真相源：`../deferred/QQ指定群持续收集与规则筛选.md`。

这不是永久放弃；不影响首期收藏群事件接收、后台运行与自动整理开关。

### 新增及其他平台范围

多平台接入由 AstrBot 承接，任务 02、07、08 只定义桥接封套、来源实例和工具契约，不新建平台登录或传输框架。QQ 是第一条真实验证路径，其他已支持的平台沿用同一个桥接插件，新增平台配置时做必要样例验证。GitHub/语雀文档拉取先查现有插件，不能把 Bot 事件适配等同于文档版本同步。GitHub 作为知识数据远端的需求记入 `../backlog.md`，目标与上传范围另行对齐，不与已批准的日常群筛选延期混淆。
