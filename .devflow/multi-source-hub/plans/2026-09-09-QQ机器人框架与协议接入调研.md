# QQ Bot 框架调研

## 查询失败原因纠正

- 现象：沙箱内 DNS 解析失败，本地代理连接失败，浏览器和 Grok 默认会话目录不可写。
- 原因边界：沙箱外通过用户指定的 HTTP 代理 127.0.0.1:7897 请求 GitHub 返回 HTTP 200；同环境下 GitHub CLI（gh）认证成功。因此此前“代理没启动”“令牌无效”的结论不成立，至少这些失败与沙箱限制有关。
- 浏览器补充：命令不在 PATH 不能证明 macOS 没装 Chrome；守护进程启动失败也不能据此确定浏览器缺失。无需改用户 DNS、重新登录 gh 或重新安装浏览器。
- 解决：仅对已授权公开资料查询使用受审查的沙箱外访问和命令级代理；不修改全局代理或认证设置。
- Grok：首次沙箱内会话创建失败，临时运行目录尝试后仍因联网失败退出；随后使用现有认证、受审查的沙箱外运行及用户代理成功返回报告。
- 信息边界：交给 Grok 的是公开研究问题，不包含聊天资料或项目源码；要求只做公开网页研究，不修改文件。Grok 输出并非全部自动采信。

## 官方 QQ 的重要新证据

已直接读取[群消息全量模式官方文档](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_message_create.html)：
- 开启“接收所有消息”后，群内每条消息（不限于 @机器人）推送 `GROUP_MESSAGE_CREATE`。
- 字段包括消息 `id`、`group_openid`、`timestamp`、作者、消息正文、附件。
- 附件结构描述图片、语音、视频、群文件等类型，包含下载 URL、文件名、大小等字段。
- `msg_elements` 描述聊天记录和引用的嵌套元素；这不证明任意转发在真实账号场景都无损。
- 页面标注更新于 2026-07-23。此前只按“官方 Bot 只能收 @”限制方案是不充分的。

仍未核验：用户账号能否开启该能力、申请审核范围、目标群权限、实际附件完整性和下载时效。文档能力不能直接等价于当前账号已经具备权限。

Grok 报告还引用[单聊事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/c2c_message_create.html)、[事件通知](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/interface-framework/event-emit.html)、[频道消息列表](https://bot.q.qq.com/wiki/develop/gosdk/api/message/get_messages.html)。
其结论为：公开文档未找到普通 QQ 群/单聊任意历史列表接口，频道历史不能套用到 QQ 群，断线恢复也不等于无限历史。此项是本轮检索边界，不宣称证明所有官方接口绝对不存在。

## 实时接收、历史回补与工具

- 官方 Bot 是独立机器人身份，不等于登录用户的个人 QQ 号，不能自动继承用户所有群与会话。
- 原始需求中的收集工具应根据适配器能力区分：事件推送（Event Push）、历史拉取（History Pull）、文件导入（File Import），不能所有源都承诺支持按日期拉历史。
- 对支持历史拉取的源，“收集某个信息源”可继续游标；对只支持事件的源，工具应报告已监听范围、已有积压或不支持历史拉取，不能伪造收集成功。
- Grok 在 [NapCat API 文档](https://napneko.github.io/develop/api) 找到群历史和好友历史接口方向；实际可回补范围、缓存与媒体可用性尚未实测，不承诺完整历史。
- 主代理另外通过 GitHub 目录接口确认 NapCat 当前源码包含 `packages/napcat-onebot/action/go-cqhttp/GetFriendMsgHistory.ts` 和 `GetGroupMsgHistory.ts`；这确认实现入口存在，不证明任意历史均可获取。
- 重复事件或重复回采由信息中心按来源实例、会话、消息 ID、源版本判重；时间只做范围辅助。智能体选择源和整理方式，程序落实幂等性（Idempotency）。

## 推荐及取舍

1. 官方 QQ Bot + NoneBot2 官方适配器是优先验证组合；若技术栈最终偏 TypeScript，则 Koishi 是同层替代，当前不锁定语言。
2. 验证重点为：能否进入目标群并开启目标事件，转发/引用是否保留足够上下文，图片文件是否可保存；不能未经测试直接把首期裁剪成只收 @消息。
3. 如必须收个人号既有会话或补历史，单独评估 NapCat 或当前 Lagrange V2。协议端与知识核心隔离，避免将账号协议兼容工作混进知识整理。
4. Bot 框架只处理平台事件和薄适配，去重、原文权限、Git 历史与知识整理留在信息中心。
5. GitHub 等文档源可以由 Bot 指令触发收集，但真正获取文档和版本应由 GitHub 适配器调用官方接口；“统一 Bot 入口”不要求所有源都通过聊天协议采集。

当前只做公开资料调研，没有批准功能延期或首期裁剪。真实账号接入测试、框架版本兼容、许可证细读和历史回补验证需要在候选收敛及计划落盘后安排。后续优先确认目标 QQ 场景与官方能力可得性；不得将暂未测试写成永久放弃。
