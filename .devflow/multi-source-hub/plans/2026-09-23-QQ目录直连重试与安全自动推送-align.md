# QQ 目录、直连重试与安全自动推送对齐

## 已确认目标

1. 将所有现有与新采集的 QQ 条目移到 `items/qq/YYYY-MM-DD/message|forward|session/标题-ID/`。每日 `content.md` 继续放在日期目录；逻辑条目身份（Logical Item ID）和去重规则不变。
2. QQ 标题取条目的首段可读文本；没有文本时依据附件或条目类型生成简短标题。目录名清理文件系统不安全字符、限制长度，末尾保留稳定 ID，防止重名。会话标记本身不作为标题。
3. 所有媒体下载默认直连（Direct Connection），不读取系统代理；可重试的下载失败最多尝试 5 次（含首次请求）。大小超限、非法地址等确定性失败不重复请求。保留明确失败原因，避免下载失败被误报为成功。
4. 对既有失败媒体提供可重复执行的补救入口，优先覆盖用户指出的 B 站专栏图片；补救时不得覆盖已成功下载的媒体或丢失原有正文。B 站可取得的播放流 MP4 做首版自动落盘。后续可另行添加显式代理配置，但本轮不启用。
5. 当 Vault 中的 Item 或每日文档更新后，自动将允许发布的资料同步到 `git@github.com:Miss-PinkElf/data-hub.git`。发布目录（Publish Directory）使用独立 Git 历史，仅包含 Markdown、每日索引及经过明确筛选的非敏感元数据；不推送现有 Vault Git 历史、原始封套（Envelope）、Cookie、快照、数据库、队列、日志或下载媒体。

## 已选择方案与取舍

- QQ 路径只改变存储投影（Storage Path Projection）。先预演迁移、检查目标冲突，再迁移现有条目并重建目录索引；新条目直接使用新路径。
- 下载沿用现有客户端的直连约束，统一失败分类与有上限的重试策略；历史失败媒体通过补救命令处理。无需引入模型判断（LLM Judgment）来决定是否重试，网络错误分类可以确定性处理。
- 自动推送使用独立的最小发布目录和文件允许清单（Allowlist）。发布动作从 Vault 更新触发，并在进程重启后检查未同步更新；推送失败保留待重试状态，不妨碍本地入库。不强制推送、不覆盖远端已有提交。
- 发布前检查远端仓库可访问且为私有仓库，并扫描拟上传内容中的鉴权信息。若无法确认安全边界，保留本地资料并报告具体阻塞。匿名 API 与 SSH 读取已验证私有性，首次真实推送仍待运行验收。

## 验收标准

1. 新旧 QQ 条目均落在 `日期/类型/标题-ID`，目录索引链接有效，重复采集仍只对应一个逻辑条目。
2. B 站、QQ 媒体下载不使用系统代理；模拟瞬时失败时最多请求 5 次，恢复后落盘；确定性失败不重复请求。
3. 用户指出的历史专栏图片经补救后成功落盘，或留下可核查的失败原因；补救命令重复执行不会重复写入或损坏已有数据。
4. 自动发布仓库只含允许文件；失败后可恢复推送；远端有新提交时不执行强推。私有性与实际推送需有真实验证证据。

## 本轮不做 / 后续阶段

- 显式代理配置（Proxy Configuration）：当前要求是全程直连；以后用户提出代理场景时再加入可选配置。
- B 站持久媒体队列（Media Job Queue）：本轮聚焦下载重试与历史补救；出现大视频阻塞轮询或要求重启续传时，进入单独的队列阶段。
- 链接筛选与格式化、知识整理（Knowledge Organization）：不在本次第 34–38 行范围；用户确认规则和输出格式后另行对齐。
- B 站多分段、画质选择与断点续传：本轮只保存接口当前返回的单段 MP4；用户要求完整画质或遇到分段视频时单独对齐。
