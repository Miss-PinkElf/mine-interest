# 多源信息中心首期整体对齐

## 审阅结果与后续澄清

本稿已获确认并进入计划。下文“建议/待审”保留起草脉络，以本段和当前任务决策记录为准。多平台由 AstrBot 原有适配器承接，信息中心只接收一个桥接插件输出的统一封套；不再询问先多平台还是先整理，不另建平台框架。具体实现以当前任务计划及待审规格为准，未授权代码实施或远端上传。

## 1. 已确认的产品方向

为个人建立独立的多源信息中心，保留原始资料，由人与大语言模型（LLM）共同维护二次知识。产品通过命令行接口（CLI）与服务工具供用户及外部智能体（Agent）使用，不绑定某个聊天窗口。

- 借用 AstrBot 的机器人接入及智能体执行能力，信息中心独立。
- 原始数据（Raw Data）只有用户可编辑，模型只能读取；二次内容（Derived Content）用户与模型均可编辑。
- 后台可以独立运行且有开关。自动整理默认开启、有独立开关，同时支持手动整理。
- 提供指定信息源的收集工具，重复收集不能重复入库。时间可辅助，但不能仅靠时间判重。
- 修改历史采用 Git 方向，具体粒度与媒体存储在计划和设计阶段决定。
- 首期 QQ 场景是主动收藏，投递位置为用户现有专用收藏群。群内两三个账号均为用户本人，群主也是用户账号。
- 用户确认转发进去就收藏，不需要逐条 @机器人或输入命令。
- 日常群消息流按规则、正则或模型判断进行筛选的能力明确延期，详见第 8 节。

## 2. 首期闭环建议（待整体审阅）

用户转发文本、图片、文件或合并聊天记录到收藏群后：

1. AstrBot 接收该群允许的收藏投递，由桥接插件（Bridge Plugin）交给信息中心。原始保存不依赖模型是否决定调用工具。
2. 信息中心保存来源事件及可取得的正文、媒体和元数据，检查重复，返回可查询的保存结果。
3. 自动整理开启时安排任务；关闭时仍保存资料，等待手动整理。
4. AstrBot 执行器读取结构约定（Schema）和工具列表，查已有页面，决定新建或更新主题、摘要及关联。
5. 二次内容保留原文回链，修改记录可回看。用户能查询整理状态、查看页面和打开原始资料。
6. 外部智能体通过同一套工具读取、搜索、整理和修改二次内容，不必经过 QQ 对话。

推荐把这一闭环作为首期验收，而不是同时接齐所有平台。非 QQ 来源首期范围尚未批准；它们继续保留在终态需求中，后续计划必须明确安排，不能静默删掉。

## 3. 组件分工与可替换性

| 组件 | 职责 | 边界 |
| --- | --- | --- |
| AstrBot 与 QQ 适配器（Adapter） | 群事件接入、消息结构解析、模型及工具循环 | 不作为原始资料和知识页面唯一存储 |
| 桥接插件（Bridge Plugin） | 从消息事件提取来源信息并调用核心，衔接任务执行结果 | 不在插件内另建一套去重和知识规则 |
| 独立知识核心（Knowledge Core） | 原始资料、媒体、来源、去重、页面、权限、版本、任务状态 | 不硬编码某个平台或模型供应商 |
| CLI / 服务接口（API） | 对人和外部智能体提供一致操作 | 操作结果包含明确状态和错误 |
| 工具协议适配（MCP Adapter，候选） | 让 AstrBot 和支持 MCP 的客户端使用核心工具 | 只包装核心能力，不复制业务逻辑 |

AstrBot 已有 MCP 客户端及工具循环，但不是现成的信息中心服务。后台任务衔接还需验证其消息上下文要求。推荐任务状态由信息中心维护，运行设施尽量复用，避免两套后台调度分别整理同一批条目。

## 4. QQ 接入证据与验证门禁

优先验证 AstrBot 官方 QQ 接入路线；这是技术候选，用户目前确认的是框架与体验，而非已授权创建账号或已验证平台权限。

- [AstrBot 官方接入文档](https://github.com/AstrBotDevs/AstrBot/blob/master/docs/zh/platform/qqofficial/websockets.md)说明可把机器人添加到自己为群主的群，设置接收群内全部消息；用户已满足群主归属条件。
- [QQ 群消息全量事件文档](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_message_create.html)明确非 @消息可推送。
- 文档和源码存在不等于当前账号可开通。需验证机器人创建/入群、全量消息权限及真实投递事件。
- AstrBot 文档声明基础文本、图片、语音、视频和文件接收能力；真实附件下载和本项目首期支持范围仍需验收。
- 已检查的解析方法保留原始对象和引用字段，但不能据此保证所有合并转发完整展开。尤其不可将仅取首个引用元素的解析当作完整历史聊天还原。
- 若原始事件本身缺失来源或媒体，应标明缺失；不得伪造来源、把缩略文本当完整聊天记录或静默改成私聊/@触发。
- 普通群/单聊任意历史拉取能力尚未证实。首期新增投递与旧收藏群历史导入不是同一件事，历史范围需另行明确。

## 5. 数据、去重与编辑建议

- 分别记录来源发送时间、系统接收时间和保存时间；AstrBot 的通用时间戳可能是处理时间，不能直接当作原始发送时间。
- 保存原始事件中可取得的群、消息、作者、转发节点和附件信息。机器人只能读既有原文，不能改写原文。
- 同一事件重试以来源实例、会话和来源消息 ID 等稳定标识判重；同内容多次主动转发产生不同消息 ID 时，结合可取得的原始身份、媒体指纹区分重复与不同出处。
- 原文内容相似不意味着来源相同。模型可以提出关联或重复建议，但不能仅凭语义相似删除原始资料。
- 原始资料来源身份与用户编辑后的正文分开，避免再次投递覆盖用户修改。
- Git 记录文本与元数据历史，二次内容写入前检查所依据的版本；存在并发修改时重新读取或提示冲突，不盲目覆盖。
- 媒体需要可靠本地保存，是否采用 Git LFS 或独立媒体存储在计划阶段比较，不默认所有视频都进入普通 Git。
- 原始数据的用户编辑入口与智能体工具权限应分开。仅靠提示词和 Git 不能阻止原文修改，具体执行隔离方案必须在设计中明确。

以上为实现约束建议，不代表已选定数据字段、数据库、事务或合并算法。

## 6. 开关与失败行为建议

| 情况 | 期望行为（待审） |
| --- | --- |
| 自动整理关闭 | 原文继续入库，停止自动安排新整理任务，手动整理仍可用 |
| 后台停用 | 不再持续收集或自动执行；保留数据和进度，明确显示暂停状态 |
| 后台恢复 | 按源实际能力继续，不能承诺无法回补的停机窗口完全无损 |
| 模型失败 | 原文保留，任务显示失败并可重试 |
| 附件暂时下载失败 | 区分正文已保存与附件未完成，不误报完整收藏成功 |
| 重复事件/并发投递 | 重复不产生第二份同源条目，进度仅在成功保存后推进 |
| 模型执行期间用户修改页面 | 检查版本冲突，保留人工修改 |
| 机器人回复或服务回执 | 不重新当作用户收藏，避免循环 |
| 不支持某类历史拉取 | 工具返回能力不支持或可替代入口，不能报成功 |

已运行任务在关闭开关时如何收束、恢复是否自动处理积压，需计划中明确；建议已开始的安全写入完成后停止领取新任务，避免留下半套页面。

## 7. 首期验收建议（待审）

1. 用户在专用收藏群直接转发，无 @ 和命令，内容被接收；来源群与用户范围可配置。
2. 文本、图片、文件、引用及合并记录分别提供真实样例；验证可取得的结构、原文和附件，缺失明确可见。
3. 同一事件重复投递、失败重试和服务重启不重复创建同源条目；主动再次转发的去重行为另列样例。
4. 自动整理关闭仍保存，手动整理成功；开启后新收藏可自动整理。
5. 一组同主题资料能更新已有主题并保留原文回链，不只生成互相孤立的摘要。
6. 用户能编辑原始数据；模型的原文写操作被拒绝。二次内容允许双方编辑，冲突可识别，历史可恢复。
7. 外部智能体能用核心工具读取与修改二次内容，并查看任务结果；知识数据不依赖 AstrBot 私有会话存储。
8. 交互式智能体关闭后，后台仍按开关运行；停用和恢复不丢已保存数据或误报同步完整。
9. 日常群规则筛选不进入首期；专用收藏群接收不受此延期影响。

验证分为核心逻辑测试、适配样例测试和真实 QQ 联调。仅 mock 通过不代表真实入群与消息权限已验证；真实联调前再处理必要的账号授权。不得要求用户在文档或聊天中粘贴密钥。

## 8. 本轮不做 / 后续阶段

已批准的延期项（Deferred Scope）只有：

**从日常 QQ 群消息流自动筛选收藏。**

- 对象：指定群持续收集，按规则（Rule）、正则表达式（Regular Expression）和 LLM 辅助判断哪些内容需要保留。
- 原因：用户明确先完成主动收藏，不同时承担日常消息流筛选。
- 触发：建议主动收藏闭环验收后，由用户开启下一阶段；提前调整时先更新对齐与计划。
- 后续：明确群范围、规则组合、模型参与及不确定行为，再写计划和规格。
- 不影响专用收藏群接收、已收藏内容的自动整理、后台开关和手动操作。
- 真相源：当前任务 `deferred/QQ指定群持续收集与规则筛选.md`。这是后续需求，不是永久放弃。

GitHub、语雀、其他聊天平台、手记、旧历史导入和展示界面仍在整体愿景中，其阶段安排尚未获用户确认；不能把本文只描述 QQ 闭环解释成自动批准这些能力延期。
