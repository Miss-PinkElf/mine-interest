# 对四项需求的具体判断

1. **视频链接**：归档应保留原始链接、规范页面链接及视频标识（BVID/AID）；下载时再交给下载器解析媒体地址。页面链接与媒体直链用途不同，拿到链接不等于下载验收通过。
2. **视频简介**：需要读取视频详情并保存原文；现有插件说明的视频上下文能力只能证明有相关入口，仍需检查简介是否截断、是否保存，以及多分集标识。
3. **父评论**：同时保存触发评论、直接父评论（Parent Comment）和根评论（Root Comment）。不能用根评论替代直接父评论。通知仅作定位线索，必须补查详情；删除、无权限或分页未找到时保留缺失状态，不能写成“没有父评论”。
4. **动态/专栏全文**：分别验收普通动态、转发动态、新图文（Opus）、旧专栏（CV）。推荐保存原始结构化数据、可读 Markdown、原始链接、作者/时间及本地图片；转发动态同时保留转发附言与原文。卡片摘要、模型总结和仅远程图片链接均不足以证明完整归档。

# 源码核验发现

阅读的 [core/reply.py](https://raw.githubusercontent.com/chenluQwQ/astrbot_plugin_bilibili_ai_bot/main/core/reply.py) 网页快照显示：

- @ 通知会提取通知编号、来源评论编号、对象编号、业务类型和根评论编号。
- 读取片段以首屏通知为输入，首次轮询跳过已有通知；归档场景需要另行验证分页及首次同步策略。
- 片段先标记已处理再执行后续逻辑，且受模型冷却影响；原文采集需要独立的成功状态与重试语义。
- 回复记录存在文本截断；该记录不能直接充当原文存储。

这些结论仅针对读到的快照，不声称当前整个插件没有其他补偿逻辑。尚未完成父评论详情及动态全文相关模块的源码核验。

# 三条路线与推荐

1. **复用 AstrBot 接入模块，加独立归档插件（推荐候选）**：复用登录和通知能力，采集成功后保存原文，语义处理另走工具。前提是确认现有插件能提供稳定事件/调用接口并关闭对外互动；不能满足时再决定局部复用代码或独立实现。复用前核对许可证与具体版本。
2. **直接安装完整 BiliBot 再扩展**：演示较快，但自动回复、主动浏览与记忆系统超过当前收藏需求；需要先核对开关和归档扩展点，不能把“安装即跑通”作为结论。
3. **独立采集服务，向信息中心桥接**：职责清晰，但需单独维护登录、通知轮询和运行状态。现有 AstrBot 能力无法复用时再选。

候选数据流：账号收到 @ 通知 → 原始通知落盘 → 定位评论和对象 → 补取直接父评论/根评论 → 获取视频详情或动态/专栏全文 → 保存原文与附件 → 按需调用模型整理工具。

大语言模型（LLM）适合判断“收藏这条评论还是整个作品”等语义和后续分类、总结；评论关系、来源标识、分页与完整性以平台数据核验，模型不得编造缺失内容。必要归档不应依赖模型成功。

# 推荐验证范围（待用户对齐，非实施计划）

- 默认只接收并保存，不自动公开回复；这是候选建议，尚未确认。
- 使用普通视频顶层 @、回复他人评论的 @、回复子评论的 @、动态评论 @、专栏评论 @ 五类样本。
- 核对真实账号能否收到通知、通知定位是否准确、父评论是否对应页面、简介及正文是否完整、图片离线是否可读。
- 验证重复通知不重复归档、重启继续、失败可重试、父评论删除时不误报完整。
- 若只是提供视频页链接，标记“可交给下载器”；至少实际下载一个可访问样本后才能声称下载链路通过。
- 登录态仅本地配置，不写入仓库或聊天。用户现有 B 站机器人账号及本地登录情况尚未知。
