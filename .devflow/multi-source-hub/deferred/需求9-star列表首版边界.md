# 需求 9 首版边界

## 已实现

- 两个插件各自新增 `github_star_list` 配置。
- 只对**本次新 star** 的仓库生效；已 star 的仓库保持「已经 star，跳过」。
- 按列表名称完全匹配，加入目标 GitHub Lists。
- 加入时保留仓库已有的其他列表。
- 留空、名称不匹配、列表查询失败时仍完成普通 star（默认位置）。
- 列表数或单列表条目超过 100 时放弃归属，避免误删手动归属。
- 不自动创建列表。

## 本轮暂不做 / 未讨论完（Deferred Scope）

1. **历史已 star 仓库的批量归类**
   - 暂不做对象：此前已经 star、但不在目标列表中的仓库。
   - 原因：用户确认只对本次新 star 生效，移动历史 star 会改变既有分组。
   - 后续触发条件：用户明确要求批量整理历史 star，并指定迁移范围与目标列表。

2. **自动创建不存在的列表**
   - 暂不做对象：配置的列表名称在 GitHub 上不存在时自动创建。
   - 原因：避免因拼写错误生成多余列表；当前回退默认位置并明确提示。
   - 后续触发条件：用户要求按名称自动建列表，并确认命名规则。

3. **超过 100 条目/100 个列表的完整分页**
   - 暂不做对象：完整遍历所有列表与列表条目后再计算归属。
   - 原因：GitHub 没有反向查询「仓库属于哪些列表」的接口，只能遍历；首版以安全为先，截断时放弃归属。
   - 后续触发条件：真实列表规模超过上限且用户需要归类。

4. **slug、别名或模糊名称匹配**
   - 暂不做对象：按 slug、大小写不敏感或模糊匹配找列表。
   - 原因：首版要求可预测，名称完全匹配最不容易误选。
   - 后续触发条件：用户明确要求更宽松的匹配规则。

5. **一个插件配置多目标列表 / 按来源或链接类型分流**
   - 暂不做对象：同一插件把不同来源的仓库放入不同列表，或一次配置多个列表。
   - 原因：本需求当前只确认「每个插件一个可配置列表」；多列表映射涉及新的规则来源（来源、链接类型、LLM 判断），尚未讨论。
   - 后续触发条件：用户提出按来源/类型分流，或要求同一插件配置多个列表。

6. **列表移除、列表改名同步**
   - 暂不做对象：从列表移除仓库、跟随 GitHub 列表改名。
   - 原因：超出「star 时归类」的首版范围。
   - 后续触发条件：用户另行提出。

## 待验证（不是延期）

- 真实仓库 star 后是否成功进入目标列表，且未移除其他已有列表。
- GitHub GraphQL mutation 在真实环境下的返回与权限要求。
