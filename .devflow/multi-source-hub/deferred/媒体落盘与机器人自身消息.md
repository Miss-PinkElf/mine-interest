# 延期项：媒体落盘与机器人自身消息

## D-MEDIA：媒体（图片/表情/语音）自动落盘

- **暂不做的对象或能力**：检查插件在收消息/展开转发时，把 `image`、`face`、`record`、`video` 等媒体段下载并保存到本地，并在 JSON 中写回 `local_path`；同时覆盖「顶层直接发的图片」与「转发内层图片」两类。含扩展名按内容魔数判断（`file` 字段的扩展名不可信）。
- **本轮暂不做的原因**：先把「内层树能取到」证明掉，媒体是独立缺口；且落盘策略涉及磁盘占用，需要用户先定体积与清理策略。用户在本轮被明确询问后尚未答复。
- **已完成的可行性验证（2026-09-20）**：手动下载一张转发展开内的图，HTTP 200、1,203,543 字节、内容完好（`GIF89a`），证明方案可行；直连腾讯 CDN 可用，走本机 Clash 代理（127.0.0.1:7897）反而全部失败。
- **已知时间压力**：`rkey` 有有效期。同一批 157 个 URL 中已有个别失效，越晚抢救可救回的越少。
- **后续进入的触发条件或推荐阶段**：用户答复体积策略（全量下载 / 限制单张大小 / 只存缩略图）与清理策略（是否保留最近 N 天）后，写独立 plan 并实施。**推荐紧接着下一轮就做**。
- **依赖**：若采用「按 id 去重」需先补事件去重能力（见 D-DEDUP）。

## D-DEDUP：事件身份与去重

- **暂不做的对象或能力**：修复 `event_id` 读取（当前 `event.message_id` 可能回退成时间）、实现重复消息标记与幂等。
- **本轮暂不做的原因**：诊断阶段每次只落一份快照，尚未产生重复入库的实际问题；且它属于正式收藏的核心能力，不应在诊断插件里草率定型。
- **后续进入的触发条件或推荐阶段**：媒体落盘若采用内容指纹去重、或开始接「正式收藏桥接」时，必须先补。见 `bug-log.md` 未解决表。

## D-SELFSG：机器人自身消息的获取

- **暂不做的对象或能力**：让「机器人自己发出的消息」也进入 AstrBot 并被记录。
- **本轮暂不做的原因**：插件侧已确认**没有**按发送人过滤，AstrBot 侧 `ignore_bot_self_message=False` 且 `1961618848` 在其全部日志中出现 0 次——**事件根本没到**。拦截点定位在 NapCat：`handleMsg` 中 `if (isSelf && !adapter.config.reportSelfMessage) continue`。配置里该值为 `true`，但运行实例疑似未应用。
- **后续进入的触发条件或推荐阶段**：用户重启 NapCat 后复测。
  - 若自身上报恢复正常 → 无需改代码，直接关闭本项。
  - 若仍不上报 → 二选一：① 更换/调整 NapCat 版本或配置（治本，依赖第三方）；② 插件侧在收到该群任意消息时调 `get_group_msg_history` 回填（治标，**必须先补去重**，见 D-DEDUP）。
- **用户明确诉求**：「在这个群里的消息都需要记录，不要按照发送人过滤」。本项未关闭前，该诉求未完全满足。

## D-CLEANUP：旧快照与旧媒体的自动清理

- **暂不做的对象或能力**：给 `data/sourcehub-inspector/` 下的快照与媒体加保留策略（如保留最近 N 天），或体积上限。
- **本轮暂不做的原因**：诊断阶段数据量尚可接受（单日 400+ 快照、单条转发 190 KB），清理策略与 D-MEDIA 的存储设计强相关，应一起定。
- **后续进入的触发条件或推荐阶段**：与 D-MEDIA 同批设计与实施。

## D-PARSE：NapCat `parseMultMsg` 是否启用

- **暂不做的对象或能力**：开启 NapCat 的 `parseMultMsg`（解析合并转发），让推送事件直接带上内层节点。
- **本轮暂不做的原因**：它是 NapCat 的全局开关，会影响其它已装插件的收包结构（消息体积可能显著变大）；而插件侧调用 `get_forward_msg` 已满足需求。
- **后续进入的触发条件或推荐阶段**：若发现 `get_forward_msg` 对某些转发拿不到内容、或自身上报问题与解析路径相关时，再评估对比。
