# Proposal（变更提案）

## 背景

现有 B 站资料把通知、作品、评论和媒体混在一个通用 Markdown 投影里；导出时又回读归档 Markdown，造成标题、图片、附件重复。B 站采集仅使用手填 `SESSDATA`，QQ 连接状态也没有独立提醒。用户希望使用专用私有 GitHub 仓库的推送邮件做主提醒。

## 目标

1. 视频、专栏、动态按已认可的 `content-new` 结构生成 `content.md`；封面和图片保存本地，评论按真实 ID 归属。
2. 根据原始 JSON 的显式格式标记恢复正文层级；无标记文本保持普通文本，不用大语言模型（LLM）猜标题。
3. 安全重渲染已有 B 站条目，提供预演、备份、断链检查和恢复证据。
4. B 站独立完成登录检查、扫码与刷新；QQ 仅根据明确状态判断登录失效或持续断线；首次故障和恢复经独立私有 GitHub 仓库各提醒一次。

## 范围

- B 站采集插件、QQ 检查器插件、共用资料库、相关配置和定向测试。
- 状态变化去重、待送重试、敏感信息最小化、告警仓库私有性校验。
- 既有视频、专栏、动态的本地资料迁移；不触碰 QQ 正文投影。

## 非目标与延期项

- 不保留对生成的 `content.md` 的人工修改；用户明确本轮不要求。未来需要人工层时另做对齐。
- 不对原文进行 LLM 排版推断；若以后需要智能整理，只在衍生文档中另设阶段。
- 不做整机停机外部心跳、远端媒体上传或其他通知渠道；分别在用户要求宿主监控、多端归档或冗余通知时开启后续阶段。
- B 站 DNS 故障属于需求 4 的网络诊断，不能视为 Cookie 失效。

## 边界场景

- 网络不可达、状态接口异常或缺少 QQ 句柄时状态为未知，不告警“需重登”。
- 媒体缺失或原始记录不完整时记录缺口，保留旧资料，不伪造本地链接。
- 评论文本相同但 ID 不同必须保留；同 ID 上级评论只出现一次。
- 私有性不能验证或推送失败时保留待送事件，绝不改用公开仓库。

## 开放问题

- QQ 的“需扫码”信号以本机 AstrBot/NapCat 可观测接口调查结果为准；若无明确信号，仅发布经确认的连接中断。
- 真实告警仓库地址、GitHub 推送邮件设置须在代码与离线测试完成后进行端到端接入；未收到邮件前不宣称邮件链路完成。
