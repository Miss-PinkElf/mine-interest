## 二、本轮完成：`0.2.4`

### 2.1 三个执行反馈缺陷

| 缺陷 | 根因 | 修复 |
| --- | --- | --- |
| `/goon` 取消后静默且误标 done | `sessions.py::goon` 的 `return ... or ""` 把 `None` 变成空串 | 去掉 `or ""`；`_execute` 返回 `None` 时显式返回 `AGENT_INTERRUPTED_REPLY` |
| 中断动作不告知 | `interrupt()` 的 `bool` 返回值被丢弃 | 中断了上一轮时回复加 `GOON_INTERRUPTED_PREFIX` 前缀 |
| 长任务期间零反馈 | `_execute` 攒齐所有 `TEXT` 事件后一次性返回 | 新增执行回执：会启动代理的输入先回一条 |

### 2.2 关键实现点

**回执判定唯一真相源**：`commands/registry.py::will_run_agent`

| 输入 | 会启动代理 | 发回执 |
| --- | --- | --- |
| 普通文本 | 是 | 是 |
| `/goon`、`/cc <消息>` | 是 | 是 |
| `/new <初始消息>`、`/! <参数>` | 是 | 是 |
| `/new`、`/!`（无参数） | 否 | 否 |
| `/help`、`/info`、`/pwd`、`/cd`、`/end`、`/resume`、`/initbase`、`/approve`、`/deny` | 否 | 否 |

**注入方式**：`service.handle(on_started=...)` 回调，由 `main.py` 传闭包。service 不持有 AstrBot context，保持分层。

**三个安全点**：
1. 回执在 `claim_message` **之后**触发 → 重复消息不会误回执。
2. `_replay_queued`（重启恢复）**不接**该回调 → 避免启动时批量刷屏。
3. 回执发送失败不阻断主流程（`send_text` 自带兜底）。

### 2.3 我主动修正的一处判断

上一轮口头方案说「只对纯文本发回执，命令都同步返回」是**错的**。`/goon`、`/cc`、带参数的 `/new` 和 `/!` 都会跑代理，恰恰最需要回执。已按「是否启动代理」判定，并在 plan 与 `decision-log.md` 中记录该修正。

## 五、排查耗时分析（本轮新增产出）

用户追问「为什么排查用了 14 分钟」，做了定量分析，文档见 `2026-10-28-排查耗时分析与优化方案.md`。

### 5.1 核心数据

第一轮 986 秒（扣除 93 秒用户决策等待后 893 秒）：

| 构成 | 耗时 | 占比 |
| --- | --- | --- |
| 模型生成 + 调度 | 680 s | **76%** |
| 工具执行 | 213 s | 24% |

| 指标 | 数值 |
| --- | --- |
| 模型往返 | 127 次，平均每步 7.8 s |
| 工具调用 | 160 次，**160 批，每批恰好 1 个（并行度 1.00）** |
| 单次 API 往返 | 中位 1.0 s，P90 3.2 s |
| 单条 Bash | 中位 1.93 s，最长 7.7 s |
| 用 Bash 干了专用工具的活 | 91 次（head/tail/sed 47、ls/find 24、grep 13、cat 7） |
| 第一轮 `Read` 工具使用 | 仅 4 次 |

### 5.2 结论

**不是卡死，不是环境慢，是执行方式的问题** —— 单点都很快，但串行跑了一百七十多趟。

### 5.3 与插件问题的映射（重要）

单轮耗时 = 往返次数 × 单步耗时。单步已接近下限（API 1 秒 + 工具 2 秒），**并行化只能压缩执行时间，压不动用户感知的等待**。

即使并行化做到极致，复杂任务仍需 8–9 分钟。**对 QQ 异步消息场景，8 分钟无中间输出依然不可接受。**

→ **流式输出不是锦上添花，是这类场景的必要能力。** 原触发条件「单轮经常超过 5 分钟」**已满足**（实测 15 分钟、16.4 分钟各一次）。

> 本轮**没有擅自把流式输出从 deferred 提级**，只更新了触发条件为「已满足」，最终优先级由用户决定。
