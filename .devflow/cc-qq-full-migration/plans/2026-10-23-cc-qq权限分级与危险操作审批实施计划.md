## 一、对齐结论（Align）

用户已确认：

1. 危险操作采用**逐次实时审批**：审批通过才放行，超时默认拒绝。
2. 基础模板采用**模板库 + `/initbase` 显式初始化**，默认不自动改动工作目录。
3. 本轮范围包含**权限主链路**与**管理员 `/cd` 切换工作目录**；私聊短时聚合与上下文截断（需求3.3）本轮不做。
4. owner／管理员保留**完全权限 + 关键路径保护**；普通成员为工作目录读写；群内非白名单为只读。

本次变更推翻第一版“普通会话一律 `bypassPermissions` / `danger-full-access`”的边界，必须同步更新 `proposal.md`、`design.md`、`tasks.md`、`README.md` 和 `deferred/阶段二至四功能.md`。

## 二、目标与不变量

### 目标

- 群内所有成员都能与代理对话；非白名单用户只能只读当前工作目录。
- 白名单成员可在当前工作目录读写，工作目录外写入与危险命令需要管理员逐次审批。
- owner／管理员拥有完全权限，但关键路径仍受保护。
- 权限按**每轮发言者**计算，不按会话持久化，避免同群成员与访客互相“继承”权限。
- 所有权限判定、审批与拒绝可审计。
- 提供基础 `CLAUDE.md`、`AGENTS.md`、`.claude/skills`、`.codex/skills`、hooks、settings 模板，由管理员显式初始化。

### 不变量

- 未启用群、未启用私聊、平台 ID 不匹配：仍然不处理。
- 私聊非白名单：仍然静默，不回复。
- 群聊未精确 @ 当前机器人：仍然静默。
- 审批回复（`/approve`、`/deny`）不进入会话串行队列，避免与正在等待审批的代理死锁。
- 审批超时、broker 不可用、hook 异常：一律按拒绝处理（fail-safe）。
- 仓库内 `.claude/settings*.json` 默认不参与插件会话（`--setting-sources ""`），避免工作区自带配置提权。

## 三、权限模型

### 角色与档位

| 角色（Role） | 判定条件 | 默认档位（Profile） |
| --- | --- | --- |
| `owner` | `owner_qq_id` 精确匹配 | `full` |
| `admin` | `admin_qq_ids` 包含 | `full` |
| `member` | 群规则 `allowed_user_ids` 或 `global_allowed_user_ids` 包含；私聊 `private_user_ids` 包含 | `workspace` |
| `guest` | 已启用群内的其他成员 | `readonly` |

档位可通过配置覆盖：

- `guest_permission_profile`，默认 `readonly`
- `member_permission_profile`，默认 `workspace`
- `owner_permission_profile`，默认 `full`（管理员沿用）
- 群规则可选覆盖：`guest_permission_profile`、`member_permission_profile`

### 档位对应的代理参数

| 档位 | Claude Code | Codex |
| --- | --- | --- |
| `readonly` | `--permission-mode dontAsk`、`--tools "Read,Grep,Glob,TodoWrite"`、注入只读 settings | 权限档案 `ccqq-readonly`：`extends=":read-only"`，工作区只读、其余拒绝、排除 `/tmp` |
| `workspace` | `--permission-mode acceptEdits`、注入开启 Seatbelt/bubblewrap 沙箱与 PreToolUse 审批 hook 的 settings | 权限档案 `ccqq-workspace`：`extends=":workspace"`，工作区读写、关闭网络、排除 `/tmp` |
| `full` | `--permission-mode dontAsk` + 全量守护 hook：默认放行，拦截凭据/系统目录与系统级危险命令 | `sandbox_mode="danger-full-access"`、`approval_policy="never"` |

Claude 所有档位默认追加 `--setting-sources ""`，可用配置 `claude_setting_sources` 放宽。

### 工作目录

- 群聊默认使用群规则 `work_dir`；私聊默认使用 `private_work_dir/<QQ号>`。
- 管理员可用 `/cd <路径>` 覆盖当前会话工作目录：
  - 仅 owner／管理员可用。
  - 必须位于 `allowed_work_dirs` 的某个根目录内（按 `realpath` 判断，防符号链接逃逸）。
  - 覆盖值持久化到 SQLite，按复合会话键隔离。
  - 当前有代理运行时拒绝切换，提示先 `/!`。
  - 切换后结束当前活跃会话；下一条消息在 `/new` 或自然语言时使用新目录。
- `/pwd` 显示当前生效工作目录、角色与权限档。

## 四、危险操作审批（Claude Code）

### 流程

```
Claude Code 进程
  → PreToolUse hook（插件自带 approval_hook.py）
  → 本机 127.0.0.1 TCP + 单行 JSON（带随机 token）
  → 插件 ApprovalBroker 生成审批号
  → 在来源会话发送审批卡片
  → owner/管理员回复 /approve <id> 或 /deny <id>
  → broker 返回 allow/deny
  → hook 输出 permissionDecision
```

### 触发审批的操作

`workspace` 档位下：

- `Edit` / `Write` / `NotebookEdit` 的目标路径不在当前工作目录内。
- `Bash` 设置了 `dangerouslyDisableSandbox`（申请脱离沙箱）。
- `Bash` 命令命中危险模式：`rm`、`rmdir`、`sudo`、`su`、`chmod`、`chown`、`dd`、`mkfs`、`mount`、`kill`、`pkill`、`shutdown`、`reboot`、`git push`、`git reset --hard`、包管理器全局安装、下载内容直接管道到 shell 等。

### 不触发审批

- 工作目录内的编辑（由 `acceptEdits` 自动放行）。
- 沙箱内的普通命令（由 `autoAllowBashIfSandboxed` 自动放行）。
- 只读工具调用。

### 审批安全规则

- 只有 owner／管理员可以批准或拒绝。
- 审批号一次性使用，超时（默认 300 秒）默认拒绝。
- 同一次工具调用重复请求使用同一审批号（按会话 + 工具 + 参数摘要去重）。
- 审批卡片在来源会话发送；群聊中需要管理员在场。管理员私聊通知本轮不做，列为后续项。
- hook 在 broker 不可达、token 不匹配、异常、超时时输出 `deny`，不放行。
- 审批记录写入 `permission_audit` 表；命令摘要截断，不记录完整环境变量或密钥。

### Codex 的边界

Codex `exec` 为非交互模式，`exec_permission_approvals` 在当前 0.162.1 仍标记为 under development。因此本轮：

- Codex 使用权限档案（Permission Profiles，Beta）：`ccqq-readonly` 与 `ccqq-workspace` 分别收紧读取和写入范围，排除 `/tmp`；已在本机 0.162.1 实测工作区外读写被拒绝。
- 工作目录外读写会被沙箱直接拒绝，不会弹出审批。
- Codex 的逐次审批列为后续项，等 CLI 提供稳定的非交互审批通道后再接。

## 五、沙箱与技术栈结论（回答需求3.2）

- **Claude Code 沙箱**：基于开源 `@anthropic-ai/sandbox-runtime`；macOS 使用 Seatbelt（`sandbox-exec`），Linux／WSL2 使用 bubblewrap（`bwrap`），网络通过本机代理和域名白名单控制。它只覆盖 Bash／PowerShell／Monitor 等 shell 子进程及其后代，不覆盖内置 `Read/Edit/Write/WebFetch`、hooks、MCP。内置文件工具由权限规则约束。
- **Codex 沙箱**：macOS 使用 Seatbelt，Linux 使用 Landlock + seccomp（新版本使用 bwrap），Windows 为实验性 AppContainer／MXC；`workspace-write` 默认关闭网络，`.git` 等敏感目录保持只读。
- **能否控制删除与命令**：可以。可靠顺序是：角色档位 → 工具面裁剪 → 权限规则 → OS 沙箱。字符串匹配（如 `Bash(rm *)`）只能挡常见写法，`python -c`、`find -delete` 等仍可绕过；真正的边界是沙箱把写入限制在工作目录，并对子进程继承限制。
- **本机实测**：Claude Code 2.1.202 的 `dontAsk + --tools` 只读组合可正常读文件；`acceptEdits + --settings` 开启沙箱后，工作目录内写入成功，`/tmp` 外写入被拒绝（`operation not permitted`）。Codex 0.162.1 的传统 `read-only` 不限制读取，改用权限档案后 `ccqq-readonly` 能阻止读取 `~/.codex/config.toml`，`ccqq-workspace` 能写工作区并阻止写 `/tmp`。

## 八、验收标准

- 群内 guest 能对话，但 Claude 只能读工作目录，Codex 为 `read-only`。
- member 能在工作目录内读写；工作目录外写入被沙箱拒绝；危险命令触发 QQ 审批，拒绝或超时不执行。
- owner／管理员可全机操作，关键路径 deny 规则仍生效。
- 非管理员无法使用 `/cd`、`/initbase`、`/approve`、`/deny`。
- `/cd` 只能进入 `allowed_work_dirs` 内的目录；切换后新会话使用新目录。
- `/initbase` 只补缺失文件，不覆盖用户已有文件。
- 审批记录可在数据库中查询；QQ 回复不泄露密钥。
- 现有 22 个单元测试不回退，新增测试全部通过。

## 十、风险

- 字符串危险命令识别存在绕过空间；工作区档以 OS 沙箱为主边界，完全权限档的守护 hook 只是应用层规则，无法拦截 `python -c` 等间接写入。需要强隔离时把 owner 档改为 `workspace` 或使用容器。
- `--setting-sources ""` 会屏蔽用户 settings 中的 `apiKeyHelper`；若现网依赖该方式认证，需要把 `claude_setting_sources` 设为 `user`。README 必须写明。
- PreToolUse hook 的 allow 行为依赖 Claude Code 版本；本机 2.1.202 已完成「hook → 本机审批 → 放行/拒绝」实测，真机 QQ 仍需验收。
- Codex 权限档案仍是 Beta，升级 CLI 后需回归验证 `ccqq-readonly`、`ccqq-workspace` 的读写边界。
- AstrBot 重载会丢失内存中的待审批请求；按 fail-safe 一律拒绝，用户重新发起即可。
