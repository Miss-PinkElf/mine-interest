## 背景与现状

- `enabled_group_ids` 已是群号白名单（Group Allowlist），仅列表内群号进入插件处理范围；本轮沿用该配置，不新增重复名单。
- `group_rules_json.allowed_user_ids` 是群成员白名单（Member Allowlist），限制群内哪些 QQ 用户可用插件，与群号白名单分别生效。
- 当前 QQ 事件适配器把 `Plain` 和 `At` 视为可支持消息段，但没有校验 @ 的目标是否为当前机器人，也没有把提及身份传给准入策略。
- 当前插件入口仍是占位回复，群聊白名单尚未真实 QQ 验收；本需求只定义后续行为，不改变“目前不能实际对话”的状态。

## 已确认方案

1. 群聊内所有会触发插件动作的输入都必须 @ 当前机器人，包括普通文本和显式斜杠命令。
2. 未 @ 当前机器人的群消息由插件完全静默处理：不调用代理、不执行命令，也不发送提示。
3. @ 目标必须与当前 QQ 机器人账号 ID 精确匹配。事件中无法可靠取得机器人账号 ID 或提及目标时，按未通过 @ 门禁处理，不猜测身份。
4. 送入代理的文本移除指向当前机器人的 @ 消息段，并保留其余文本内容；命令解析也基于移除提及后的文本。消息原始段仍可保留在归一事件中，便于平台层校验与诊断。
5. 私聊不要求 @，维持既有私聊开关和用户准入规则。
6. 群号白名单继续使用 `enabled_group_ids`；群成员白名单继续使用 `group_rules_json.allowed_user_ids`。两层配置不可相互替代。

## 候选实现路径与取舍

- **推荐：事件归一时保留结构化提及信息，准入前独立执行 @ 门禁。** `qq_events.py` 解析 @ 段中的 QQ 目标和文本段，平台适配器提供当前机器人身份；`service.py` 在命令／代理分派前检查门禁。这样命令与自然语言共享同一规则，策略层不必依赖 AstrBot 私有对象。
- 仅在入口 `main.py` 中检查 @：改动少，但会把平台事件细节和业务准入混在入口，且不利于针对服务行为验证。
- 将 @ 门禁伪装成普通成员白名单：无法表达消息级触发条件，也会错误地把群成员授权与消息提及混为一谈。

## 验收标准

- 群内 @ 正确机器人后，普通文本和命令都继续进入现有授权／服务链路；没有通过既有白名单的用户仍不得启动代理。
- 未 @、@ 其他 QQ 账号、机器人身份缺失或提及目标无法判定的群消息均静默，且不会产生代理进程或命令副作用。
- 代理输入不含机器人 @ 段；@ 后文本及命令参数保持正确。
- 私聊没有 @ 仍按既有配置与授权正常处理。
- 白名单范围仍可由 `enabled_group_ids` 独立控制，未列群不因 @ 机器人而被启用。
- 完成代码后需按仓库要求提升插件版本并覆盖 AstrBot 安装副本；真实 QQ 运行证据作为阶段验收，不以静态检查代替。

## 本轮不做 / 后续阶段（Deferred Scope）

- 不新增群号白名单管理界面或命令：当前已有配置字段；管理入口随总体计划阶段 2–3 的配置管理能力推进，触发条件是第一阶段消息闭环通过且进入对应阶段。
- 不在本轮设计 QQ 引用、图片、文件等非文本消息中的提及兼容：当前阶段只处理文本与 @ 消息段；待阶段 2 媒体消息能力进入计划时，基于实际 AstrBot 事件结构扩展并增加验收。
- 不把白名单解释成代理文件系统权限限制：代理权限仍依既有对齐决策执行，安全边界需继续在配置与 README 中说明。
