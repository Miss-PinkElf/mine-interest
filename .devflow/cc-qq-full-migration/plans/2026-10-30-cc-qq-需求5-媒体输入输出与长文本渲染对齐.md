## 三、现状事实（代码级，非推测）

### 3.1 会话键与权限

- `contracts.py:27-39`：会话键为 `(平台实例, 群聊/私聊, 会话号)`。
  - 群聊：会话号 = 群号 → **整群共用一个 agent 会话**。
  - 私聊：会话号 = 发送者 QQ 号 → 每人独立。
- `permissions.py:44-49`：权限档位按**每轮发言者**计算（guest→`readonly`、白名单→`workspace`、owner／管理员→`full`），不写入会话记录。
- 结论：**对话历史共享，权限不共享**。guest 以只读档进入同一个共享历史，能读到之前的对话内容；其发言也会写入共享历史。

### 3.2 当前媒体处理：一律拒绝

- `platform/qq_events.py:17`：`SUPPORTED_TEXT_SEGMENTS = frozenset(("Plain", "At"))`。
- `qq_events.py:103-105`：出现 Image／Reply／Forward／File／Record 等任何其它消息段，置 `has_unsupported_segments=True`。
- `main.py:230-231`：命中后直接回复 `UNSUPPORTED_SEGMENT_REPLY`（"当前阶段只支持文本消息……"），不进入代理。
- `platform/replies.py`：发送端只有 `send_text`，纯文本按 `MAX_QQ_TEXT_CHARS = 1500` 分段，无图片、无图文混排、无合并转发。

### 3.3 AstrBot 侧可复用的既有能力

- 引用消息：`astrbot.core.utils.quoted_message.extract_quoted_message_text(event)` / `extract_quoted_message_images(event)`，可提取被引用消息的文本与图片，并能展开嵌套的合并转发（内部调用 `get_forward_msg`，有最大跳数限制）。
- 转发展开：`OneBotClient(event).get_forward_msg(forward_id)`（`astrbot/core/utils/quoted_message/onebot_client.py:123`），依赖 `event.bot.api.call_action`。
- 图片落盘：`Image.convert_to_file_path()`（`components.py:501+`），网络 URL 会自动下载。
- 图文发送：`MessageChain([Plain(...), Image.fromFileSystem(path)])` 可混排。
- 消息组件：`Image`、`Reply`（含 `chain`）、`Forward`（仅 `id`）、`Node`／`Nodes`（合并转发）、`File` 均已存在。

### 3.4 本地长文本渲染：AstrBot 已内置，无需浏览器

- `astrbot/core/utils/t2i/renderer.py` 的 `HtmlRenderer.render_t2i(text, use_network=False)`。
- `astrbot/core/utils/t2i/local_strategy.py`：**用 Pillow 直接渲染 Markdown 子集**（标题、段落、列表、引用、代码块、表格、公式、图片），800px 宽，输出临时图片路径；不依赖浏览器、不依赖外网。
- 另有网络策略（`https://t2i.soulter.top/text2img`，支持 Shiki 代码高亮），失败会自动回退本地。
- 结论：需求 5.3 可以**直接复用本地 T2I 出长图**，不需要 Playwright／Chrome／wkhtmltoimage（本机三者均未安装）。

### 3.5 只读档的路径边界

- `permissions.py:373-397`：`PROFILE_READONLY` 下，`Read`／`Grep`／`Glob` 的路径必须位于 `work_dir` 内，越界直接拒绝；`Bash` 与写工具一律拒绝。
- 含义：图片若落在插件数据目录（`work_dir` 外），**guest 只读档读不到**，这是本轮必须解决的设计点。

### 3.6 CLI 图片输入能力

- Codex：`codex exec -i/--image <FILE>...` 原生支持（本机 0.162.1 实测 `--help`）。
- Claude Code：命令行无 image 参数；但 Read 工具可读本地图片，可在 prompt 中给出路径。
- 两者都需要图片先落盘为本地文件。

### 3.7 GitHub Pages 频率（供对比，本轮不采用）

- 官方软限制：**每小时 10 次构建**（使用自定义 GitHub Actions 工作流构建发布则不受此限）、每月 100GB 带宽、站点 ≤1GB、单次部署超 10 分钟超时、超限可能返回 429。
- 结论：人工对话场景够用，但不是"可以无限频繁"；相较之下本地 T2I 无外部依赖、无频率限制。

### 4.2 需求 5.2-A：媒体输入

**数据契约**

`IncomingMessage` 增加：
- `images: tuple[str, ...]`：本条消息直接携带的图片引用
- `quoted_text: str`、`quoted_images: tuple[str, ...]`：被引用消息的文本与图片
- `forward_text: str`、`forward_images: tuple[str, ...]`：合并转发展开后的文本与图片

**解析链路**

1. `parse_qq_event` 放行 `Image`、`Reply`、`Forward` 段；其余未知段仍标记不支持。
2. 直接图片：收集 `Image.url` / `Image.file` / `Image.path`。
3. 引用消息：调用 `extract_quoted_message_text/images`（复用 AstrBot 现成实现，不自己造轮子）。
4. 合并转发：对 `Forward` 段调用 `OneBotClient.get_forward_msg`，用 `OneBotPayloadParser.parse_get_forward_payload` 提取文本与图片；限制展开条数与字符数。

**落盘**

- 目录：`<插件数据目录>/media/<会话键哈希>/<YYYYMMDD>/<message_id>/`
- 用 `Image.convert_to_file_path()` 下载到上述目录。
- 限制：单条消息最多 `MAX_INCOMING_IMAGES`（建议 6）张；单张最大 `MAX_IMAGE_BYTES`（建议 10 MB）；仅接受图片扩展名／MIME。
- 清理：插件启动时删除超过 `MEDIA_RETENTION_DAYS`（建议 7 天）的文件。

**只读档如何读到图片（关键决策点）**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| M1（推荐） | 插件数据目录 + 只读 hook 放行一个额外的**只读媒体根** | 不污染工作目录；权限语义仍是"写禁止、读限域" | 需要扩展 `classify_tool_call` 与 hook 环境变量 |
| M2 | 图片落在工作目录内 `.cc-qq/media/` | 不改权限模型 | 污染用户仓库，需要 .gitignore，且只读档可读但白名单可写 |
| M3 | 只读档不支持图片理解，仅白名单／owner 支持 | 改动最小 | guest 体验不一致 |

推荐 **M1**：媒体根仅放行插件自己下载的图片，`realpath` 严格校验，写工具仍然全部拒绝。

**已确认（2026-10-30）：采用 M1。**

**传给代理**

- `AgentRequest` 增加 `images: tuple[str, ...]`。
- prompt 末尾追加结构化上下文，例如：
  ```
  [用户图片]
  1. /path/a.jpg
  2. /path/b.jpg
  [被引用消息]
  ...
  [转发消息]
  ...
  ```
- Claude：prompt 中提示"可用 Read 工具查看上述图片"。
- Codex：每个图片追加 `-i <path>` 参数。
- 纯图片无文本时，不再回复"当前阶段只支持文本"，而是把图片交给代理。

### 4.3 需求 5.2-B：发送图片／图文回复

**协议（推荐 P1）**

- 代理回复文本中出现 `[[image:<path>]]` 标记时，插件解析为该位置的图片。
- 路径必须位于**当前工作目录**或**插件媒体目录**内（`realpath` 校验），否则忽略并记录日志。
- 发送时按标记切分：文本段用 `Plain`，图片用 `Image.fromFileSystem`，同一条 `MessageChain` 内混排，超过 1500 字的文本段继续分段。
- 图片发送失败时保留文本、记录错误，不回滚已发送内容。

**候选 P2（本轮不做）**：扫描工作目录下 `.cc-qq/outbox/` 本轮新增图片自动附发。留到用户写 skill 时再定，避免现在造协议。

**已确认（2026-10-30）：采用 P1。**

**边界**：本轮不做图片来源、搜索、表情包、合理性判断；这些由用户后续用 skill 解决。

### 4.4 需求 5.3：长文本渲染长图

**方案（推荐）**：复用 AstrBot 本地 T2I（Markdown → Pillow 长图）。

- 触发条件（任一满足）：
  1. 回复正文长度 ≥ `LONG_TEXT_IMAGE_THRESHOLD`，**默认 360 字（用户已确认），可配置**。
  2. 回复包含围栏代码块（```），用于覆盖 diff 场景。
- 手动开关：`/img on|off`（owner／管理员），控制本会话是否自动转长图；默认开。
- 渲染：`HtmlRenderer().render_t2i(text, use_network=False)` → 本地图片路径。
- 发送：**只发长图（用户已确认）**；图片发送失败时自动回退现有文本分段，不阻断回复。
- 失败回退：渲染异常或超时 → 退回现有文本分段，不阻断回复。
- 配置开关：`long_text_image_enabled`（默认开）、阈值、是否优先网络渲染（默认关，本地优先）。
- 异步：Pillow 渲染放线程池，避免阻塞事件循环。
- 超长图：高度超过 `MAX_IMAGE_HEIGHT`（建议 4000px）时分页为多张，避免 QQ 压缩导致不可读。

**diff 来源**：本轮约定由代理在回复中输出 ```diff 代码块（或用户后续 skill 输出），插件只负责渲染，不主动执行 `git diff`。

## 六、风险与边界

1. **权限模型扩展**：M1 需要给只读档增加一个只读媒体根，属于权限模型改动；必须 `realpath` 校验、只放行插件媒体目录、写工具仍全拒绝，并补单测。
2. **外网图片下载**：需要大小、数量、超时、扩展名限制，防止大文件与异常输入。
3. **合并转发体积**：展开条数与总字符数都要设上限，避免一条转发撑爆上下文。
4. **T2I 渲染开销**：长图渲染是 CPU 密集操作，必须放线程池；失败必须回退文本。
5. **QQ 风控**：短时间大量发图可能触发风控，需要最小发送间隔（建议复用现有 10 秒去重窗口）。
6. **Codex `-i` 兼容性**：需要真机确认 `codex exec -i` 在现有权限档案下能读取媒体目录。
