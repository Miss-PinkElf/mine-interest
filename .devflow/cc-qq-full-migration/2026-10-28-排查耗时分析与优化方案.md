## 二、结论先行

**不是卡死，不是环境慢，是执行方式的问题。**

| 结论 | 实测依据 |
| --- | --- |
| 单条命令很快 | 最慢 Bash 7.7 秒，中位数 1.93 秒 |
| 单次模型往返很快 | 中位数 1.0 秒，P90 3.2 秒 |
| 但往返次数极多 | 127 次模型往返 + 160 次工具调用 |

一句话：**「每次都不慢，但跑了一百七十多趟」。**

### 3.2 时区约定（重要）

**会话文件里所有 `timestamp` 都是 UTC。** 本地（CST，UTC+8）时间需要 +8 小时。本文若无特别说明，表格中的时间均为**本地时间**。

同类陷阱已在 cc-qq 的 SQLite 回执表出现过（`created_at` 也是 UTC），排查时一度按本地时间误读，特此记录。

### 3.3 测量口径

| 指标 | 测量方法 |
| --- | --- |
| 工具执行耗时 | 配对 `tool_use` 的 `id` 与 `tool_result` 的 `tool_use_id`，取二者时间戳差 |
| 模型生成耗时 | 会话总时长减去工具执行耗时（含调度、网络、生成、日志落盘） |
| 工具调用次数 | 按 `tool_use.id` 去重（原始记录里同一事件会重复写入 3–4 次） |
| 并行度 | 统计每条 assistant 消息内包含的 `tool_use` 数量 |
| 文件触及次数 | 从 `Read` 的 `file_path` 与 `Bash` 命令文本中提取文件名去重计数 |

**去重是必须的**：原始 JSONL 里同一条 assistant 消息最多重复出现 4 次（推测与流式落盘有关）。不去重会把 160 次工具调用误算成 400 多次。

界面显示 `Baked for 14m 40s`（880 秒），本次实测第一轮为 **986 秒（16.4 分钟）**。差异 106 秒，推测来自计时器起止点定义不同（可能不含会话首次加载或最后一次渲染）。**本文采用实测的 986 秒，界面值仅作交叉参考。**

## 五、根因分析

### 5.1 根因一：完全没有并行（贡献最大）

统计每条 assistant 消息包含的工具调用数量：

```
1 个工具: 160 条消息
（没有 2 个及以上）
```

**并行度 = 1.00，160 批，批批只有 1 个。**

这意味着每一次工具调用都要经历完整的串行链条：

```
模型生成（约 3–4 s）→ 工具执行（约 2 s）→ 结果回填 → 模型再生成 → …
```

单个循环约 7.8 秒。127 步 × 7.8 秒 ≈ 986 秒，与实测完全吻合。

**为什么这是最严重的问题**：第一轮里有大量天然独立的查询。例如「检查 6198 端口是否监听」「查 NapCat 配置文件」「查 e2e 实例配置」三者毫无依赖，完全可以一次性并发发出，却拆成了三个串行往返。

### 5.2 根因二：专用工具闲置，Bash 一把梭

第一轮 77 次 Bash 调用中，本该用专用工具完成的：

| 用 Bash 做的事 | 次数 | 本应使用 |
| --- | --- | --- |
| `head` / `tail` / `sed -n` 切片看文件 | 47 | `Read` 的 `offset` / `limit` |
| `ls` / `find` 列目录查找 | 24 | `Glob` |
| `grep` 搜索 | 13 | `Grep` |
| `cat` 全文输出 | 7 | `Read` |

第一轮 `Read` 工具只用了 **4 次**，`Glob` 和 `Grep` 基本没用。

**这不只是「风格问题」**。Bash 调用是黑盒：我不知道文件有多少行、内容多长，只能先 `wc -l` 再切片，或者直接 `cat` 全量灌进上下文——两个方向都低效。而 `Read` 带行号、带边界提示，`Grep` 直接返回匹配行与文件名，一次到位。

### 5.3 根因三：同一文件反复触及

第一轮中同一文件被多条命令触及的次数：

| 文件 | 触及次数 |
| --- | --- |
| `cc_qq.sqlite3` | 10 |
| `constants.py` | 7 |
| 会话 JSONL `3fe53f78….jsonl` | 6 |
| `cmd_config.json` | 5 |
| `sessions.py` | 5 |
| `main.py` | 3 |

对 `sessions.py` 和 `constants.py`，我分别用 `cat`、`sed -n`、`grep`、`Read` 反复切入不同区段，每次都触发一次独立往返。**如果第一次就把需要的区段读全，可以省掉其中大部分。**

### 5.4 根因四：探索策略是「先扫后钻」

第一轮的开局顺序是：

1. 列 `.devflow` 目录、读 `state.md`、`checkpoints.md`、`handoffs` 索引
2. 查进程树、查端口、查 `cmd_config.json`、查 NapCat 配置、查 e2e 配置
3. 查 SQLite schema、查回执表、查 turns 表
4. 查会话 JSONL 事件、查 Claude 进程状态
5. 然后才开始针对具体问题深挖

前四步是**宽泛扫描**，其中相当一部分是「顺便看看」而非直接证据。例如我一开始完整展开了 `cmd_config.json` 的 80 行键值对，但真正用到的只有 `platform[]` 里的三个端口配置。

**正确顺序应是**：先用 1–2 条高信噪比命令定位方向，再针对性深挖。宽泛扫荡应交给子代理（Subagent），只回收结论。

### 5.5 不是根因的项（排除）

为避免误导，以下因素**经实测排除**：

| 疑似原因 | 实测 | 结论 |
| --- | --- | --- |
| 单条命令太慢 | Bash 中位 1.93 s，最长 7.7 s | 否 |
| 网络/API 慢 | 往返中位 1.0 s，P90 3.2 s | 否 |
| 缓存未命中导致重算 | `cache_read` 持续命中，从 36k 涨到 151k | 否 |
| 上下文过大拖慢生成 | 输入 token 稳定在 0.5k–3k（缓存读），输出中位 800 | 否 |
| 磁盘/CPU 瓶颈 | 单项工具耗时均正常 | 否 |

**注意上表最后一条**：单步 7.8 秒而 API 往返只有 1.0 秒，差额来自工具执行 + 调度 + 日志落盘。这个差额本身正常，问题在它被乘以 127 次。

## 七、优化方案（候选项，未实施）

### 7.1 强制并行

**规则**：同一批互不依赖的查询，必须在**一条消息内**并发发出。

```python
# 反例（本次实际做法）：三次独立往返
Read(a) → 等 → Read(b) → 等 → Read(c) → 等

# 正例：一次往返
Read(a), Read(b), Read(c)  # 同一条消息内发出
```

**判定标准**：如果我写第二段命令时还不知道第一段的结果，那它们就该并发。

**适用场景**：多个不同文件的读取、多个不同目录的列举、进程/端口/配置的并行探查、多条独立 grep。

### 7.2 工具选型纪律

| 需求 | 必须用 | 禁止用 |
| --- | --- | --- |
| 读文件某区段 | `Read`（`offset`/`limit`） | `sed -n`、`head`、`tail` |
| 找文件 | `Glob` | `ls`、`find` |
| 按内容搜 | `Grep` | `grep` |
| 看全文 | `Read` | `cat` |

**例外**：需要管道组合（如 `grep … | python3 …`）、需要调用外部程序（`sqlite3`、`lsof`、`ps`）时，仍用 Bash。

### 7.3 一次读全

**规则**：同一文件在同一轮任务里，第二次 `Read` 之前必须先回答「我上次读到了什么范围、缺什么」。

**实践**：
- 首次读取就按需给足 `limit`（如 200 行），不要读 40 行再回头补。
- 大文件先 `Grep` 定位行号，再 `Read` 精确区段，而不是整段 `cat`。

### 7.4 先定位再深挖

**规则**：宽泛扫荡（「这个配置在哪被写」「这个模块的调用链」）交给 Explore 子代理；主线只做定向验证。

**收益机制**：子代理的往返不占用主线程上下文，且其输出经过压缩，只回结论。

### 7.5 上下文卫生

大量低相关输出（完整配置文件、完整日志、整个 schema）注入上下文后，会推高每步的输入 token，虽不直接增加单步延迟（缓存命中），但会让后续生成更容易跑偏、需要更多纠偏往返。

**规则**：Bash 输出先 `| head -N` 或先精确 grep，再决定是否全量读。

### 7.6 预期收益（估算，非承诺）

基于以下假设的粗略估算：

- 160 次工具调用中约 70% 可以合并成并行批次（平均每批 3 个）
- 模型往返次数从 127 降到约 70
- 单步耗时不变

| 项目 | 现状 | 优化后（估） |
| --- | --- | --- |
| 工具批次 | 160 | ~70 |
| 模型往返 | 127 | ~70 |
| 工具墙钟 | 306 s | ~150 s |
| 模型生成 | 680 s | ~375 s |
| **合计** | **986 s（16.4 分）** | **~525 s（8.8 分）** |

**这是估算，未经实测验证。** 真实收益取决于任务本身的可并行度；纯阅读型排查收益大，强依赖型任务（后一步必须看前一步结果）收益小。

## 八、与 cc-qq 插件问题的映射

这次分析结论直接映射到 `0.2.4` 之前的 `/goon` 问题。

### 8.1 同一个根因

用户在 QQ 里发 `/goon` 后等了 10 分钟。查 `3fe53f78` 会话文件，那一次：15 分钟、67 次 Bash 调用、15 段超过 20 秒的停顿。

**这和我这次的 16 分钟是同一件事**：串行多步 + 中间无输出。

### 8.2 已被 `0.2.4` 部分缓解的部分

`0.2.4` 新增的执行回执（`EXECUTION_STARTED_REPLY`）解决了「完全静默」：

```
用户发送 → 1 秒内收到「已收到，正在处理」→ …（10 分钟）… → 最终结果
```

用户不再怀疑「没反应」，但**仍然要等 10 分钟**。

### 8.3 尚未解决的部分

**流式输出（Streaming）仍是 `deferred`。** 当前 `sessions.py::_execute` 把 agent 的所有 `TEXT` 事件攒进 `parts` 列表，进程退出后才一次性返回：

```python
parts: list[str] = []
async for event in stream:
    if event.kind is AgentEventKind.TEXT and event.content:
        parts.append(event.content)   # ← 攒着，不发
...
text = "\n".join(parts) or final_text
return text                        # ← 全部结束后才返回
```

**本次分析给出一条新的、可量化的决策依据**：

> 单轮耗时 = 模型往返次数 × 单步耗时。在 agent 串行工作模式下，单步耗时已接近下限（API 1 秒 + 工具 2 秒），**唯一能压缩的是「用户感知到的等待」而不是「实际执行时间」**。

也就是说：即使把并行化做到极致，一次复杂排查仍然要 8–9 分钟。**对于 QQ 这种异步消息场景，8 分钟无中间输出依然不可接受。** 流式输出不是「锦上添花」，是这类场景的必要能力。

### 8.4 建议

把流式输出从 `deferred` 提升为待排期事项。触发条件由原先的「单轮经常超过 5 分钟」改为**已满足**：`3fe53f78` 那次 15 分钟、本次 16 分钟，均超过阈值。

## 九、局限与未验证项

诚实标注这份分析的边界：

1. **样本单一**：只分析了 1 个会话（`b94f6bc6`，26.2 分钟）。样本量为 1，不能断言这是普遍规律。
2. **归因是定性排序**：「无并行贡献最大」来自「0/160 批次含多工具」这一硬数据，但各原因的**精确百分比**没有做对照实验，无法拆分。
3. **第七节收益是估算**：~8.8 分钟的推算基于「70% 可并行」的假设，未实测。
4. **模型生成耗时的构成不可见**：680 秒里分别是多少时间用于「思考」、多少用于「输出 token」、多少用于「调度开销」，会话文件里没有记录。只知输出 token 总量 356,475。
5. **`Baked for 14m 40s` 与实测 986 秒的差异未追查到底**，只推测定时口径不同。
6. **未验证「用专用工具是否真的更快」的因果**：`Read` 比 `cat` 快是推断（`Read` 有行号与边界、无需二次切片），但没有做 A/B 对照。
