# Codex 模型降级检测 · 调研报告

**日期**：2026-09-28
**环境**：codex-cli 0.157.1（npm 安装）· macOS · ChatGPT OAuth 登录
**起因**：怀疑官方 Codex 里的模型被静默降级（原本 `gpt-6-astra`，变成 `gpt-6-luna`）

---

## 一、结论摘要

| 问题 | 结论 |
|---|---|
| `gpt-6-luna` 是降级吗？ | **不是。** 是 safety buffering 机制，服务端明示 |
| 官方 Codex 有降级检测吗？ | **有，但在 OAuth 路径下拿不到数据，等于哑火** |
| 本地日志能看出来吗？ | **不能。** 只记录请求侧模型 |
| 第三方插件能用吗？ | 能，但**只能发现「换了型号」**，测不出同型号被削弱 |
| 自己能做检测吗？ | **能。** 反向代理方案已实测跑通 |
| 能可靠判断降级吗？ | **目前不能完全可靠。** 关键信号存疑，见第六节 |

## 二、调研过程与发现

### 阶段 1 · 官方能力排查

在 codex 二进制（238MB，`@openai/codex-darwin-arm64`）里搜到：

```
ModelReroutedNotification : thread_id / turn_id / from_model / reason
model/rerouted            : app-server JSON-RPC 通知方法
model/verification        : 模型验证通知
```

**官方确实内置了降级检测。** 官方仓库 commit `b3a8571` 的测试名直接就叫 `response_model_field_mismatch_emits_model_rerouted_notification`。

但那个 commit 把判定源从 `response.model` 字段**改成了依赖 `headers["OpenAI-Model"]` 响应头**。

实测本机：

| 检查项 | 结果 |
|---|---|
| 登录方式 | `Logged in using ChatGPT`（OAuth，非 API key） |
| 实际链路 | `wss://chatgpt.com/backend-api/codex/responses` |
| 全库 `openai-model` 记录 | **0 条** |
| 全库 `rerouted` / `response.created` / `model/verification` | **0 条**（235MB 日志，9 天） |

**ChatGPT OAuth 后端不返回 `openai-model` 头**，所以官方检测收不到信号。这是整个问题的根源。

### 阶段 2 · 本地日志分析

数据在两个地方，都**只有请求侧**：

- `~/.codex/logs_2.sqlite` —— 每轮带 `model` + `reasoning_effort`
- `~/.codex/sessions/年/月/日/rollout-*.jsonl` —— `turn_context` 事件

按 thread + model + effort 分组统计本机 9 天数据：

```
thread           model           effort   count
01a0c1cc-2e90    gpt-6-astra     medium   312    ← 主对话
01a0c1ba-18b9    gpt-6-astra     medium    29    ← 主对话
01a0c1bb-2ad7    gpt-5.6-luna    low       26    ← 子会话（spawn 派生）
01a0c1cc-94f2    gpt-5.6-luna    low       24    ← 子会话
```

当时判断 `luna` 出现在 `thread_spawn` 子会话中，属正常设计——**方向对了，但直到阶段 5 才找到确切机制**。

### 阶段 3 · 第三方插件评估

对社区方案做了实测评估（读源码、读文档，非转述）：

| 工具 | 原理 | 实测评估 |
|---|---|---|
| `kiyoakii/is-gpt-nerfed` | 请求记录 + 随机数指纹（ModelTrace 校准库） | 安装脚本规范（含 sha256 校验）。**指纹识别的是「哪个模型」，测不出同型号被削弱** |
| `Awfp1314/codex-degrade-guard` | 写/删前闸门，`tibo`/`cutoff`/`juice` 三信号 | 文档极诚实，作者原话：**「都是经验信号，不是可靠的模型鉴定手段」**，并自陈误报率与三个工程缺陷 |
| `@mzwing/pi-codex-downgrade-detector` | 比对 `openai-model` / `x-openai-model` 头 | 源码确认（`SERVED_MODEL_HEADERS`）。但**是给 Pi 用的，不是 Codex**；且在 OAuth 路径下会永远显示 `unverified` |

**共同天花板**：只能发现「模型被换成了另一个型号」，**测不出同型号被削弱**（量化 / 限速 / 降 effort）——因为客户端拿不到服务端的执行参数。

### 阶段 4 · 网关场景延伸

若经 LiteLLM / sub2api 等网关接入，格局变化：

- **多一层可观测性**：LiteLLM 返回 `x-litellm-model-id`（实际 deployment）/ `x-litellm-model-group`（请求名）
- **多一层降级源**：网关自身的 fallback / 号池轮换
- **致命陷阱**：LiteLLM 在**流式响应下会把 body 里的 `model` 覆盖成请求值**（litellm#31722），而 Codex 默认就是流式

### 阶段 5 · 反向代理方案实测

**方案**：把 Codex 的 `base_url` 指向本地代理，代理转发到 chatgpt.com 并采集信号。

选它而非 mitmproxy 的理由：**不需要往系统信任链装自签根证书**。

实测跑通，Codex 确实把请求打到本地：

```
/backend-api/codex/models?client_version=0.157.1
/backend-api/codex/responses
```

OAuth 正确转发（`authorization` + `chatgpt-account-id`），HTTP 200 完整响应。

**踩坑**：Codex 读 `~/.codex/.env` 里的 `HTTPS_PROXY`，自身能连通；新起的 Python 进程若不继承该环境变量则直连超时（`Errno 60`）。现象极迷惑——**Codex 正常，代理全超时**。

### 阶段 6 · 信号分析（关键收获）

实测捕获的三类信号：

**A 类 · 可信**

```
x-codex-safety-buffering-enabled: true
x-codex-safety-buffering-faster-model: gpt-6-luna
x-models-etag: W/"9fd094b7de2cd73b7e2d40fe16c629ad"
```

**B 类 · 账户配额（可信，事前预警）**

```
x-codex-plan-type: plus
x-codex-active-limit: premium
x-codex-primary-used-percent: 80 → 81 → 90    (5 小时窗口)
x-codex-secondary-used-percent: 28 → 29        (7 天窗口)
x-codex-credits-balance: 0
```

**C 类 · 存疑**

```
response.created.model   = 请求的模型
response.completed.model = 请求的模型
```

## 三、关键结论：`gpt-6-luna` 的真相

**`gpt-6-luna` 就是 `x-codex-safety-buffering-faster-model` 的值。**

这是 OpenAI 的 **safety buffering** 机制：对部分内容，服务端先用一个「更快的模型」做安全缓冲，再用所选模型出结果。

与「降级」的本质区别：

| | 降级 | safety buffering |
|---|---|---|
| 服务端是否告知 | 否，静默 | **是**，`enabled: true` + 指定模型名下发明示 |
| 是否影响最终质量 | 是 | 否，只是中间处理 |

本机日志里那 93 次 `gpt-5.6-luna` + `low` effort，也是该机制的产物。

## 四、C 类信号为什么存疑

`response.created.model` 两次实测都跟随请求值（`astra`→`astra`，`sol`→`sol`）。这既可能是「如实报告」，也可能是「回显请求值」。

为区分，做了决定性的**请求改写测试**——让代理把请求体里的 `model` 悄悄改成 `gpt-6-fake-probe`：

```
HTTP 400
{"detail":"The 'gpt-6-fake-probe' model is not supported
 when using Codex with a ChatGPT account."}
```

**说明服务端会校验模型名，不是无脑回显。** 但这**不等于**降级时会如实报告——那需要一个真实降级样本才能校准，而无法主动触发。

**一条重要旁证**：官方 commit 的标题是 `remove response model check and rely on header model for downgrade detection`。**如果 body 里的 model 可信，官方没有移除它的理由。**

因此 `check.py` 默认不对 C 类报警，仅记录留档。

## 五、最终方案

```
Codex ──► 本地探测代理 (127.0.0.1:8787) ──► chatgpt.com
                    │
                    ├─ 逐块转发（实测真流式：首字节 0ms / 总时长 3255ms / 52 分块）
                    └─ 采集 A/B/C 三类信号 ──► ~/.codex-probe/turns.jsonl
                                                      ▲
                    Codex hooks (Stop) ──► check.py ──┘ ──► macOS 通知
```

**hooks 只能做触发器**，不能采集：其输入 JSON 只有 `session_id` / `transcript_path` / `cwd` / 请求侧 `model`，没有响应头。且 `Stop` 触发时该轮 HTTP 响应早已结束，靠 hooks 临时抓包在时序上不成立。

**判定优先级**（按可信度）：

1. **额度百分比** —— 可信，且是**事前**信号，最实用
2. **safety-buffering 模型变化** —— 可信
3. **模型不一致** —— 存疑，仅记录

## 六、未验证 / 存疑的部分

1. **C 类信号未校准** —— 无法区分如实报告与回显，需要真实降级样本
2. **无法主动触发降级**以验证检测有效性
3. **同型号被削弱测不出** —— 目前无任何可靠的客户端手段
4. **sub2api 是否回传响应头未验证**（GitHub 抓取失败）
5. 官方 `model/rerouted` 通知在 OAuth 下**从未触发过**（0 条记录），无法确认其实际行为
