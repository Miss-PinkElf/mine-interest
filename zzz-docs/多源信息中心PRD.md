# 多源信息中心产品需求文档（Source Hub PRD）

## 1. Executive Summary（执行摘要）

### 1.1 Problem Statement（问题陈述）

有意思的聊天记录、图片、仓库文档和随手想法，散落在 QQ、微信、GitHub、小红书等地；现有笔记软件接不住这些活水源，传统检索增强生成（RAG, Retrieval-Augmented Generation）每次提问都重新考古。结果是：来时路会断，关系留不住，知识不会复利。

### 1.2 Proposed Solution（解决方案）

做一份个人多源信息中心（Source Hub）：先把四类信息源收成不可变的原始资料（Raw Sources），再由大语言模型（LLM, Large Language Model）按结构约定（Schema）持续编译成会复利的个人维基（LLM Wiki）。人在回路（Human-in-the-loop）决定去留；命令行接口（CLI, Command Line Interface）和应用程序接口（API, Application Programming Interface）让 Agent 管理；Obsidian 或自研界面只是可替换的展示层（Presentation Layer）。

一句话：

> 先收住「我觉得有用」，再编译成一份会长大的个人世界。

### 1.3 Success Criteria（成功标准）

以下指标针对完整终态，在个人中等规模下验收：约 100 份原始资料、数百个 Wiki 页面。

1. **四类源可接入，插件可扩展。** 聊天平台（Chat）、文档仓库（Docs）、公开内容（Public）、自己手记（Self）每类至少 1 个可用适配器（Adapter）。第三方信息源能按插件契约接入，且不必改核心代码。验证：适配器契约测试 + 插件样例跑通。
2. **原文不可变，元数据完整。** 摄入（Ingest）、查询（Query）、巡检（Lint）、重编都不得改写 `raw/`。状态为「已接受（accepted）」或「已编译（compiled）」的条目，最小元数据（Minimal Metadata）字段完整率 100%。验证：`raw/` 目录哈希对比 + Schema 校验。
3. **活水源必须经过人。** 来自聊天和公开内容的条目默认进入收件箱（Inbox），不得自动变成 `compiled`。用户一次操作即可接受、拒绝或改标签 / 改主题。验证：集成测试。
4. **编译会沉淀，而不是只生成摘要。** 对 20 条金标资料做 ingest：每条都有源摘要页、`index.md` 条目、`log.md` 条目；至少 80% 的金标主题被链到正确的主题页或实体页；Wiki 中来自资料的事实句，回链到原始条目 ID 的覆盖率 >= 95%。
5. **提问会复利。** 10 道需要综合多份资料的问题里，至少 8 道优先引用已有综合页 / 实体页 / 主题页，而不是只从原文临时拼接。好答案回写后，同一问题再次提问必须能命中该页。
6. **巡检找得到病。** 在预埋的 5 类问题（矛盾、过时结论、孤儿页、缺失交叉引用、提到但没有专页的概念）上，检出率 >= 80%，且每条结果都指出涉及页面。

未指定预算、工期、具体模型。这些保持 `TBD`，不作为本 PRD 的约束。

### 1.4 Product Principles（产品原则）

1. **收集和编译是两层，不要混成一件事。**
2. **原文和整理层必须分开。** 原始资料只进不出；Wiki / 摘要 / 标签 / 关系可以重编。
3. **先 Schema 和索引，不要先赌向量 RAG。** 中等规模用 `index.md`、关键词、概述、标签做主航道。
4. **人要待在回路里。** 尤其是「有意思的聊天 / 图片」。
5. **Obsidian / 语雀 / 自研界面只是皮肤。** 真正值钱的是稳定的原始资料层、一份人和 LLM 共同维护的 Schema、会回写的编译层。
6. **难度顺序：先能存，再能编，再能连，最后才是酷炫检索。**

## 2. User Experience & Functionality（用户体验与功能）

### 2.1 User Personas（用户画像）

本产品默认单用户、个人向。

| 角色 | 英文 | 是谁 | 要什么 |
|---|---|---|---|
| 主理人 | Owner | 仓库主人。不喜欢断舍离，会随手记冷门知识和临时想法，同时用多个聊天 / 社交 / 文档平台。 | 来时路不断；有意思的东西先收住；整理不能靠自己天天改 15 个文件。 |
| 维护 Agent | Maintainer Agent | 通过 CLI / API 工作的 LLM Agent。 | 按 Schema 摄入、查询、巡检、回写；不能改原文；需要稳定工具而不是每次重新扮演图书管理员。 |
| 浏览者 | Reader | 同一人，只是换了一种姿势：在 Obsidian 或以后的界面里逛。 | 顺着链接看主题怎么长大，能从 Wiki 页一跳回到原文。 |

没有多租户、没有团队权限矩阵。企业知识库那套最佳实践不套到这个产品上。

### 2.2 User Flow（主路径）

```text
遇到有意思的东西
        │
        ▼
   适配器 / 剪藏 / 手记
        │
        ▼
  原始资料落盘（不可变）+ 最小元数据
        │
        ▼
  聊天 / 公开内容 ──► Inbox
  文档 / 手记可按策略直达或仍进 Inbox
        │
        ▼
  LLM 给出：去留建议、候选标签、可能所属主题
        │
        ▼
  人接受 / 拒绝 / 修改
        │
        ▼
  Ingest：写源摘要、更新实体 / 概念 / 主题 / 综合页、改 index、写 log
        │
        ▼
  Query：先读 index 和已有 Wiki 页
        │
        ▼
  好答案回写成新页
        │
        ▼
  定期 Lint：矛盾、过时、孤儿、缺链
        │
        ▼
  整理错了：回到原文，按 Schema 重编
```

辅助路径：

- 主理人在 Obsidian 里闲逛，从图谱或反向链接进入某一主题。
- Agent 用 CLI 批量 ingest、跑 lint、把查询结果归档。
- 某个源被暂停后，已有原文保留，只是不再进新货。

### 2.3 User Stories（用户故事）与 Acceptance Criteria（验收标准）

#### US-01 手动记下想法

作为主理人，我想随手记下冷门知识、临时想法、以后可能有用的项目，以便它们先成为带元数据的原文，而不是只活在聊天框里。

- 可用 CLI 或 API 创建一条 `source_type = self` 的原始条目。
- 条目立即落在 `raw/`，带最小元数据；创建动作写入 `log.md`。
- 正文、图片、附件都有稳定相对路径，之后能被打开。
- 不强制立刻编译；可以只收住，标记为「以后可能有用」。

#### US-02 从聊天里留下一条有意思的消息或图片

作为主理人，我想把 QQ / 微信 / Telegram / Discord 里觉得有意思的消息或图片收进来，以便来时路不断。

- 终态至少支持上述四个聊天平台中的 Bot 或「用户主动推送」适配器；微信 / QQ 若无稳定官方接口，必须提供降级路径（转发到文件助手 / 导出 / 手动收藏），不得把非官方协议写成唯一方案。
- 收藏后生成原始条目，保留来源、时间、原始定位符（Source Locator，如消息 ID、会话名）、媒体文件。
- 默认进入 Inbox，状态不是 `compiled`。
- 同一条消息重复收藏时不产生第二份原文，只更新或复用同一 `id`。

#### US-03 同步指定文档仓库

作为主理人，我想把特定 GitHub 仓库、语雀文档或 Obsidian 目录里的有用文档拉进来，以便文档更新能进入同一套编译。

- 可注册一个文档源：仓库 URL / 语雀知识库 / 本地目录，以及包含 / 排除规则。
- 能做首次全量拉取和之后的增量更新；更新本身只新增或追加原始版本，不改写旧版原文。
- 每个文档版本是一条原始条目，能打开原文。
- 新版本进入后，可触发对该主题的重新 ingest，而不是覆盖旧原文。

#### US-04 从公开平台主动投递

作为主理人，我想在 B 站 / 小红书 / X / 微博里看到有意思的帖子、视频或评论时主动投递进来，以便公开内容也进入个人世界。

- 支持「在内容里 @bot」或剪藏 / 分享到收件箱，至少覆盖上述平台中的一种完整投递路径，其余平台按适配器补齐。
- 禁止以全站爬取作为正式能力。
- 投递条目带原始 URL、截取时间和媒体类型，默认进 Inbox。
- 原始页面失效后，本地原文和媒体仍可打开。

#### US-05 接入自定义信息源

作为主理人，我想用插件方式接入自己的信息源，以便核心不必为每个新源改一遍。

- 插件清单（Manifest）声明：插件 ID、名称、来源类型、能力（拉取 / Webhook / 手动投递）。
- 插件只能通过中心提供的捕获接口写入原始条目，不能直接改 Wiki，也不能改其他插件的原文。
- 官方文档给出一份最小插件样例；样例在不改核心代码的情况下可被发现、启用、停用。
- 停用插件不删除已收原文。

#### US-06 在 Inbox 里看到 LLM 建议

作为主理人，我想在确认前先看到「值不值得留下、可能是什么标签、可能属于哪个主题」，以便不去点每一条原始垃圾，也不把判断权交给全自动。

- Inbox 列表展示：来源、时间、原文预览、媒体缩略图、建议去留、候选标签、候选主题。
- 建议由 LLM 生成，但必须可被忽略；缺少建议时人仍能直接接受或拒绝。
- 建议生成失败不得阻塞收藏；条目保持 `captured` 或 `suggested`。
- 同一条目的建议可重跑，旧建议被新建议替换，原文不变。

#### US-07 一次操作完成去留

作为主理人，我想接受、拒绝或改一下标签 / 主题，以便「有意思」最终由我决定。

- 支持：接受、拒绝、接受但只浅收（打「以后可能有用」，不深编）、修改标签、修改主题后接受。
- 拒绝后的条目不进入编译，原文仍保留，状态为 `rejected`，可被日后搜回或恢复。
- 接受后状态变为 `accepted`，可立即或排队 ingest。
- 一次操作的结果可在 `log.md` 里查到。

#### US-08 容纳「以后可能有用」

作为主理人，我不想断舍离，但也不想知识库变成垃圾桶，所以需要一种「先收住、不深编」的状态。

- 存在明确状态或标签：例如 `keep_for_later`。
- 这类条目出现在原文库和 Inbox / 归档里，不强制生成综合页。
- Lint 可以提醒「长期浅收但从未被引用」，但不得自动删除。
- 日后仍可对它做正式 ingest。

#### US-09 摄入一条已接受的资料

作为主理人 / 维护 Agent，我想对一条已接受资料执行 ingest，以便它开始进入 Wiki，而不是只躺在原文库。

- ingest 至少产生：源摘要页、`index.md` 更新、`log.md` 追加。
- 若 Schema 判断它碰到已有实体 / 概念 / 主题 / 综合页，必须更新旧页，而不是只新建一篇孤立摘要。
- ingest 输出可检查的变更清单：新建了哪些页、更新了哪些页。
- 失败可重试；重试不得修改 `raw/`，也不得留下半套损坏页面而不记 log。

#### US-10 一份资料能更新多页

作为主理人，我希望一次像样的 ingest 能把关系编进去，以便知识不是一堆孤立文件。

- Schema 定义何时新建、何时更新。
- 金标集里，需要跨页更新的样本，至少 80% 实际更新了预期旧页。
- 更新旧页时保留可追溯的依据：引用了哪条 `raw id`。
- 不允许用「另写一篇新摘要」代替更新旧综合页。

#### US-11 从 Wiki 回到原文

作为主理人，我想从任何由资料得出的表述跳回原文，以便 LLM 写错时还能回到那张图和那句原话。

- Wiki 页中来自资料的事实句或段落，能指向 `raw id` 和原文定位。
- CLI / API / 展示层都能打开原文和本地媒体。
- 原文缺失或被用户归档时，Wiki 页显示「原文不可用」，不得假装引用仍有效。

#### US-12 新资料与旧结论冲突时要记下来

作为主理人，我想在新资料推翻旧判断时看到矛盾，而不是让旧结论悄悄留在某一页。

- ingest 若发现与已有综合页 / 实体页冲突，必须在相关页标记矛盾，并写入 log。
- 矛盾标记包含：旧表述、新表述、各自 `raw id`，以及「尚未裁决 / 已采纳新结论」。
- 不得在不留痕迹的情况下直接覆盖旧结论。

#### US-13 整理错了可以重编

作为主理人，我想在第一次标错主题之后重编，而不失去原文。

- 提供按条目、按主题或按全库重编的能力。
- 重编只改 Wiki，不改 `raw/`。
- 重编前后 `log.md` 都有记录；旧 Wiki 页可通过 git 或版本机制回看。`TBD`：版本机制默认用 git。
- 重编后，index 与实际页面一致，不得留下指向已删页的死链而不被 lint 发现。

#### US-14 对着 Wiki 提问

作为主理人，我想先问已经编好的 Wiki，而不是每次从原文重新发现知识。

- Query 先读 `index.md` 和标题 / 标签，再下钻相关页面。
- 中等规模默认不依赖向量库；向量检索若存在，只能当增强，不能当唯一通路。
- 答案必须引用 Wiki 页；若 Wiki 不足，可声明不足并请求是否回读原文，不得把临场拼接伪装成已编译结论。
- 查询本身写入 `log.md`。

#### US-15 好答案回写进 Wiki

作为主理人，我想把一次问清楚的综合判断留在 Wiki 里，以便提问本身也成为知识生产。

- Query 结果可一键或一条命令归档为新页（综合 / 对比 / 问答沉淀）。
- 回写页带：问题、结论、引用页、引用 raw id、时间。
- 回写后 `index.md` 更新。
- 再次问同一问题时，系统应能命中该页。

#### US-16 在 Obsidian 里逛编译结果

作为主理人，我想用 Obsidian 看链接和图谱，以便检验 Wiki 是不是真的连起来了。

- Wiki 是普通 Markdown 目录，Obsidian 打开即可浏览。
- 页面之间使用 Obsidian 兼容的 `[[wikilink]]` 或相对链接。
- 不把「做 Obsidian 插件」当作终态必选项；Obsidian 是皮肤和验收界面。
- 没有编译层时，目录里不假装已经有一份个人世界。

#### US-17 定期巡检 Wiki

作为主理人 / 维护 Agent，我想定期体检 Wiki，以便矛盾、过时结论、孤儿页和缺链不会无限堆积。

- `lint` 至少检查：页间矛盾、被新资料取代的过时结论、无入链孤儿页、被提到但无专页的重要概念、缺失交叉引用、指向不存在原文的引用。
- 输出结构化报告：问题类型、涉及页面、建议动作。
- 报告写入 `log.md`；问题项可被接受修复或标记为暂不处理。
- 预埋 5 类问题的检出率 >= 80%。

#### US-18 用 CLI / API 让 Agent 管理

作为维护 Agent，我想通过稳定的 CLI / API 完成捕获、Inbox、ingest、query、lint，以便不必依赖某个聊天窗口的一次性操作。

- CLI 与 API 覆盖同一组核心动作：`capture`、`inbox`、`ingest`、`query`、`lint`、`source`、`plugin`。
- 每个动作有机器可读输出（JSON）和人可读摘要。
- API 需要本机认证。方案 `TBD`，但不得默认无鉴权对局域网暴露原文。
- Agent 不能通过这些接口改写 `raw/` 正文；删除 / 归档是单独的、显式的主理人动作。

#### US-19 暂停、恢复或移除一个信息源

作为主理人，我想关掉某个太吵的源，而不丢掉它已经留下的原文。

- 每个源可启用 / 暂停。
- 暂停后不再进新货；已有 `raw/` 和 Wiki 引用保留。
- 移除适配器不等于删除历史原文；删除历史必须二次确认。
- 源状态可在 CLI / API 查询。

#### US-20 查看目录和时间线

作为主理人 / 维护 Agent，我想先看 `index.md` 和 `log.md`，以便在中等规模下不用上向量库也能找到路。

- `index.md` 按页面类型或主题列出：链接、一句话摘要、来源数或更新时间。
- `log.md` 只追加；每条以稳定前缀开头，便于 `grep`。建议格式：`## [YYYY-MM-DD] ingest | 标题`。
- ingest / query / lint / 去留 都必须能在 log 里找到对应条目。
- index 与真实页面不一致时，lint 必须报出来。

### 2.4 Functional Requirements（功能需求一览）

| ID | 能力 | 终态要求 |
|---|---|---|
| FR-01 | 原始资料存储 | 文件系统上的不可变原文 + 媒体 + 元数据 |
| FR-02 | 最小元数据 | 见 4.2，accepted / compiled 必须 100% 完整 |
| FR-03 | 聊天适配器 | QQ / 微信 / Telegram / Discord；微信 / QQ 允许降级 |
| FR-04 | 文档适配器 | GitHub 指定仓库、语雀、Obsidian 目录 |
| FR-05 | 公开内容适配器 | B 站 / 小红书 / X / 微博，仅主动投递或剪藏 |
| FR-06 | 手记入口 | CLI / API，后续皮肤可再包一层 |
| FR-07 | 插件源 | Manifest + 捕获契约 + 样例插件 |
| FR-08 | Inbox 与人在回路 | 活水源默认审核 |
| FR-09 | LLM 预建议 | 去留、标签、主题，失败不阻塞收藏 |
| FR-10 | Ingest | 摘要、旧页更新、index、log |
| FR-11 | Query | 先目录后下钻，答案可回写 |
| FR-12 | Lint | 六类健康检查 |
| FR-13 | 重编 | 只改 Wiki，不改原文 |
| FR-14 | 回链 | Wiki → raw id → 打开原文 / 媒体 |
| FR-15 | CLI / API | 同一组核心动作 |
| FR-16 | 展示层 | Markdown 可被 Obsidian 打开；自研 UI 非必须 |
| FR-17 | Schema | 页面类型、新建 / 更新规则、禁写区 |

### 2.5 Non-Goals（非目标）

这些不是「以后也不做」，其中一部分只是终态也不该做成产品主航道。

| 不做 | 原因 |
|---|---|
| 再做一个语雀式协同笔记软件 | 皮肤可以后换。没有稳定入口和编译层，界面只是另一个文件夹。 |
| 以向量库 / RAG 作为主检索 | 当前要解决的是关系沉淀和复利，不是语义检索还不够强。 |
| 把 Graphify 当主产品形态 | 主输入是聊天、社交、想法和少量文档，没有 AST，噪声模型不同。图谱只能做内部增强。 |
| 全量自动灌入所有聊天和社交 | 活水源一接上，知识库会先被噪声淹没。 |
| 全站爬取公开平台 | 只接受用户主动投递、剪藏或 @bot。 |
| 企业权限矩阵、多租户、合同库字段抽取 | 这是个人知识库，不是企业知识库。 |
| 让人亲手维护 Wiki 正文 | 人放弃 Wiki 的原因就是维护负担。 |
| 把「做很强的自动聚类 / 图谱问答」当第一期或主界面 | 没有稳定条目、metadata 和 Schema，图谱只是把混乱画得更漂亮。 |
| 把非官方微信 / QQ 协议写成唯一接入方式 | 高风险，必须可降级。 |

## 3. AI System Requirements（AI 系统要求）

### 3.1 Role Split（分工）

| 谁 | 负责 | 不负责 |
|---|---|---|
| 人 | 选源、判断「有意思」、裁决矛盾、决定什么值得强调 | 亲手改 10 到 15 个交叉引用 |
| LLM | 去留建议、摘要、归档、交叉引用、更新旧页、回写、巡检 | 改原文、发明一套新的整理法、把活水源全自动入 Wiki |
| Schema | 约束页面类型、新建 / 更新规则、禁写区、引用格式 | 绑定某个具体模型 |

模型可以换，Schema 不能每周重写。

### 3.2 Tool Requirements（工具要求）

维护 Agent 必须能看见并选择以下工具，而不是把流程写死成单次 prompt。工具列表作为真相源提供给 Agent，由它按 Schema 选择。

| 工具 | 英文名建议 | 作用 | 禁区 |
|---|---|---|---|
| 捕获原文 | `capture_raw` | 写入 raw + 最小元数据 | 不得写 Wiki |
| 列 Inbox | `list_inbox` | 看待审条目和建议 | 不得默默接受 |
| 去留 | `review_item` | 接受 / 拒绝 / 浅收 / 改标签主题 | 不得改 raw 正文 |
| 读原文 | `read_raw` | 读单条原文和媒体 | 只读 |
| 读 Wiki | `read_wiki` | 读页面、index、log | 只读 |
| 写 Wiki | `write_wiki` | 新建或更新页面 | 不得写 `raw/` |
| 更新目录 | `update_index` | 维护 `index.md` | 不得手写乱序到不可解析 |
| 追加日志 | `append_log` | 只追加 `log.md` | 不得改历史条目 |
| 关键词检索 | `search_keyword` | 对 Wiki / 原文做目录和关键词检索 | 中等规模的主检索 |
| 摄入 | `ingest` | 按 Schema 编译一条或一批 | 失败要可重试 |
| 查询 | `query_wiki` | 先 index 再下钻 | 不得把临场答案冒充已有综合页 |
| 回写 | `file_answer` | 把好答案存成 Wiki 页 | 必须带引用 |
| 巡检 | `lint_wiki` | 输出结构化问题 | 不得直接静默改完而不报告 |
| 重编 | `recompile` | 从原文重建部分 Wiki | 不得改 raw |
| 源管理 | `manage_source` | 启用 / 暂停源和插件 | 不得顺手删历史 |

可选增强，不是主航道：

| 可选工具 | 何时才能上 |
|---|---|
| 向量检索 `search_vector` | 页面已经稳定，且出现「说法不同、意思接近」的查询失败 |
| 图路径 `search_graph` | 页面开始互相指认，需要问「A 怎么连到 B」 |
| 网页抓取 `fetch_url` | 仅用于用户主动投递的 URL，补全文或媒体 |

### 3.3 Schema Requirements（结构约定）

必须有一份人和 LLM 共同维护的 Schema，建议同时存在：

- 给 Agent 读的规则文档：`schema/AGENTS.md` 或等价物
- 给机器校验的 JSON Schema：`raw-item.schema.json`、`wiki-page.schema.json`

Schema 至少回答：

1. 一条原始信息最小有哪些字段。
2. Wiki 页有哪些类型：源摘要、实体、概念、主题、综合、对比、问答沉淀。
3. 什么时候更新旧页，什么时候新建页。
4. 事实性表述如何回到原文。
5. 查询结果如何回写。
6. 哪些路径 LLM 不能改：`raw/`、历史 `log.md` 条目、插件目录中不属于自己的文件。
7. Inbox 的默认策略：哪些源必须等人。
8. 「以后可能有用」如何标记，何时才升级为深编。

没有 Schema，不得宣称编译层已完成。

### 3.4 Evaluation Strategy（评测策略）

必须有一套可复跑的金标集（Golden Set），而不是只靠「看起来挺聪明」。

#### 3.4.1 金标集构成

| 子集 | 规模 | 内容 |
|---|---|---|
| 原文样本 | >= 20 | 覆盖聊天文本、聊天图片、GitHub 文档、公开帖子、手记；其中至少 5 条是高噪声、应被拒绝或浅收 |
| 跨页样本 | >= 5 | 同一主题的多来源故事，例如「一张 QQ 图 + 两周后的 GitHub 文档 + 一条手记」 |
| 综合问题 | >= 10 | 必须读已编译页才能稳定答对，而不是只靠单条原文 |
| 巡检预埋 | >= 5 | 矛盾、过时、孤儿、缺链、缺页各至少 1 |

金标集放在仓库里，可重复执行。具体目录 `TBD`。

#### 3.4.2 评测项

| 评测 | 通过线 | 说明 |
|---|---|---|
| 原文不可变 | 100% | 任何 AI 动作前后，`raw/` 哈希不变，除非主理人显式归档 / 删除 |
| 元数据完整 | 100% | accepted / compiled 通过 JSON Schema |
| 活水源不自动编译 | 100% | 聊天 / 公开内容样本不得跳过 Inbox |
| 去留建议精度 | >= 80% | 在已标注的噪声聊天上，keep / drop 与人工标签一致 |
| 源摘要与目录 | 100% | 每条应编译样本都有摘要页、index、log |
| 跨页更新 | >= 80% | 预期待更新的旧页确实被更新 |
| 事实回链 | >= 95% | 来自资料的事实句能回到 raw id |
| 综合问答 | >= 80% | 10 道综合题中至少 8 道引用了综合 / 实体 / 主题页 |
| 回写复利 | 100% | 回写后再问，能命中新页 |
| 巡检出病 | >= 80% | 预埋问题被检出 |
| Schema 纪律 | 100% | 连续两次 ingest 不得发明 Schema 以外的页面类型 |

#### 3.4.3 人审抽检

LLM 会一本正经写错。除自动评测外，主理人抽检规则：

- 每 20 次 ingest 至少抽 1 次：打开源摘要、一个被更新的旧页、对应原文。
- 发现事实错误：标记矛盾或直接重编，不得只在聊天里改口。

### 3.5 Prompt and Tool List Management（提示词与工具列表）

前端提示词、后端提示词、Agent 目标、工具列表、默认文案、状态 key、阈值，必须集中管理，禁止散落在函数体或 JSX 里。命名必须表达业务语义，例如 `PROACTIVE_MEMORY_PREVIEW_GOAL` 这种风格，而不是 `TEMP_TEXT`。

本产品至少要有这些真相源：

- 维护 Agent 目标（Maintainer Agent Goal）
- 去留建议提示词
- ingest / query / lint 提示词
- 工具列表元数据
- 状态枚举：`captured` / `suggested` / `accepted` / `rejected` / `keep_for_later` / `compiled`
- 评测阈值常量

模型供应商、模型名、温度等配置保持 `TBD`，但必须可替换，且不写进 Schema 正文。

### 4.2 Data Contracts（数据契约）

#### 4.2.1 原始条目最小字段

| 字段 | 英文 | 必填时机 | 说明 |
|---|---|---|---|
| 条目 ID | `id` | 创建时 | 稳定唯一。建议 ULID，具体 `TBD` |
| 来源类型 | `source_type` | 创建时 | `chat` / `docs` / `public` / `self` / `plugin` |
| 来源名 | `source_name` | 创建时 | `qq` / `wechat` / `telegram` / `discord` / `github` / `yuque` / `obsidian` / `bilibili` / `xiaohongshu` / `x` / `weibo` / `manual` / 插件 ID |
| 捕获时间 | `captured_at` | 创建时 | ISO 8601 |
| 原始时间 | `authored_at` | 能拿到就填 | 消息发送时间或文档提交时间 |
| 原始定位符 | `source_locator` | 创建时 | 消息 ID、仓库路径、URL、本地路径 |
| 媒体类型 | `media_type` | 创建时 | `text` / `image` / `video` / `mixed` / `file` |
| 标题 | `title` | 可空 | 没有标题时可为预览句 |
| 正文路径 | `body_path` | 创建时 | 相对 `raw/` |
| 媒体路径 | `media_paths` | 创建时 | 数组，可空 |
| 留下原因 | `why_kept` | 接受时 | 人或 LLM 建议经人确认后的原因 |
| 摄入状态 | `ingest_status` | 创建时 | 见状态枚举 |
| 插件 ID | `plugin_id` | 插件源必填 | 其他源为空 |
| 标签 | `tags` | 接受时建议有 | 人可改 |
| 候选主题 | `candidate_topics` | 建议时 | 人可改 |
| 扩展 | `extra` | 可选 | 适配器私有字段，不得破坏最小字段 |

#### 4.2.2 Wiki 页面最小字段

| 字段 | 英文 | 说明 |
|---|---|---|
| 页面类型 | `page_type` | `source_summary` / `entity` / `concept` / `topic` / `synthesis` / `comparison` / `filed_answer` / `index` / `log` |
| 标题 | `title` | 人可读 |
| 更新时间 | `updated_at` | ISO 8601 |
| 引用原文 | `source_ids` | raw id 列表 |
| 标签 | `tags` | 可空 |
| 相关页 | `related_pages` | wikilink 列表 |

正文使用 Markdown。事实句或关键段落必须能回到 `source_ids`。

#### 4.2.3 状态机

```text
captured --> suggested --> accepted --> compiled
                 │            │
                 ├--> rejected
                 └--> keep_for_later --> accepted --> compiled
```

规则：

- `chat` / `public` 不得从 `captured` 直接到 `compiled`。
- `docs` / `self` 是否跳过 Inbox，由 Schema 配置，默认建议仍进 Inbox。
- `rejected` 和 `keep_for_later` 都保留原文。
- 任何状态变化都追加 log。

### 4.3 Integration Points（集成点）

| 集成 | 方式 | 约束 |
|---|---|---|
| Telegram / Discord | 官方 Bot API | 终态必做之一 |
| QQ / 微信 | 官方能力或用户主动推送 / 导出 | 非官方协议不得成为唯一路径 |
| GitHub | API、Webhook 或定时拉取指定仓库文档 | 只拉用户配置的仓库和路径 |
| 语雀 | 官方 API 或导出，`TBD` | 不可用时降级为导出文件 |
| Obsidian 目录 | 文件系统同步 | 只读对方目录，写入只发生在本库 raw/wiki |
| B 站 / 小红书 / X / 微博 | @bot、分享、剪藏 | 禁止全站爬取 |
| LLM | 用户配置的模型接口，`TBD` | 可替换；一次请求默认只带相关条目，不默认上传全库 |
| Obsidian 浏览 | 打开 wiki 目录 | 不是必须的插件 |
| CLI | 本机命令 | 与 API 同构 |
| HTTP API | 本机或用户指定绑定，`TBD` | 默认需要鉴权 |
| 插件 | Manifest + 捕获契约 | 进程隔离或至少路径隔离，`TBD` |

持久化主形态：Markdown + JSON / YAML 元数据，兼容 git 和 Obsidian。是否另加数据库属于实现细节，`TBD`；若加数据库，Markdown 仍必须能作为可阅读导出或主存储之一。

语言、框架、打包方式（是否 Electron、是否沿用当前仓库桌宠栈）全部 `TBD`。本 PRD 不绑定现有桌宠项目的技术选型。

### 4.4 Interface Sketch（接口草图）

命名可在实现时调整，语义不可丢。

CLI：

```text
sourcehub capture --source manual --title "..." --body "..."
sourcehub capture --source github --locator "owner/repo/path"
sourcehub inbox list
sourcehub inbox review <id> --accept|--reject|--later --tags ... --topics ...
sourcehub ingest <id>
sourcehub ingest --accepted
sourcehub query "我之前为什么对本地优先感兴趣"
sourcehub query "..." --file
sourcehub lint
sourcehub recompile --item <id> | --topic <name>
sourcehub source list|enable|pause
sourcehub plugin list|enable|disable
sourcehub open-raw <id>
```

API 与上述动作一一对应，返回 JSON。错误必须区分：源不可达、鉴权失败、Schema 校验失败、模型失败、条目不存在。

### 4.5 Retrieval Policy（检索策略）

检索跟着知识形态走，禁止过早把所有入口收成 embedding。

| 知识形态 | 先用什么 |
|---|---|
| 命名良好的页面 | `index.md`、标题、标签 |
| 代码、日志、原文定位 | 关键词 / grep |
| 说法不同但意思接近 | 再考虑向量 |
| 两个对象如何相连 | 再考虑图路径 |

终态允许向量和图作为增强层，但：

- Query 的默认路径仍是目录 + 页面。
- 没有稳定页面时，不得把图谱当作主界面。
- 过时结论被新资料推翻后，编译层要更新页面；不能只靠向量里躺着的旧碎片。

### 4.6 Security & Privacy（安全与隐私）

1. **默认个人本地。** 原文、媒体、Wiki、源凭证默认落在本机。云同步若要做，必须显式开启，`TBD`。
2. **凭证隔离。** 聊天和平台 token 不得写入 `wiki/`，不得进 git。配置文件要可被忽略。
3. **最小送模。** ingest / 去留建议默认只发送当前条目、相关 Wiki 页和 Schema，不默认打包全部聊天记录。
4. **活水源默认审核。** 系统不得在主理人未接受时，把群聊天编进综合页。
5. **删除权。** 主理人可归档或删除某条原文；之后 lint 必须扫出悬挂引用。编译层自己不能删原文。
6. **API 鉴权。** 本机 API 默认不裸奔。具体方案 `TBD`。
7. **插件权限。** 插件只能写入自己产生的原始条目，不能读其他源的凭证。
8. **媒体。** 图片和附件下载到本地。外链只作定位符，不作为唯一副本。
9. **合规。** 不提供绕过平台风控或破解私人会话的能力说明。微信 / QQ 以用户主动导出或官方能力为准。

## 5. Risks & Roadmap（风险与路线图）

### 5.1 Phased Rollout（分阶段交付）

本文写的是终态。下面只规定到达终态的顺序，不把后段能力从需求里删掉。

#### MVP（先能存，再能编一次）

- 原始条目 Schema、`raw/` 不可变、最小元数据校验。
- 手记入口 + 至少再打通 1 个源。推荐顺序：手记 + GitHub 文档；若主理人更常从聊天收藏，可改成手记 + 一个有官方 Bot 的聊天平台。
- Inbox、人在回路、去留建议。
- 第一版编译：源摘要、标签、主题页、`index.md`、`log.md`。
- CLI。
- Wiki 可被 Obsidian 打开。
- 金标集起步：至少 10 条原文、5 道问题、原文不可变测试。

验收：一条手记和一份文档能被收进 raw、被人接受、编成摘要和主题页，并能从 Wiki 打开原文。

#### v1.1（活水源 + 回写 + 巡检）

- Telegram 或 Discord Bot。
- 公开内容的一种主动投递或剪藏。
- 实体页 / 综合页，一次 ingest 更新旧页。
- Query 与好答案回写。
- Lint 第一版。
- 插件契约和 1 个样例插件。
- 去留建议精度开始按金标集回归。

验收：同一主题的两条不同来源被编到同一主题页；一次提问的结论能回写成页；lint 能找出预埋孤儿页。

#### v2.0（完整终态）

- 四类来源的适配器齐备，微信 / QQ 至少有一条稳定降级路径。
- 全部核心 CLI / API。
- 完整 Schema：六类 Wiki 页 + 回写页。
- 重编、源暂停、浅收、矛盾标记。
- 评测集达到第 3.4 节规模和通过线。
- 向量检索、知识图谱仅作为可选增强上线，且默认关闭或排在目录检索之后。
- 自研展示界面仍非必须；若做，也只消费同一套 raw / wiki / API。

验收：第 1.3 节全部成功标准通过。

### 5.2 Technical Risks（技术风险）

| 风险 | 为什么严重 | 缓解 |
|---|---|---|
| 微信 / QQ 接入不稳定或不合法 | 最想收的源可能正好最难接 | 适配器可插拔；官方或用户主动推送优先；不把非官方协议当唯一路径 |
| 活水源噪声淹没 Wiki | 全量自动会把知识库变成垃圾桶 | Inbox 强制；浅收状态；暂停源 |
| Schema 不稳，LLM 每次发明新整理法 | 库看起来在长大，其实在分裂 | JSON Schema 校验页面类型；连续 ingest 纪律评测 |
| ingest 太贵或太慢 | 一份资料可能改 10 到 15 页 | 先做该更新的页，再允许批量；失败可重试；浅收不深编 |
| LLM 一本正经写错 | 个人世界会被错误结论污染 | 原文不可变；回链；矛盾标记；抽检；可重编 |
| 图片 / 视频理解差 | 很多「有意思」是图 | 媒体本地化；去留阶段让人看图；编译时图文分步读 |
| 过早上向量或图谱 | 放弃已经编译好的结构 | 检索策略写进 Schema；增强层默认不挡主航道 |
| 凭证或私聊泄漏 | 聊天记录进模型或进 git | 凭证隔离；最小送模；API 鉴权 |
| 展示层做成另一个语雀 | 工期被皮肤吃掉 | MVP 只用 Markdown + Obsidian + CLI |

### 5.3 Open Questions（待确认）
