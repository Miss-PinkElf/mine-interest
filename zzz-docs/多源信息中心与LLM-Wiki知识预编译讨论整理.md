# 多源信息中心与 LLM Wiki 知识预编译讨论整理

## 一句话结论

要做的不是再做一个语雀，也不是再套一层检索增强生成（RAG, Retrieval-Augmented Generation）。真正的方向是：

> 先把散落在聊天、社交、仓库和脑子里的「我觉得有用」捞进来，再由大语言模型（LLM, Large Language Model）持续编译成一份会复利的个人维基（Wiki）。

Karpathy 的 LLM Wiki 解决后半段「怎么整理、怎么积累」。当前想法真正多出来的难点，是前半段「怎么把 QQ / 微信 / GitHub / 小红书这些活水源持续接进来」。

## 1. 前因后果：这件事为什么这样想

### 1.1 事情是怎么开始的

本轮没有改代码，也没有开 mission。用户先丢了三份笔记，要求讲解：

1. `zzz-prompt-debug/多种信息源整合.md`：自己的产品想法，并配了一张手绘结构图。
2. `zzz-prompt-debug/llm-wiki.md`：Karpathy 的 LLM Wiki 方法说明。原文来自 [gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)，不是一个现成软件。
3. `zzz-prompt-debug/llm-wiki-mine.md`：自己对 LLM Wiki、Graphify、几篇微信文章的补充判断。

当前仓库名就是 `mine-interest-source-hub`，和「信息源中心」这个念头是对得上的。所以这轮讨论的性质是：先把「想做什么」和「业界已经怎么想」叠在一起看清楚，而不是立刻选型或开工。

### 1.2 用户真正想解决的问题

手绘图的中间是一个圆：个人知识库 + 多种信息源 + 笔记软件。四周是输入，下面是沉淀。

四周输入可以分成四类：

| 来源类型 | 例子 | 接入方式 |
|---|---|---|
| 聊天平台 | QQ、微信、Telegram、Discord | Bot 接入 |
| 文档仓库 | GitHub Wiki、语雀、Obsidian | 同步 / 拉取文档 |
| 公开内容 | B 站、小红书、X、微博的帖子、视频、评论 | 在内容里 `@xxbot` |
| 自己写的 | 想法、冷门知识、好玩的项目、以后可能有用的东西 | 手动记录 |

产品约束也已经写在笔记里：

- 每条信息要有结构化元数据（Structured Metadata），说明它是什么、从哪来、什么时候进来。
- 对外提供命令行接口（CLI, Command Line Interface）或应用程序接口（API, Application Programming Interface），方便 AI 管理。
- 信息源最好能像插件一样自己接。
- 整理方式先想了两层：AI 整理 + 标签分类（Tag）。
- 图边上有一句很关键的动机：**自己不喜欢断舍离，总想把来时路记下来。**

所以动机不是「再做一个更好看的笔记软件」，而是：

> 不想让有意思的聊天记录、图片、仓库文档、随手想法断掉。先收住，再慢慢编成自己的 Wiki。

### 1.3 为什么不满意传统 RAG

三份笔记叠在一起后，共同针对的是同一件事：大多数人用 LLM 处理文档的方式，是提问时再检索、再拼答案。

典型流程是：

1. 把文档切成碎片（chunk）
2. 做成向量（embedding）
3. 提问时取最像的几段
4. 让模型当场拼一个答案

NotebookLM、ChatGPT 上传文件、大多数企业知识库，都走这条路。它能用，但有一个致命问题：**知识不会积累。**

今天问「这五篇材料合在一起说明什么」，模型得重新找、重新拼。明天再问一个更细的问题，还得再来一遍。交叉引用、矛盾、综合判断，每次都从零发现，不会沉淀成一份越来越厚的资产。

Karpathy 把这个判断说得很干脆：LLM 每次都在 rediscover，没有 accumulation。

用户自己的补充更准一层：

> 文档之间、记忆之间肯定不是孤立的，这个联系 RAG 可能做不好。  
> 关键词检索、索引、概述、手动切片，效果也可能不错。  
> 需要一个 JSON 或 Schema，让 LLM 来维护。

也就是说，用户不满意的不只是「检索不准」，而是「关系留不住、结构没人维护、每次提问都重新考古」。

### 1.4 为什么选 LLM Wiki，而不是再做一个向量库

LLM Wiki 换的是处理时机，不是再换一个检索算法。

它的做法是：资料进来时就编译一次，之后一直维护。提问时先读已经编好的 Wiki，而不是每次从原文重新发现知识。Karpathy 称之为一份会复利的持久产物（Persistent, Compounding Artifact）。

三层结构是：

```text
原始资料（Raw Sources）     不可改，真相源（source of truth）
        ↓  LLM 只读不写
Wiki（Markdown 页面）       LLM 拥有，人只读
        ↑
结构约定（Schema）          告诉 LLM 怎么整理、怎么更新
例如 AGENTS.md / CLAUDE.md
```

三个日常操作是：

- 摄入（Ingest）：新资料进来，生成摘要、更新实体页 / 概念页、改索引、写日志。一份资料可能碰到 10 到 15 个页面。
- 查询（Query）：对着 Wiki 提问。好答案要回写进 Wiki，不能只留在聊天记录里。
- 巡检（Lint）：定期体检矛盾、过时结论、孤儿页、缺失交叉引用。

两份特殊文件是：

- `index.md`：内容目录。中等规模（大约 100 份资料、几百个页面）时，先读目录再下钻，往往就够用。
- `log.md`：只追加的时间线。记录 ingest / query / lint。

分工也很明确：

- 人负责：选源、提问、判断什么重要。
- LLM 负责：摘要、归档、交叉引用、记账。

当时采用这个方向，不是因为它更新潮，而是因为它正好打中两个约束：

1. 人养不住 Wiki，是因为维护成本涨得比价值快。LLM 不会烦，一次能改很多文件。
2. 用户已经明确觉得「关系」比「相似片段」更重要，而页面之间的交叉引用、综合页、实体页，就是在编译关系，不是在赌向量相似度。

### 1.5 为什么 Graphify 被一起拿出来，却不能直接当答案

用户笔记里同时列了：

- [nashsu/llm_wiki](https://github.com/nashsu/llm_wiki)：把 Karpathy 的方法做成桌面应用。
- [Graphify](https://github.com/Graphify-Labs/graphify)：把一个目录编成可查询的知识图谱（Knowledge Graph）。

一句话区分：

> LLM Wiki 把知识编成页面；Graphify 把知识编成关系。

Graphify 的默认场景更偏代码仓库、文档、PDF。代码部分用树sitter（tree-sitter）抽象语法树（AST, Abstract Syntax Tree）做确定性解析，不用 LLM；文档和媒体才走语义抽取。每条边会标：

- `EXTRACTED`：原文里明确写了
- `INFERRED`：系统推断出来的

它刻意不是向量库。你问的是「A 和 B 怎么连上的」，不是「哪几个 chunk 最像这个问题」。

所以 Graphify 值得借鉴的是「关系先编出来、边要可解释」。它不能直接当答案，是因为当前想法的主输入不是代码仓库，而是聊天记录、社交帖子、随手想法和少量文档。那些东西没有 AST，噪声也大得多。

### 1.6 当时已经形成的决策逻辑

本轮没有批准实现方案，但讲解后已经收敛出几条判断。它们是讨论结论，不是开工许可。

1. **收集和编译是两层，不要混成一件事。**  
   Karpathy 默认资料已经在文件夹里。当前想法默认资料还散落在聊天和社交平台。先能存，再能编。

2. **原文和整理层必须分开。**  
   原始资料只进不出，永远不改。Wiki / 摘要 / 标签 / 关系可以重编。这是为了以后整理错了还能回到原文。

3. **先 schema 和索引，不要先赌向量 RAG。**  
   中等规模用 `index.md`、关键词、概述、标签就可能够用。向量检索是增强项，不是地基。

4. **人要待在回路里。**  
   尤其是「有意思的聊天记录 / 图片」这种源。全量灌进来会变成垃圾桶；全靠人点又太累。更稳的是：先粗收，LLM 建议，人做去留。

5. **Obsidian / 语雀 / 自研笔记界面只是皮肤。**  
   真正值钱的是：稳定的原始资料层、一份人和 LLM 共同维护的 Schema、会回写的编译层。

6. **难度顺序已经排过。**  
   先能存，再能编，再能连，最后才是酷炫检索。

### 1.7 当时的约束条件

- 本轮只讲解，不改代码，不开 mission。
- 微信第一篇文章《Pinecone 给 RAG 办了葬礼》被拦截，正文没读到；第二篇只读到标题；第三篇全文读到了。
- 内置网页抓取工具不可用，GitHub 和微信主要靠页面打开工具补读。
- 当前仓库里还没有对应的 Align / Plan，因此本文不能被当成已批准设计。
- 用户明确说过：自己不喜欢断舍离，想记下来时路。这意味着系统必须能容纳「现在不一定有用、以后可能有用」的东西，但不能因此放弃筛选。

### 1.8 为什么不那么做

下面这些路不是错，而是相对当前问题更不划算，或者过早。

| 不先做的事 | 为什么先不做 |
|---|---|
| 再做一个语雀式笔记软件 | 皮肤可以后换。先没有稳定入口和编译层，界面再好看也只是另一个文件夹。 |
| 一上来上向量库 / RAG | 当前痛点是「关系没沉淀、知识不复利」，不是「语义检索还不够强」。 |
| 直接当 Graphify 的个人版 | Graphify 更擅长代码和结构化文档。聊天、图片、社交帖子没有 AST，噪声模型也完全不同。 |
| 全量自动接入所有聊天和社交 | 活水源一接上，知识库会先被噪声淹没。「有意思」必须有人在回路里。 |
| 先做很强的自动聚类 / 图谱问答 | 没有稳定条目、metadata 和 schema，图谱只是把混乱画得更漂亮。 |
| 让人亲手维护 Wiki | 人放弃 Wiki 的原因就是维护负担。这正是要让 LLM 做记账的理由。 |

## 2. 例子说明：把抽象判断变成可感知的东西

### 2.1 为什么「每次提问都重新拼」会让人觉得知识没留下

假设手里有三份材料：

1. 产品发布说明：v2.3 新增批量导入，单次最多 5000 条，emoji 可能导致失败。
2. 客服工单：最近 7 天 42 个客户反馈导入失败，31 个和 emoji 有关，其中 12 个是金融客户。
3. 销售纪要：金融客户很关注批量导入，竞品已经支持 10000 条。

如果有人问：「批量导入现在最大的问题是什么，对金融客户有什么影响？」

传统 RAG 会把这三份材料切碎，检索几段，让模型当场拼答案。下次再问「企业版客户呢」「竞品差距呢」，它还得重新找、重新组合、重新判断。

LLM Wiki 会在资料进来时就做三件事：

1. 给每份资料写摘要页。
2. 给「金融客户」这种反复出现的对象写实体页。
3. 给「批量导入风险」写一篇综合分析页，把产品限制、客服反馈、客户影响、竞品差距放在一起。

以后再问，先读综合页。知识被编译过一次，不是每次重新考古。

这个例子说明的不是「综合页比 chunk 高级」，而是：**多文档关系一旦被问过、被看清，就应该变成资产。**

### 2.2 为什么聊天记录更需要「收集」和「编译」分开

把上面的产品例子换成用户真正会遇到的场景：

某天 QQ 群里有人丢了一张架构图，顺口说「这个项目以后可能会开源」。过了两周，GitHub 某个仓库更新了一份文档，恰好和那张图是同一件事。再过一个月，自己在小红书看到一个类似做法，随手觉得「以后可能有用」。

如果系统只是「全部记下来」，三个月后你搜「那个图」，会先翻出一堆表情包和吃饭讨论。  
如果系统只做 RAG，提问时可能召回小红书那条，却召不回两周后的 GitHub 文档，更不会主动告诉你它们是同一件事。  
如果系统先把三条都收成不可变原文，再让 LLM 在编译层写一个主题页「某某架构做法」，并把三条原文挂上去，这件事才开始变成知识，而不是时间线上的三个碎片。

这就是为什么本轮反复强调：

- 原文永不改，是为了以后还能回到那张图和那句原话。
- Wiki 可以重编，是因为第一次整理很可能标错主题。
- 「有意思」不能全自动，是因为群里 99% 的内容对未来的你没有意义。

### 2.3 为什么一份资料要改 10 到 15 个页面

假设新摄入的是一篇关于「本地优先笔记」的文章。一次像样的 ingest 可能同时碰到：

- 源摘要页：这篇文章讲了什么
- 概念页：本地优先（local-first）
- 概念页：CRDT / 同步冲突
- 实体页：某个具体软件，比如 Obsidian
- 对比页：本地优先 vs 云同步
- 综合页：自己为什么想做信息源中心
- `index.md`
- `log.md`

这看起来很重，但这正是 Wiki 养得住的原因。人做这件事会放弃；LLM 一次就能改完。如果只生成一篇摘要、不更新旧页，知识库仍然是一堆孤立文件。

### 2.4 为什么好答案必须回写

继续用「批量导入」的例子。如果有人问出了一个很好的问题：「金融客户的失败，是产品上限问题，还是 emoji 兼容问题？」

模型如果只在聊天里答一次，这个判断第二天就没了。  
如果把这个问答沉淀成一页「金融客户批量导入失败归因」，下一次 ingest 再进来一份新工单时，LLM 就可以更新这页，而不是让你重新发明这个问题。

对当前想法来说，这一点特别重要。用户会随手记冷门知识、临时想法。「提问 / 比较 / 突然想通」本身就是知识生产，不应该只活在会话里。

### 2.5 为什么 `index.md` 往往比向量库先够用

假设 Wiki 里暂时只有 80 个页面。提问「我之前为什么对本地优先感兴趣」。

一条更稳的路径是：

1. 先读 `index.md`，看到「本地优先」「Obsidian」「信息源中心动机」这几页。
2. 打开这几页。
3. 必要时再回原文。

这条路径可解释、可调试、token 也可控。  
一上来做 embedding，表面上更「智能」，但你会很难回答：它为什么召回了这三段，漏了那一页综合分析，以及旧结论被新资料推翻后向量里是不是还躺着过时碎片。

所以本轮的判断不是「向量无用」，而是：**在页面数量还不大、结构还可以被人看懂时，目录 + 关键词 + 概述更适合当主航道。**

### 2.6 合同例子：为什么「关系」比「查得到」更难

第三篇微信文章用 30 份合同做对比。查金额、日期、甲乙方，传统 RAG 也能答个七七八八。真正容易翻车的是：

主合同之后又签了补充协议，追加了设备；验收单记录延期 45 天，但双方协商免除违约金。

如果只召回验收单，会看见延期。  
如果只召回主合同，会按违约金条款算钱。  
只有把主合同、补充协议、验收单串起来，才知道为什么延期、为什么没扣钱。

这个例子和企业知识库有关，但对个人信息源中心同样成立：QQ 里的一张图、两周后的 GitHub 文档、一个月后的随手想法，分开看都成立，合在一起才是完整故事。

### 2.7 为什么 Obsidian 被提到，却不是核心

Karpathy 自己的用法是：一边 LLM Agent 改文件，一边 Obsidian 看图谱、跟链接。用户手绘图上也写了「其实 Obsidian 的形式要比我现在的好用」。

这里容易误会成「所以应该做 Obsidian 插件」。本轮的判断不是这个。

Obsidian 只是一个很好用的 Markdown 浏览器。它能让人立刻看见页面之间的边，所以适合当皮肤和验收界面。真正有价值的仍然是 Agent 生成并维护的那层 Wiki。没有这层，Obsidian 只是又一个能阅读的文件夹。

## 3. 知识延伸：从「预编译知识」往外长

这一节不按百科去列产品，只沿当前主题自然往外长：同一份知识，到底应该在什么时候被组织，组织成什么形状，由谁维护。

### 3.1 从 Memex、卡片盒到 LLM Wiki：维护者终于出现了

Karpathy 自己把 LLM Wiki 连到了 1945 年 Bush 的 Memex（记忆扩展器）：一份私人的、被主动策展的知识库，文档之间的联想路径和文档本身一样值钱。卡片盒笔记（Zettelkasten）、常青笔记（Evergreen Notes）、个人知识管理（PKM, Personal Knowledge Management）后来都在重复这件事。

它们反复失败的原因通常不是「不会分类」，而是：

- 新笔记进来时，旧笔记不会自动更新
- 交叉引用要人记得去补
- 矛盾不会自己冒出来
- 维护负担随规模超线性增长

LLM Wiki 并没有发明一种新的知识形状。它发明的是一个不怕记账的维护者。页面、反向链接、综合笔记这些形状，人早就用过；以前缺的是谁愿意持续改 15 个文件。

取舍很清楚：

- 人维护：质量上限高，规模上限低，最后往往停更。
- LLM 维护：规模和一致性更好，但会一本正经地写错，必须能回到原文。
- 人机共维：人决定什么值得留下、什么值得强调；LLM 负责传播式更新。

这和当前想法是对齐的。用户不是不会记，而是不想因为维护太烦而放弃「记下来时路」。

### 3.2 四种组织时机：切块、编译、连边、建索引

围绕「什么时候组织知识」，现在至少有四条路。它们不是互斥，但主航道只能先选一条。

| 路线 | 组织时机 | 知识形态 | 擅长 | 代价 |
|---|---|---|---|---|
| 传统 RAG | 提问时 | 文本碎片（chunk） | 单点事实、模糊语义 | 多文档综合每次重来，关系留不住 |
| LLM Wiki | 资料进入时 | 摘要页 / 实体页 / 综合页 | 复利、矛盾标记、主题演化 | ingest 重，schema 要持续养 |
| 知识图谱 | 资料进入或定期构图 | 节点和边 | 路径、社区、意外连接 | 图会脏，边的解释成本高 |
| 目录 + 关键词 | 写入时建目录，提问时 grep | 文件、标题、标签 | 可解释、便宜、好调试 | 语义近似和别名问题要另补 |

为什么本轮把「编译」放在「切块」前面：用户要的是一份会长大的个人世界，不是一个每次都能勉强答一句的问答框。  
为什么不把「图谱」当第一性：当前主输入是聊天和社交，先没有稳定实体，边会非常吵。  
为什么「目录 + 关键词」必须保留：它是最小可运行的导航层，也是 LLM 自己最容易操作的层。

一个实用拼法是：

1. 用 schema 决定条目长什么样
2. 用 Wiki 编译主题和实体
3. 用目录 / 关键词导航
4. 需要时再补图谱或向量

### 3.3 页面优先还是关系优先

LLM Wiki 和 Graphify 的分歧，不是工具偏好，是知识应该先长成什么形状。

页面优先（Wiki-first）的好处：

- 人能直接读
- 适合综合判断、时间线和「我现在怎么看这件事」
- 天然适合 Obsidian 这种浏览方式
- 查询结果也容易回写成新页面

关系优先（Graph-first）的好处：

- 适合问「A 怎么连到 B」
- 更容易发现意外连接和知识空洞
- 代码、API、模块这类本来就有边的对象非常合适
- 边带 `EXTRACTED` / `INFERRED` 时，比「模型感觉它们相关」更可审计

对当前产品，更合理的折中不是二选一：

- 对外给人看的，仍应是页面。人不会每天盯着一张大图生活。
- 对内给 Agent 用的，可以逐渐补一层关系。比如「这条 QQ 图片」和「那个 GitHub 文档」指向同一主题。

如果过早把聊天记录直接构图，得到的往往不是知识网络，而是一张谁都在连谁的毛线团。

### 3.4 个人知识库和企业知识库不是同一套最佳实践

第三篇微信文章的结论值得单独留下：个人知识库的最佳实践，不一定是企业知识库的最佳实践。

个人侧更在乎：

- 来时路有没有断
- 主题会不会自己长大
- 自己能不能在 Obsidian 里逛起来
- 噪声和「以后可能有用」如何共存

企业侧更在乎：

- 受控 schema
- 结构化字段
- 原文引用
- 权限边界
- 可复跑评测

所以从 LLM Wiki / Graphify 里该抄的，不是桌面应用本身，而是两句工程判断：

1. RAG 少了一层知识预编译。
2. Agent 不一定每次都要从原始文件穷读，结构化导航很重要。

当前仓库如果继续往「个人兴趣信息源中心」走，应更靠近个人侧：允许一点主观、允许一点不完整，但必须保住原文、时间和来源。不要一上来按合同库、权限矩阵、字段抽取去设计。

### 3.5 活水源和死文档，噪声模型完全不同

Karpathy 举例里的论文、书籍章节、会议纪要，默认是已经被人选过的资料。  
当前想法里的 QQ、微信、B 站评论、小红书帖子，默认是高噪声流。

这会改变整条流水线：

- 死文档：ingest 可以偏重「读懂并编进去」
- 活水源：必须先有「值不值得留下」这一跳

「值不值得留下」如果全靠规则，会漏掉真正有意思但形态不规则的东西。  
如果全靠 LLM，又贵，也会有稳定误判。  
更像是分层：

1. 来源层先粗收，保留原文和 metadata
2. LLM 给出去留建议、候选标签、可能所属主题
3. 人做最终去留，尤其是图片、一句闲聊、以后可能有用的项目

这和「让 Agent 自己选工具」是同一类设计：系统提供候选和结构，判断权不下放成全自动。

### 3.6 检索不是越聪明越好，而是要和知识形态匹配

第二篇微信文章的标题已经把一个工程事实写死了：`grep` + bash 在不少任务上能打赢 embedding，还更便宜。这和用户说的「关键词、索引、概述可能也不错」是同一方向。

可以把它理解成：检索方法应该跟着知识形态走。

- 知识如果已经是命名良好的页面，先读 `index.md` 和标题。
- 知识如果是代码或日志，先 grep。
- 知识如果是「说法不一样但意思接近」，再上向量。
- 知识如果是「两个对象如何相连」，走图路径，而不是 top-k chunk。

过早把所有入口都收成 embedding，表面统一，实际是在放弃已经编译好的结构。Wiki 存在的意义之一，就是让后续检索变简单，而不是再给 Wiki 做一次盲检索。

### 3.7 Schema 为什么比「再聪明一点的模型」更关键

用户已经写到：需要一个 JSON 或 Schema，让 LLM 来维护。这比纠结用哪个聊天模型更关键。

原因是：编译层一旦没有稳定约定，LLM 每次都会发明一种新的整理法。今天把一条 QQ 图片写成「灵感」，明天写成「项目」，后天写成「未分类」，知识库看起来在长大，其实在分裂。

一份最小有用的 Schema，至少要回答：

- 一条原始信息最小有哪些字段：来源、时间、原文位置、媒体类型、为什么留下
- Wiki 页有哪些类型：源摘要、实体、主题、综合、对比
- 什么时候更新旧页，什么时候新建页
- 事实性表述如何回到原文
- 查询结果如何回写
- 哪些文件 LLM 不能改

模型可以换，Schema 不能每周重写。这和代码库里的 `AGENTS.md` 是同一类东西：它让 Agent 变成有纪律的维护者，而不是每次都从零扮演图书管理员。

### 3.8 对当前仓库的直接含义

如果以后要把这轮讨论推进成产品，自然切口不是「先做一套个人 RAG」，而是：

1. 先定义一条信息最小长什么样。
2. 先打通一两个源，证明「能收进来、能打开原文、能带 metadata」。
3. 再让 LLM 按 Schema 做第一版编译：摘要、标签、主题页。
4. 先用目录和关键词找，不先上向量。
5. 等页面开始互相指认，再考虑图谱。

这也是本轮最后留下的分工建议：

- 收集层：当前想法独有，也更难。
- 编译层：LLM Wiki 和 Graphify 能直接借鉴。
- 展示层：Obsidian 或自研界面都可以后换。
