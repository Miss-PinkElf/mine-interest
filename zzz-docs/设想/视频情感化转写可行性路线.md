## 结论

整体可行，但不要把它理解成“一个 STT 模型直接解决”。更合理的定义是一个多阶段媒体理解 Agent（multistage media understanding agent）：先做稳定的语音转文字（Speech to Text, STT）和时间轴（timeline），再把音频情绪（speech emotion）、画面表情（facial expression）、字幕/OCR（Optical Character Recognition）、评论区/搜索语境（social/search context）和多模态大模型（multimodal LLM）的判断融合成结构化描述。

推荐路线是：Python 核心管线（Python pipeline）负责重计算和可复现处理，Agent 工具层（agent tool layer）负责按需搜索、反向搜图、评论区读取和多模态校正，n8n workflow 负责流程编排、人审节点和自动化集成。n8n 不建议承担全部媒体处理逻辑，因为视频切片、抽帧、缓存、GPU 推理和错误恢复更适合代码化。

如果优先做本地开源 MVP（Minimum Viable Product，最小可行产品），建议把 SenseVoice-Small（FunASR）纳入主候选：它覆盖 ASR（Automatic Speech Recognition，自动语音识别）、SER（Speech Emotion Recognition，语音情绪识别）、AED（Audio Event Detection，音频事件检测），并且 2026-05 的项目说明中已增加 speaker diarization（说话人分离）组合用法。它不应被写成“唯一方案”，但很适合作为中文/英文混合视频的本地 baseline（基线）。

最小可行产品（MVP, Minimum Viable Product）建议先做“上传一个视频 -> 输出带时间戳的情感化转写 JSON/Markdown”，暂时不追求全自动理解所有梗。梗、meme、时事和领域语境应设计成可选的研究增强阶段（research enrichment stage）。

## 候选技术栈

### 1. 音频前处理（Audio Preprocessing）

用途：从视频里提取音频，尽量保留人声干声，降低背景音乐（BGM, background music）和噪声对 STT 的影响。

- FFmpeg：基础媒体处理（media processing），用于抽音频、切片、重采样、抽帧。
- audio-separator：可作为服务端/脚本化人声分离（vocal separation）候选，支持 CLI（Command Line Interface，命令行接口）和 Python API，并集成 UVR（Ultimate Vocal Remover）生态中的 MDX-Net、VR Arch、Demucs、MDXC 等模型。其模型列表包含 `model_bs_roformer_ep_317_sdr_12.9755.ckpt`，可输出 vocals / instrumental 两路 stem（音轨）。
- Demucs：音乐源分离（music source separation），可分离 vocals、drums、bass 和 accompaniment；文档中也支持 `--two-stems=vocals` 只分离人声。它适合“有背景音乐的视频”，但项目主页明确提示原仓库已不再积极维护，所以应作为可用但需验证的组件。
- UVR（Ultimate Vocal Remover）：实际使用上常集成 Demucs 等模型，适合桌面化批处理，但如果做服务端管线，建议直接调用 Demucs 或其他 source separation backend。
- RNNoise / noisereduce / WebRTC VAD：用于传统降噪（denoise）和语音活动检测（Voice Activity Detection, VAD），适合轻量预处理。

判断：可行，但不能保证把人声和 BGM 完美分离。重 BGM、多人重叠说话、音效遮挡会显著影响后续识别。来自 `数据集处理.md` 的经验也应吸收：降噪（denoise）不是越多越好，过度降噪可能破坏音色、语气、能量变化等情感线索；应先做噪声/BGM/混响检测，再选择性处理。

### 2. 语音识别与说话人分离（STT and Speaker Diarization）

用途：得到可靠文本、时间戳和说话人标签。

- WhisperX：基于 Whisper / faster-whisper 的批量语音识别工具，支持词级时间戳（word-level timestamps）和说话人分离（speaker diarization）。它明确提供 speaker ID labels，并说明 overlapping speech 和 diarization 仍不完美。
- pyannote.audio：Python 说话人分离工具包（speaker diarization toolkit），提供预训练 pipeline，也可本地运行；适合需要独立控制 speaker diarization 的场景。
- SenseVoice-Small（FunASR）：本地开源候选，项目说明定位为 speech foundation model（语音基础模型），覆盖 ASR、LID（Language Identification，语种识别）、SER 和 AED。当前项目 README 还给出 VAD（Voice Activity Detection，语音活动检测）+ CAM++ speaker model + punctuation model 的说话人标签示例。适合作为“本地优先”的中文/英文 baseline。
- OpenAI Speech to Text：OpenAI Audio API 支持 `gpt-4o-transcribe`、`gpt-4o-mini-transcribe` 和 `gpt-4o-transcribe-diarize`，其中 diarized JSON 可返回 speaker、start、end 等片段信息。

推荐：本地优先比较两条 baseline：SenseVoice-Small（FunASR）一体化路线，以及 WhisperX + pyannote.audio 组合路线。如果接受云 API 成本和隐私边界，可以用 OpenAI `gpt-4o-transcribe-diarize` 快速做对照 baseline。不要在没有实测样本集前断言某一条路线绝对最优。

### 3. 语音情绪识别（Speech Emotion Recognition, SER）

用途：从声音本身判断愤怒、开心、讽刺、紧张、疲惫等线索。

- SpeechBrain emotion-recognition-wav2vec2-IEMOCAP：Hugging Face 模型卡显示它用于 emotion recognition，基于 wav2vec2，在 IEMOCAP 数据上训练。但模型卡也提示不保证迁移到其它数据集的性能。
- SenseVoice-Small：可直接输出富转写（rich transcription）中的情绪和音频事件标签，适合作为第一版 SER baseline。它的情绪标签应被视为候选证据，不应直接覆盖最终叙事判断。
- emotion2vec+：FunASR 生态中的情感分类候选，可作为 SenseVoice 之外的二次验证或参考音频/片段筛选工具。来自 `数据集处理.md` 的经验是，情感分类后仍要人工校对。
- openSMILE / eGeMAPS：更传统的声学特征（acoustic features）路线，可提取 pitch、energy、jitter、shimmer 等特征，适合给 LLM 做证据而非直接下结论。
- LLM 校正层：不要只信单一 SER 分类结果。更稳的做法是把语速、音高、能量、停顿、上下文文本和视觉表情一起交给 LLM 生成“情绪解释 + 置信度 + 证据”。

判断：可行，但情绪识别是弱可靠模块。它应该输出“证据和概率”，不要输出绝对结论。

### 4. 抽帧、多模态理解与表情识别（Frame Sampling, Multimodal Understanding, Facial Expression Recognition）

用途：理解画面、人物表情、动作、字幕、屏幕文字、视觉梗。

- FFmpeg 抽帧：可按每 5 秒抽帧，也可以按镜头变化（scene change）或语音片段边界抽帧。固定 5 秒简单，但容易错过关键表情；建议 MVP 先固定抽帧，后续加 scene-aware sampling。
- OpenAI Vision：OpenAI 图片与视觉（Images and vision）能力支持把 image input 传入模型，让模型分析画面内容。适合做“这帧发生了什么、人物表情像什么、是否有文字/梗图元素”的语义解释。
- MediaPipe Face Landmarker：可输出 3D face landmarks、blendshape scores 和 facial transformation matrix；文档说明 blendshape scores 可表示 facial expression。它适合作为客观表情特征，不直接等同复杂情绪。
- DeepFace / FER：可作为快速表情分类工具，但要注意种族、光照、遮挡、夸张表情、二次元/表情包视频的泛化风险。
- Google Cloud Vision OCR：可做画面文字识别（OCR），特别适合短视频字幕、弹幕、梗图文字。

推荐：视觉侧不要只让 LLM 看每 5 秒截图。更稳的方式是“抽帧 -> OCR -> face landmarks/blendshapes -> 多模态 LLM 总结”，把模型判断和可解释特征一起保存。

### 5. 梗、meme、时事与评论区语境（Meme, Current Events, Social Context）

用途：解决“字面文本不够理解视频”的问题。

- YouTube Data API commentThreads：官方 API 可按 videoId 读取评论线程（comment threads），适合 YouTube 来源视频。
- SerpApi Google Lens API：可用图片 URL 做类似 Google Lens 的视觉搜索结果，适合找同款梗图、截图来源或商品/人物线索。
- Google Custom Search / Bing Web Search / Tavily：可用关键词搜索视频标题、字幕关键词、截图 OCR 关键词和评论区高频词。
- 平台评论抓取：Bilibili、抖音、TikTok、小红书等平台的评论获取通常涉及登录、反爬和服务条款，建议先做“手动导入评论文本”或“仅官方 API/合规接口”。

判断：可行但不稳定。外部语境增强（context enrichment）最好设计成可选工具，而不是 STT 主流程的硬依赖。

### 6. Agent 编排与状态管理（Agent Orchestration and State Management）

用途：把长任务拆成可恢复、可审计、可条件路由的节点，避免一个超长 prompt 串完整个视频处理流程。

- LangGraph：LangChain 官方文档将其定位为构建、管理和部署 long-running, stateful agents（长运行、有状态 Agent）的低层编排框架，核心能力包括 persistence（持久化）、human-in-the-loop（人在环路）、memory（记忆）和 debugging/observability（调试与可观测性）。这与视频理解任务的长耗时、分支决策、失败恢复高度匹配。
- LangChain：适合接模型、工具和常见 Agent loop，但不建议把所有状态恢复都压在 LangChain chain 里。
- n8n AI Agent：适合可视化触发、Webhook、外部 SaaS 集成和人工审核节点；不适合独立承担 GPU 推理、视频切片和大文件缓存。

推荐：研发阶段优先 LangGraph + Python worker；稳定后把 worker 封装为 FastAPI（REST API）或队列任务，再由 n8n 作为外层 workflow shell 调用。

## 音频预处理细化方案（Audio Preprocessing Recipe）

这部分主要吸收 `数据集处理.md` 的音频清洗经验，并改写为视频理解管线可用的工程步骤。

### 推荐顺序

```text
输入视频/音频
  -> FFmpeg 抽取音频
  -> 响度检测与标准化（loudness normalization）
  -> 判断 BGM / 噪声 / 混响强度
  -> 必要时做人声分离（vocal separation）
  -> 必要时去混响（dereverb / de-echo）
  -> 谨慎降噪（denoise）
  -> VAD 切片 + 最大片段时长限制
  -> STT / SER / diarization
  -> 低置信度片段人工校对
```

### 可借鉴规则

- 干声（dry vocal）优先：如果原音频足够干净，例如游戏素材、录屏干声、会议原始音频，可以跳过人声分离，避免模型处理引入伪影（artifact）。
- 先分离再去混响：对 BGM 明显的视频，优先用 BS-Roformer / audio-separator / UVR5 提取 vocals，再按混响程度选择 DeEcho-Normal、DeEcho-Aggressive 或 Dereverb 类处理。
- 降噪要保守：降噪会破坏音色细节。对情绪识别来说，能量、气声、尾音、停顿都可能是证据，所以只在噪声明显影响 STT 时开启。
- 响度要统一：可借鉴 `数据集处理.md` 中“最大音量约 -9dB 到 -6dB”的经验，但实现时建议写成可配置的响度标准化（loudness normalization），不要硬编码成唯一阈值。
- 切片要受显存约束：长片段容易导致模型推理慢或爆显存。建议用 VAD 切片，并设置 `max_single_segment_time`、`min_interval`、`max_sil_kept` 等同类参数；过密语音可降低静音间隔阈值，但要避免把完整语义切碎。
- 字幕优先：如果视频有内嵌字幕（burned-in subtitle）、外挂字幕（sidecar subtitle）或可抽取字幕轨，应优先抽取并作为高置信文本来源，再用 STT 做补漏和校正。
- 标注要可校对：对低置信度 STT、重叠说话、强噪声、强情绪或疑似反讽片段，进入人工校对（human review）队列，不要强行自动定稿。

## 推荐工作流

### 阶段 A：媒体准备（Media Preparation）

1. 输入视频或音频文件。
2. 用 FFmpeg 提取音频、标准化采样率、生成低码率代理文件（proxy media）。
3. 做响度检测与标准化，记录原始响度、峰值、是否削波（clipping）。
4. 如检测到 BGM 较强，调用 audio-separator / UVR / Demucs 做人声分离（vocal separation）。
5. 如混响明显，按轻度/中度/重度选择 de-echo 或 dereverb；如原音频清晰则跳过。
6. 谨慎降噪，只在噪声明显影响识别时启用。
7. 使用 VAD（Voice Activity Detection）切出语音片段，生成初始时间轴，并保留最大片段长度约束。

输出：`audio_raw.wav`、`audio_vocals.wav`、`audio_clean.wav`、`audio_quality_report.json`、`segments.json`、`frames/`。

### 阶段 B：语音转写（Speech Transcription）

1. 先尝试抽取字幕轨或 OCR 字幕，作为高置信文本候选。
2. 用 SenseVoice-Small 或 WhisperX / OpenAI `gpt-4o-transcribe-diarize` 生成文本。
3. 如果用 WhisperX，接 pyannote.audio 做 speaker diarization；如果用 SenseVoice，验证 VAD + speaker model + punctuation model 的句级 speaker label 是否满足样本要求。
4. 对每个 segment 保存 start、end、speaker、raw_text、clean_text、word_timestamps、source（subtitle / STT / OCR）。
5. 用 LLM 做一次轻量文本修正，但必须保留 raw_text，避免过度改写。

输出：`transcript_raw.json`、`transcript_aligned.json`。

### 阶段 C：视觉与表情分析（Visual and Facial Analysis）

1. 按语音 segment 边界抽关键帧；MVP 可先每 5 秒抽帧。
2. 对关键帧做 OCR（Optical Character Recognition）和画面描述（image captioning）。
3. 对有人脸的帧运行 MediaPipe Face Landmarker，记录 landmarks 和 blendshape scores。
4. 多模态 LLM 汇总每个时间段的画面、表情、动作和屏幕文字。

输出：`visual_observations.json`。

### 阶段 D：情绪融合（Emotion Fusion）

1. 从音频提取 pitch、energy、speech rate、pause 等声学特征。
2. 运行 SenseVoice / emotion2vec+ / SpeechBrain 等语音情绪识别（SER）得到候选标签和置信度。
3. 记录音频事件检测（AED）结果，例如 laughter、crying、applause、bgm、cough。
4. 汇合文本语义、音频特征、视觉表情、上下文画面。
5. 由 LLM 输出“情绪标签 + 证据 + 不确定性”，例如：愤怒（angry）、调侃（ironic）、尴尬（awkward）、兴奋（excited）、冷淡（flat）。

输出：`emotion_segments.json`。

### 阶段 E：外部语境增强（External Context Enrichment）

1. 如果视频来源是 YouTube，读取标题、描述和评论区高频信息。
2. 对代表性截图做反向搜图（reverse image search）或 Google Lens 搜索。
3. 对 OCR 文本、评论高频词和 STT 关键词做搜索。
4. LLM 判断是否存在 meme、时事、领域黑话或反讽语境。

输出：`context_evidence.json`。

### 阶段 F：最终叙事输出（Narrative Output）

1. 以 segment 为单位生成“对话 + 情绪 + 表情 + 语境解释”。
2. 输出 JSON 供程序使用，同时输出 Markdown 供人阅读。
3. 对每个推断结论标注 confidence（置信度）和 evidence（证据）。
4. 对不确定内容明确写“可能 / 不确定 / 需要人工确认”，不要伪造确定性。

输出：`emotion_transcript.json`、`emotion_transcript.md`。

## Agent / n8n 设计建议

### 推荐架构

```text
用户上传视频
  -> Python Media Worker（FFmpeg / audio-separator / SenseVoice / WhisperX / pyannote / MediaPipe）
  -> Artifact Store（音频、帧、JSON、日志）
  -> LangGraph Agent Orchestrator（LLM + tools + state）
  -> Optional n8n Workflow（通知、人审、搜索 API、结果分发）
  -> 最终 Markdown / JSON / 可视化时间轴
```

### 为什么不要纯 n8n

n8n 的 AI Agent node 可以连接外部 tools 和 APIs，并让 Agent 根据任务选择工具，这与“让 Agent 自己选择工具”的想法一致。但视频处理是长任务、重 I/O、重 GPU、强缓存需求的流程，纯 n8n 节点会难以管理中间文件、失败重试和资源占用。

更稳的方案是：

- Python 负责 deterministic pipeline（确定性管线）：切片、抽帧、模型调用、缓存、日志。
- LangGraph Agent 负责 reasoning pipeline（推理管线）：决定是否搜索、是否反向搜图、如何融合证据，并记录每个节点的状态与失败恢复入口。
- n8n 负责 workflow shell（工作流壳层）：触发、人工审核、消息通知、Webhook、结果写入 Notion/飞书/数据库。

### Agent 工具列表建议（Tool List）

不要把工具硬编码在 prompt 里，而是让 Agent 读取工具元数据（tool metadata），类似 Codex/skills 的模式。

建议工具：

- `extract_audio(video_path)`：提取音频。
- `separate_vocals(audio_path)`：人声分离。
- `normalize_loudness(audio_path)`：响度标准化。
- `dereverb_audio(audio_path, mode)`：去混响或去回声。
- `transcribe_audio(audio_path, diarize=true, engine="sensevoice|whisperx|openai")`：STT + speaker diarization。
- `detect_audio_emotion(audio_path, engine="sensevoice|emotion2vec|speechbrain")`：语音情绪识别。
- `sample_frames(video_path, strategy)`：抽帧。
- `analyze_frame(image_path)`：多模态画面理解。
- `detect_face_expression(image_path)`：表情/面部动作检测。
- `ocr_frame(image_path)`：画面文字识别。
- `search_web(query)`：搜索外部语境。
- `reverse_image_search(image_path)`：反向搜图。
- `fetch_comments(source_url)`：读取评论或导入评论。
- `fuse_emotion(segment_bundle)`：融合文本、音频、视觉和外部证据。
- `render_report(result_json)`：输出 Markdown/HTML。

## 可行性分级

| 能力 | 可行性 | 风险 |
| --- | --- | --- |
| 普通 STT 转写 | 高 | 噪声、口音、多人重叠 |
| 说话人分离（speaker diarization） | 中高 | 重叠说话、短句切换、同音色人物 |
| 人声/BGM 分离 | 中 | 背景音强、音效复杂、压缩音质差 |
| 语音情绪识别（SER） | 中 | 泛化弱，容易把语速/音量误判成情绪 |
| 音频事件检测（AED） | 中高 | 标签粒度有限，事件和情绪不能直接等同 |
| 表情识别（facial expression recognition） | 中 | 遮挡、夸张表情、动漫/表情包、低清视频 |
| 多模态 LLM 画面理解 | 中高 | 抽帧遗漏、细节幻觉、成本 |
| 梗/meme/时事理解 | 中 | 搜索结果不稳定，评论区噪声大 |
| 全自动可信融合 | 中 | 需要证据链和人工校验机制 |

## 主要风险与规避

1. 情绪不是单一模型输出。
   - 风险：SER 或表情分类可能误判。
   - 规避：输出 evidence（证据）和 confidence（置信度），让 LLM 做综合解释，低置信度时标注“可能”。

2. 视频梗依赖外部语境。
   - 风险：只看视频本身可能无法理解内涵。
   - 规避：把评论区、搜索、反向搜图设计成可选增强工具，并保留来源链接。

3. 多人重叠说话会破坏转写。
   - 风险：speaker diarization 和 STT 都会下降。
   - 规避：对重叠区间标注 `overlap=true`，允许人工校正。

4. LLM 可能过度脑补。
   - 风险：把普通表情解释成复杂意图。
   - 规避：要求每个解释绑定来自文本、音频、视觉或搜索的 evidence；无证据时不能下确定结论。

5. 平台数据合规。
   - 风险：评论抓取、视频下载、反爬可能违反平台条款。
   - 规避：优先使用官方 API 或用户手动导入数据；文档和实现中明确数据来源。

6. 本地模型环境复杂。
   - 风险：CUDA、ONNX Runtime、PyTorch、FFmpeg、Hugging Face / ModelScope 模型下载和显存限制都会影响可复现性。
   - 规避：MVP 阶段固定 Python 版本和模型版本；优先提供 Docker / Conda 环境；把模型下载、GPU 可用性、FFmpeg 可用性写入启动自检。

7. pyannote.audio 与本地 Python 版本可能冲突。
   - 风险：说话人分离依赖链较重，Python 3.12+ 或特定 CUDA 组合可能出问题。
   - 规避：优先锁定 Python 3.11；保留 SenseVoice speaker diarization、FunASR CAM++ 或 Resemblyzer 类后备路线。

## MVP 建议

第一版最小可行产品（MVP）建议只做：

1. 输入本地视频文件。
2. FFmpeg 提取音频和每 5 秒抽帧，并生成 `audio_quality_report.json`。
3. audio-separator / UVR / Demucs 作为可选人声分离，不默认强制开启。
4. SenseVoice-Small 和 WhisperX + pyannote.audio 各跑一条小样本 baseline，比较中文/英文、噪声、多人场景效果。
5. 每个 segment 附近取 1-3 张图给多模态 LLM 分析画面。
6. 使用 SenseVoice / emotion2vec+ / 声学特征 + LLM 生成情绪解释。
7. 对低置信度片段输出人工审核列表。
8. 输出 `emotion_transcript.json` 和 `emotion_transcript.md`。

第一版不要做：

- 不做自动下载全平台视频。
- 不做复杂 UI。
- 不做训练自有情绪模型。
- 不做所有平台评论自动抓取。
- 不把“梗理解”作为必达指标，只做可选增强。

### 第一版范围与明确延期矩阵（MVP Scope and Deferred Scope Matrix）

| 能力 | 第一版是否做 | 本轮口径 | 后续触发条件 |
| --- | --- | --- | --- |
| 本地视频/音频输入 | 做 | 只支持用户提供的本地文件，不做平台下载 | MVP 通过后再评估 URL 输入 |
| 音频质量报告（audio quality report） | 做 | 输出响度、削波、BGM/噪声/混响初步判断 | 样本集验证后再扩展更多质量指标 |
| 人声分离（vocal separation） | 第一版可选 | audio-separator / UVR / Demucs 作为按需工具，不默认强制处理 | BGM 明显影响 STT（Speech to Text，语音转文字）时启用 |
| SenseVoice-Small baseline | 做 | 验证 ASR（Automatic Speech Recognition，自动语音识别）、SER（Speech Emotion Recognition，语音情绪识别）、AED（Audio Event Detection，音频事件检测） | 若中文/英文混合样本表现不足，再补其它模型 |
| WhisperX + pyannote.audio baseline | 做 | 作为词级时间戳（word-level timestamps）和说话人分离（speaker diarization）对照路线 | 若 pyannote 环境不稳定，切换后备 diarization 方案 |
| 每 5 秒抽帧 | 做 | 作为最简单视觉采样（frame sampling）策略 | 后续引入 scene-aware sampling（镜头感知抽帧） |
| 多模态 LLM 画面描述 | 做 | 只处理 segment 附近关键帧，输出证据化描述 | 成本可控后再扩展长视频原生理解 |
| 表情识别（facial expression recognition） | 第一版可选 | MediaPipe / DeepFace 只作为候选证据，不直接定稿情绪 | 清晰人脸样本足够后再提高权重 |
| 外部搜索 / 反向搜图 | 延期 | 不作为 MVP 必达能力 | Phase 3 进入 meme / 时事 / 语境增强时启用 |
| 评论区分析 | 延期 | 第一版只允许手动导入评论文本，不做平台抓取 | 明确平台、合规接口和数据权限后启用 |
| n8n workflow | 延期 | 第一版不创建 n8n workflow JSON | Python worker API 稳定后进入 Phase 4 |
| 前端 UI | 延期 | 第一版优先 CLI（Command Line Interface，命令行接口）或脚本输出 | 核心链路稳定后再设计 UI |
| 训练自有情绪模型 | 延期 | 先用 SenseVoice / emotion2vec+ / SpeechBrain 预训练能力 | 特定领域样本上情绪接受率不足时再考虑 fine-tune（微调） |
| 全自动梗理解 | 延期 | 第一版只输出“不确定 / 需要人工确认” | 外部证据链和人工审核机制稳定后再推进 |

## 工程实施路线与资源估算（Engineering Roadmap and Resource Estimate）

### Phase 1：音频闭环 MVP（2-3 周候选）

目标：跑通“音频 -> 说话人 -> 文本 -> 情绪/事件 -> Markdown/JSON”的最小闭环。

| 步骤 | 内容 | 验证标准 |
| --- | --- | --- |
| 1.1 | 固定 Python 3.11、FFmpeg、CUDA / CPU 环境 | 启动自检能输出 Python、FFmpeg、GPU、模型缓存状态 |
| 1.2 | 接入 audio-separator 或 UVR 类人声分离 | BGM 样本能输出 vocals / instrumental，且不会覆盖原始音频 |
| 1.3 | 接入 SenseVoice-Small | 中文/英文样本能输出文本、情绪标签、音频事件标签 |
| 1.4 | 接入 WhisperX + pyannote.audio | 多人样本能输出 speaker label 和时间戳 |
| 1.5 | 建立对照报告 | 同一批样本可比较 SenseVoice 与 WhisperX 路线的准确率、耗时、失败原因 |

### Phase 2：视频与多模态增强（2-3 周候选）

目标：加入抽帧、OCR、表情和多模态 LLM 解释。

| 步骤 | 内容 | 验证标准 |
| --- | --- | --- |
| 2.1 | 按固定间隔和 segment 边界抽帧 | 帧文件名带时间戳，可回溯到原视频 |
| 2.2 | 接入 OCR 和字幕轨抽取 | 有字幕视频优先使用字幕文本，OCR 作为补充 |
| 2.3 | 接入 MediaPipe / DeepFace | 清晰人脸样本能输出 landmarks / emotion 候选 |
| 2.4 | 多模态 LLM 融合 | 输出的情绪解释必须绑定文本、音频、视觉或搜索证据 |

### Phase 3：Agent 化与外部语境增强（2-3 周候选）

目标：让 Agent 根据内容决定是否搜索、反向搜图、读取评论或进入人工审核。

| 步骤 | 内容 | 验证标准 |
| --- | --- | --- |
| 3.1 | 用 LangGraph 拆分节点 | 每个节点有输入、输出、失败状态和可恢复 artifact |
| 3.2 | 接入搜索和反向搜图工具 | 疑似 meme 样本能返回外部证据或标记不确定 |
| 3.3 | 接入评论区或手动评论导入 | 能提取高频社区解读，但不直接替代模型判断 |
| 3.4 | 低置信度人工审核 | 输出待审核片段列表和证据包 |

### Phase 4：n8n 编排与产品化（2-4 周候选）

目标：把稳定的 Python worker 暴露为 API，由 n8n 负责触发、通知、人审和结果分发。

| 步骤 | 内容 | 验证标准 |
| --- | --- | --- |
| 4.1 | FastAPI 封装 Python worker | n8n 可通过 HTTP 调用任务 |
| 4.2 | 任务队列和 artifact store | 长视频任务可恢复，不丢中间结果 |
| 4.3 | n8n workflow shell | Webhook -> worker -> human review -> output 全链路跑通 |
| 4.4 | 成本与资源监控 | 每个视频记录处理时长、GPU/CPU、API 调用和失败原因 |

### 资源估算口径

- 最低可跑：CPU-only 可以跑部分 STT / SER / OCR，但长视频会很慢，适合功能验证，不适合作为体验基线。
- 推荐本地：8GB VRAM 起步，适合分时加载模型；12-16GB VRAM 更适合同时处理人声分离、STT 和视觉分析。
- 云 API：OpenAI / Gemini / 搜索 API 的价格变化较快，文档不写固定月成本。实现阶段应做 cost profiler（成本剖析器），按“每分钟视频、每张截图、每次搜索、每 1M token”记录。
- Gemini 低成本多模态路线值得关注，但具体模型名称、上下文窗口和价格必须以实施当日官方 pricing（价格）为准。

## 后续阶段建议

### 阶段 1：PRD / OpenSpec

把目标用户、输入输出、隐私边界、成本预算、支持语言和评价指标写清楚。重点定义：

- 主要输入：本地视频、本地音频、URL、评论文本。
- 主要输出：JSON、Markdown、字幕、可视化时间轴。
- 成功标准：STT 准确率、speaker 分离可用性、情绪解释人工接受率、处理耗时。

### 阶段 2：本地原型

先做 Python CLI（Command Line Interface，命令行接口），不用 UI：

```text
python -m emotion_transcript run --input sample.mp4 --output out/
```

生成固定目录：

```text
out/
  audio/
  frames/
  transcript_raw.json
  visual_observations.json
  emotion_transcript.json
  emotion_transcript.md
```

### 阶段 3：Agent 工具化

把每个阶段包装成工具，让 Agent 根据视频情况决定是否调用：

- 如果 BGM 弱，跳过人声分离。
- 如果没有人脸，跳过表情识别。
- 如果 OCR/评论提示有梗，再调用搜索工具。
- 如果低置信度，输出“需要人工确认”。

### 阶段 4：n8n 编排

n8n workflow 只做编排：

- Webhook 接收任务。
- 调用 Python worker API。
- 等待结果。
- 调用 Agent 做增强分析。
- 人工审核低置信度片段。
- 把结果发送到 Notion/飞书/数据库。
