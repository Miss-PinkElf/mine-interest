# 改动手册（Change Handbook）

## 这个 skill 解决什么问题

AI 改完东西后，用户常常只知道「好了」，但不知道：

- 到底动了哪些文件、哪些配置；
- 为什么这么改就能生效；
- 这个改法靠不靠谱、有没有前提条件；
- 不依赖 AI 时，自己怎么一步步复现；
- 出了问题怎么退回去。

本 skill 把这些信息整理成一份**用户能独立执行的中文手册**。核心不是复述聊天记录，而是把改动翻译成「事实 + 原理 + 可执行步骤」。

## 什么时候不要用

- 纯问答、只读排查、没有产生任何写操作：直接说明「本次没有实际改动」，不要硬编文档。
- 用户只想要一句话结论：先给结论，再问是否需要完整手册。

## 工作流

### 第 0 步：确认有没有真实改动

盘点本次对话中的所有写操作，包括但不限于：

- `Write` / `Edit` 修改的文件；
- `Bash` 中产生副作用的命令（安装、移动、删除、`cp`、`chmod`、服务重启等）；
- 配置文件修改（如 `~/.claude/settings.json`）；
- 新建、删除、备份的文件；
- 通过其他工具写入的内容。

如果没有任何写操作，直接告诉用户，不要生成文档。

### 第 1 步：收集事实（禁止凭记忆）

用户要的是能复现的手册，所以每条结论都要有证据。至少做下面四件事：

1. **仓库内改动用 git 取证**
   - 运行 `git -C <目录> status --short` 和 `git -C <目录> diff`。
   - 明确区分「本次对话造成的改动」与「对话开始前就存在的未提交改动」。例如本仓库可能在对话开始前就有 `M .claude/settings.local.json`、`M AGENTS.md`，这些不能算作本次改动。
   - 只看对话里确实写过的文件，不要把所有未提交改动都收进文档。

2. **读取关键文件的当前内容**
   - 引用真实路径和关键行号。
   - 改动涉及配置时，确认配置如何被加载、是否真的指向新文件（例如 `statusLine.command` 是否指向被改的脚本）。

3. **收集验证证据**
   - 有测试或运行输出就引用；没有就写「未验证」，不要写「应该可以」。
   - 能安全复测的，重新执行一次验证命令并记录输出。

4. **处理历史会话**
   - 如果用户指的是当前对话之前的改动，优先查 `git log` / `git diff` / 文件修改时间 / 备份文件。
   - 必要时查看 `~/.claude/projects/<项目目录 slug>/*.jsonl` 中的会话记录；找不到就向用户确认，不要猜。

### 第 2 步：确认范围与落盘位置

**范围**：默认覆盖本次对话的全部改动。用户点名某项时，只详细写该项，其余用一句话带过，避免把手册写成流水账。

**落盘位置**：默认跟**当前会话工作目录**走，而不是跟改动对象走。这样手册总能在用户正在工作的项目里找到，也方便随项目提交。

| 场景 | 文档位置 |
|---|---|
| 默认 | `<当前会话工作目录>/docs/change-notes/YYYY-MM-DD-<slug>.md` |
| 改动属于另一个 git 仓库，且用户希望文档跟仓库走 | `<该仓库根目录>/docs/change-notes/YYYY-MM-DD-<slug>.md` |
| 用户明确要求集中管理全局改动 | `~/.claude/change-notes/YYYY-MM-DD-<slug>.md` |
| 用户明确指定其它位置 | 以用户指定为准 |

- 即使改动对象是 `~/.claude` 等全局配置，默认也写到当前项目；只有在用户明确要求时才写全局目录。
- 文件名用 `YYYY-MM-DD-<slug>.md`，slug 用简短英文 kebab-case，例如 `2026-10-24-statusline-two-line.md`。
- 同名文件已存在时，更新原文件并刷新「更新时间」，不要新建 `-2`、`-final`。
- 仓库内文档中的路径一律用相对路径；引用仓库外的文件时用绝对路径并写明原因。

### 第 3 步：按模板写文档

读取 `assets/change-note-template.md`，按其中的固定章节输出。不要删减 Metadata 字段；某一项确实没有内容时写「无」或「未提供」，不要留空。

写每一节时的要点：

- **改了什么**：用表格列出文件/对象、改动类型、改动前、改动后。改动前的内容从旧文件、备份或 `git diff` 里取，不要凭记忆编。
- **原理**：解释数据流或调用链，让用户理解「为什么改这里会生效」。例如状态栏是「Claude Code 把 JSON 从 stdin 传给脚本，脚本把 stdout 当成状态栏」，而不是「改了脚本所以状态栏变了」。
- **为什么可以这么改**：给出依据（官方文档、源码、实测输出），并写清前提条件、风险和不适用的场景。
- **手动复现步骤**：从零开始、编号、命令可直接复制。关键路径不要用 `...` 省略。每一步尽量配一条「验证」。
- **回滚方案**：优先用备份文件；没有备份就给反向操作或 `git checkout` 命令。

### 第 4 步：自检

交付前逐条检查：

- [ ] `Metadata（元数据）` 齐全，创建/更新时间具体到分钟。
- [ ] 每条改动都能在对话、文件内容或 git diff 中找到证据。
- [ ] 没有把历史未提交改动误算成本次改动。
- [ ] 手动步骤从零可执行，路径正确，命令可复制。
- [ ] 至少有一条可观察的验证方法。
- [ ] 回滚方案可用（有备份或反向操作）。
- [ ] 没有输出 token、密钥、密码等敏感值。
- [ ] 文档用简体中文，专业术语中英双语。

## 写作规范

- 使用简体中文；专业术语首次出现用「中文（English）」格式。
- 结论必须有证据；没有验证过的内容明确标注「未验证」。
- 命令可复制，关键路径不省略；可以省略无关的日志输出，但要说清楚省略了什么。
- 危险操作（删除、覆盖、重启服务、改全局配置）要标注影响范围和回滚方式。
- 敏感信息脱敏为 `<已脱敏>`，不要把 `ANTHROPIC_AUTH_TOKEN`、API Key、密码写进文档。
- 只读地记录改动，不要为了写文档去修改被记录的对象。
- 篇幅以「能照着复现」为准，一般 100～250 行，不写空话。

## 输出后的动作

写完后告诉用户：

1. 文档的完整路径；
2. 一句话摘要；
3. 哪一步最需要人工确认（例如权限、服务重启、全局配置）；
4. 如果发现改动本身有问题或有未验证项，单独列出来。
